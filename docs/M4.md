# BeeZip — M4 (Explorer integration) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M3.md`](M3.md) and keeps their decisions, except where §13 corrects PLAN.md. Versions and licenses were checked on 2026-11-04 against crates.io. The APIs named here were checked in the sources of windows 0.62.2 (`Win32::UI::Shell`'s `IExplorerCommand` and `IEnumExplorerCommand`, `Win32::System::Com`'s `IClassFactory`, `Management::Deployment`'s `PackageManager`), windows-core 0.62.2, windows-future 0.3.2, toml_edit 0.25.17, tauri-build 2.7.4, tauri-utils 2.10.2 (capability window globs) and Tauri's NSIS template at `tauri-cli-v2.12.4` (`installer.nsi`, `FileAssociation.nsh`). The packaging rules were checked against Microsoft's pages on [unsigned packages](https://learn.microsoft.com/en-us/windows/msix/package/unsigned-package), [packaging with external location](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps) and [File Explorer context menus](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer).

Six spikes on this machine (Windows 11 build 26300, Developer Mode on, not elevated) back the Explorer design: a cascading `IExplorerCommand` in Rust, registered as a classic verb and from a sparse package, checked through the shell's own menu code and in real Explorer windows. §16 records what they showed. Three of their results change PLAN:
- a packaged verb also appears under "Show more options", so registering both ways shows BeeZip twice there;
- the Windows 11 menu shows one entry per package, so items can be hidden there but not moved to the top level;
- a process the packaged handler starts inherits the package's identity, and its AppData writes are redirected into the package's folder unless the manifest turns that off.

## Scope
- **Explorer menus:**
  - **`crates/beezip-menu`** (new, pure Rust): the menu model shared by everything below. It defines the items, which of them a selection gets, their titles, and the job request a click writes.
  - **`crates/beezip-shell`:** the COM DLL, `beezip_shell_<ver>.dll`, serving one cascading `IExplorerCommand` to both registrations. It is the second crate with unsafe code, after `beezip-unrar`.
  - **The classic registration:** HKCU keys, no admin. It is used on Windows 10, and on Windows 11 when the package can't be registered.
  - **The Windows 11 registration:** a sparse package (`beezip-sparse.msix`, identity `BeeZip`) with external location. It needs a trusted signature, or Developer Mode for the unsigned manifest.
  - **The commands:** `shell.status`, `shell.install` and `shell.uninstall` (System, hidden from MCP); `beezip shell …` on the command line.
- **Job mode:**
  - `shell.plan` turns a job request into steps;
  - `BeeZip.exe --job <file>` opens a small job window per request and runs its steps, or hands them to a running BeeZip;
  - "Open with BeeZip", "Extract to…" and "Compress to…" reach the main window and its dialogs.
- **Settings:**
  - `settings.get` and `settings.set`, which edit `config.toml` in place and keep its comments;
  - new `[shell]` and `[jobs]` sections, with the menu toggles mirrored to the registry for the DLL;
  - the engine picks up a change without a restart;
  - a settings page in the desktop app.
- **The CLI:** grouped subcommands, `beezip shell …` and `beezip settings …`.
- **Packaging:**
  - `cargo xtask dist` stages the DLL and the sparse manifest, and signs the package when given a certificate;
  - the NSIS hooks register the menu on install, remove it on uninstall and handle upgrades, including M3's lost association backup (§15);
  - `cargo xtask dev-cert` and `cargo xtask shell` for development.
- **End-to-end checks** on Windows 11 here, and on a Windows 10 22H2 VM (§12).

**Out of scope:**
- **M5:** adding to an existing archive. "Add to "a.zip"" when `a.zip` exists asks to replace it or keep both (§14).
- **M6:** production signing, so the Windows 11 menu from the installer needs `xtask dev-cert` or Developer Mode until then (§5.3); the updater; drag-out; the tauri-driver E2E test.
- **Not planned:**
  - a "Directory\Background" entry (right-clicking empty space in a folder);
  - an `IContextMenu` implementation. The spike showed the `IExplorerCommand` cascade in Windows 11's classic menu, and only Windows 10 is left to check (§11, step 9);
  - translated menu titles.
- **Follow-ups:** M3 §11 #54 (opening a million-entry zip takes 5 s) goes to M5 (§15).

## 3. The menu model (`beezip-menu`)

### 3.1 Items

| Id | Title | Offered for | Does |
|---|---|---|---|
| `open` | Open with BeeZip | archives | opens each as a tab in the main window |
| `extract-here` | Extract here | archives | `archive.extract` into the archive's folder with `smart` (M1 §4.3): into a folder named after it unless everything is under one top-level folder |
| `extract-folder` | Extract to "a\\" | archives | into `<folder>\<stem>\`; several archives: "Extract each to its own folder" |
| `extract-to` | Extract to… | archives | the main window's extract dialog |
| `test` | Test archive | archives | `archive.test` |
| `add-zip` | Add to "a.zip" | files and folders | `archive.create` beside the selection |
| `add-7z` | Add to "a.7z" | files and folders | the same, 7z |
| `add-tar-zst` | Add to "a.tar.zst" | files and folders | the same, tar.zst |
| `compress-to` | Compress to… | files and folders | the main window's create dialog with the selection as inputs |

- **The ids are stable:** they are config keys (`[shell.items]`), registry values and TS types.
- **Every item is shown by default.** Any can be hidden. "Archive" items come first, then the add items, with a separator before the first add item (`ECF_SEPARATORBEFORE`; whether the Windows 11 menu draws it is checked in PR 3).
- **The icon** is `BeeZip.exe,0` on the root and on items moved to the top level of the classic menu.

### 3.2 Which items a selection gets
`menu(selection, settings) -> Vec<Entry>` is a pure function, unit-tested and fuzzed (§10). It never touches the disk: Explorer calls `GetState` for every item on every right-click, out of process or not (§16, item 7).
- **Archives:** every selected item is a file whose extension, compound ones included (`.tar.zst`, `.7z.001`, `.part1.rar`), is one BeeZip reads.
  - **The list:** every extension in `formats.list`, plus `.001`. `xtask codegen` writes it into `gen_exts.rs`, and `codegen --check` keeps it current.
  - **Zip-based documents included:** unlike the file associations (M3 §5.4), the list keeps `.jar`, `.docx`, `.epub` and the like. Double-click stays with their apps, but "Extract here" on a `.jar` is useful.
- **Files and folders:** anything with a file-system path. Items without one (inside a zip folder, a phone) get no BeeZip entries.
- **Titles** come from the same stem function `shell.plan` uses, so the title and the result agree.
  - **Stems:** `a.tar.zst` → `a`, `a.7z.001` → `a`, `a.part1.rar` → `a`.
  - **Add items:** one item uses its own name; several use their folder's name.
  - **Long names** are cut to 40 characters with an ellipsis.
- **Large selections:** the classic verb showed for 20 files with all 20 reaching one `Invoke` (§16, item 6). There is no 15-item cut-off, so `MultiSelectModel` isn't needed.

### 3.3 The job request
A click writes this and starts BeeZip, with nothing else on the command line:

```json
{ "version": 1, "item": "extract-here", "paths": ["C:\\Users\\me\\Downloads\\a.zip", "C:\\Users\\me\\Downloads\\b.7z"] }
```

- **Where:** `%TEMP%\BeeZip\jobs\<random>.json`, created new and never overwritten.
- **Why a file:** PLAN's reason holds. A selection of thousands of paths doesn't fit a command line.
- **What BeeZip accepts:** only files in that folder, of at most 16 MiB, with `version` 1. It deletes each file once read, and on startup sweeps any older than a day.
- **The type:** `JobRequest` derives serde, and, behind a `wire` feature that beezip-commands turns on, JsonSchema, ts-rs and clap. The DLL builds without the feature, so it has none of those.

## 4. `beezip-shell` (the DLL)

### 4.1 COM objects
- **One class factory serves several CLSIDs:**
  - the **classic root**;
  - the **modern root**;
  - **one CLSID per item**, used only when the classic menu isn't cascaded (§5.1).

  The CLSIDs are new GUIDs fixed in `beezip-menu`; the spike's are not reused. The factory tells the context from the CLSID.
- **The root command** reports `ECF_HASSUBCOMMANDS`. `EnumSubCommands` returns the visible items, through an `IEnumExplorerCommand` whose `Next` honours `celt`; Explorer asks for one at a time.
- **Item commands:**
  - `GetTitle` comes from §3.2;
  - `GetState` is `ECS_ENABLED` or `ECS_HIDDEN`, and ignores `fOkToBeSlow`, since nothing in it is slow;
  - `GetCanonicalName` returns the item's GUID; `GetToolTip` is `E_NOTIMPL`;
  - `Invoke` is §4.3.
- **Object count:** `DllCanUnloadNow` counts live objects. In the spike Explorer released everything as the menu closed, and the surrogate unloaded the DLL.

### 4.2 Keeping Explorer safe
- **The classic menu loads the DLL into `explorer.exe`.** The spike's log showed it in the Explorer window's own process. The Windows 11 registration runs it in `DllHost.exe`, the COM surrogate, so a crash there can't take Explorer down (§16, item 4). The rules are written for the in-process case.
- **Every COM method body runs in `guard()`:** `catch_unwind`, then `E_UNEXPECTED`. Since Rust 1.81 a panic leaving an `extern "system"` function aborts the process, and `#[implement]` calls our methods from such functions. `panic = "unwind"` stays in every profile (PLAN §1).
- **Small and self-contained:**
  - no beezip-core, and no file I/O in any menu-building method;
  - settings are read with one `RegGetValue` per menu, from `HKCU\Software\BeeZip\Shell` (§5.4), so a toggle applies on the next right-click.
- **A debug log,** off by default: `Log = 1` under that key appends calls to `%LOCALAPPDATA%\BeeZip\shell.log`, as the spike did. That is how the manual checks see what Explorer asked.

### 4.3 Invoke
1. Collect the file-system paths (`SIGDN_FILESYSPATH`) from the `IShellItemArray`.
2. Write the job request (§3.3).
3. Start the app: `std::process::Command::new(app).arg("--job").arg(file).spawn()`. The app is the `App` value under the settings key; failing that, `BeeZip.exe` beside the DLL. The spawn is safe Rust, and no archive work ever runs in Explorer.
4. Call `AllowSetForegroundWindow(child)`, passing on whatever foreground right the host has. Whether the job window comes to the front from the Windows 11 menu, where the host is `DllHost.exe`, is a manual check (§12).

A process started this way from the Windows 11 menu inherits the package identity (§16, item 8). §5.2 is why that is harmless.

### 4.4 Building
- **The file name:** `cargo build -p beezip-shell` makes `beezip_shell.dll`. `xtask dist` stages it as `beezip_shell_<version>.dll`, so an upgrade never has to replace a file Explorer has loaded.
- **Exports:** `beezip_shell.def` exports `DllGetClassObject` and `DllCanUnloadNow` as `PRIVATE`, passed by `build.rs` as `cargo:rustc-cdylib-link-arg=/DEF:…`. Without it, link.exe warns LNK4104 (§16, item 10).
- **Unsafe code:** the crate has `#![allow(unsafe_code)]`, and each `unsafe` block carries a `SAFETY:` comment. The unsafe parts are:
  - the two exports;
  - `IEnumExplorerCommand::Next`'s pointer writes;
  - `CoTaskMemFree` of display names;
  - `AllowSetForegroundWindow`.

## 5. Registration

### 5.1 The classic menu (Windows 10, and Windows 11 without the package)
All under HKCU, no admin:

```
Software\Classes\CLSID\{classic root}\InprocServer32   (default) = <installdir>\beezip_shell_0.1.0.dll
                                                        ThreadingModel = Apartment
Software\Classes\*\shell\BeeZip                         ExplorerCommandHandler = {classic root}
Software\Classes\Directory\shell\BeeZip                 ExplorerCommandHandler = {classic root}
```

- **Without the cascade** (`[shell] cascade = false`), each visible item gets its own verb, `…\shell\BeeZip.<id>`, with its own CLSID key, and the root verb goes. `settings.set` rewrites the verbs when `cascade` or `[shell.items]` change.
- **Explorer re-reads static verbs** each time it builds a menu: new Explorer windows had the spike's keys at once, with no `SHChangeNotify`.
- **No `IContextMenu`:** the spike showed the cascade in Windows 11's classic menu, from `explorer.exe` and from the shell's menu builder, with state, multi-select and `Invoke`. Windows 10 22H2 is checked first in PR 3 (§11). If the cascade doesn't show there, PR 3 adds an `IContextMenu` for the classic registration only, as 7-Zip has.

### 5.2 The Windows 11 menu (sparse package)
- **`packaging/windows/sparse/AppxManifest.xml`:** identity `BeeZip`, version `<app version>.0`, `ProcessorArchitecture="neutral"`, and `uap10:AllowExternalContent`. It declares the `runFullTrust` and `unvirtualizedResources` capabilities. Its one `Application` is `BeeZip.exe`, `mediumIL`, `win32App`, `AppListEntry="none"`.
- **The extensions:**
  - `com:SurrogateServer` with the modern root's class, `Path="beezip_shell_<version>.dll"`, `STA`;
  - `desktop4:FileExplorerContextMenus` with `desktop5:ItemType` `*` and `Directory`, and one `desktop5:Verb` each.
- **Write virtualization off:** `desktop6:FileSystemWriteVirtualization` and `desktop6:RegistryWriteVirtualization` are `disabled`.
  - Without them, `BeeZip.exe --job` started from the menu wrote its `%APPDATA%` and `%LOCALAPPDATA%` files into `%LOCALAPPDATA%\Packages\BeeZip_<hash>\LocalCache`. Every `PROC_THREAD_ATTRIBUTE_DESKTOP_APP_POLICY` value left it there.
  - With them, the spike's probe wrote to the real folders and HKCU (§16, item 8). So `config.toml`, partial files and the WebView2 data stay where the CLI and the main app look.
- **One verb, the cascade.** A second verb from the same package didn't appear: Explorer instantiated both and showed one (§16, item 5). PowerToys ships a package per context-menu entry for this reason.
- **`BeeZip.exe` gets no `<msix>` identity element** (§13). The menu doesn't need one, and the app keeps one identity however it is launched.
- **Registering it** (`PackageManager`, from safe Rust; the spike took 145 ms to register and 218–258 ms to remove):
  - **signed `.msix`:** `AddPackageByUriAsync` with `ExternalLocationUri = <installdir>`. The signature must chain to a certificate in `LocalMachine\TrustedPeople` or a trusted root. `CurrentUser\TrustedPeople` fails with `0x800B0109`, despite the 2026-10-03 docs (§16, item 2);
  - **unsigned manifest under Developer Mode:** `RegisterPackageByUriAsync(AppxManifest.xml)` with `ExternalLocationUri` and `DeveloperMode = true`. No admin, no certificate; the package shows `IsDevelopmentMode`;
  - **unsigned `.msix`:** refused for a non-admin user, "an unsigned package cannot include Executable activations" (`0x80073D2B`). It isn't used.
- **Updates:** a newer version with the same identity updates in place. The surrogate releases the DLL seconds after a menu closes, and one removal waited 5.3 s for it, so registration retries once on `ERROR_PACKAGES_IN_USE`.

### 5.3 Which one, where
Only one registration is ever in place, because a packaged verb also appears under "Show more options" (§16, item 3).

| Windows | Package registrable | `shell.install` (`mode: auto`) |
|---|---|---|
| 10 (build < 22000) | – | classic |
| 11 | signed and trusted | modern |
| 11 | unsigned, Developer Mode on, `--dev` given | modern, as a development package |
| 11 | neither | classic ("Show more options" only), with the reason in the output |

- **Explicit modes:** `mode: classic` and `mode: modern` force one.
- **Switching:** installing one mode removes the other.
- **Windows 10** stays classic even where a package could register (packages with external location need 2004, build 19041, or later). The classic menu is its only menu either way, so a package would add a second mechanism, and a signature, for the same result. Not tested here: there's no Windows 10 machine.
- **In M4 the installer has no signed package** (no production certificate until M6). So it gives Windows 11 the classic menu unless `xtask dist --sign-dev` built it (§9). On a Developer Mode machine, `beezip shell install --mode modern --dev` switches an installed BeeZip to the Windows 11 menu (§14).

### 5.4 The settings mirror
`HKCU\Software\BeeZip\Shell`, written by `shell.install` and by `settings.set` whenever `[shell]` changes:

| Value | Type | Meaning |
|---|---|---|
| `App` | REG_SZ | the `BeeZip.exe` that `Invoke` starts |
| `Dll` | REG_SZ | the registered DLL, for `shell.status` and clean-up |
| `Mode` | REG_SZ | `classic` or `modern` |
| `Hidden` | REG_MULTI_SZ | item ids left out |
| `Cascade` | REG_DWORD | classic menu only |
| `Log` | REG_DWORD | §4.2 |

The DLL never parses TOML (PLAN §1).

### 5.5 `shell.status`, `shell.install`, `shell.uninstall`
All three are `Surfaces::NO_MCP`. Their CLI form is `beezip shell status|install|uninstall` (§8). On Linux and macOS they are `UnsupportedOperation`.

- **`shell.status`** (ReadOnly) reports:
  - the Windows build and whether Developer Mode is on;
  - the mode in place;
  - the classic keys, and whether their DLL exists;
  - the package's full name, whether it is a development registration, and its external location;
  - `App`, the hidden items and `cascade`;
  - `problems`: a DLL that is missing, both registrations at once, an `App` that isn't there.
- **`shell.install`** (System) takes:
  - `mode: auto | classic | modern`, default `auto` (§5.3);
  - `dev`;
  - `dll`, `app` and `package` (a `.msix`, or a folder holding `AppxManifest.xml`). Their defaults come from the install layout beside `bin\beezip.exe`.

  It writes the mirror, registers the mode, removes the other one and deletes old DLLs (§5.6). It returns the status, the actions taken and, when `auto` fell back to classic, why.
- **`shell.uninstall`** (System) removes both registrations, the mirror key and old DLLs. It leaves `config.toml` alone.
- **Safe Rust only:**
  - the build number and Developer Mode come from `HKLM` values read through windows-registry (`CurrentBuildNumber`, `AppModelUnlock\AllowDevelopmentWithoutDevLicense`);
  - packages are found by name and publisher through `FindPackagesByUserSecurityIdNamePublisher`, for the current user (an empty SID) and each publisher BeeZip has used, so a development registration and a signed one are both found;
  - deployment operations block on windows-future's `join()`.
- **Tests write elsewhere:** registry writes go through one base key, which tests point at `HKCU\Software\BeeZip-test-<pid>` (§10).

### 5.6 DLL files: upgrades and locks
- **What a loaded DLL allows:** while `explorer.exe` has it loaded (the classic menu), it can't be deleted, but it can be renamed or moved within its volume. Once moved, it is deleted when the process lets go (§16, item 9).
- **Why not PLAN's mechanism:** PLAN's `MoveFileEx(DELAY_UNTIL_REBOOT)` needs admin, and the install is per user.
- **What `shell.install` and `shell.uninstall` do with every `beezip_shell_*.dll`** in the install folder that isn't the registered one:
  1. delete it;
  2. failing that, move it to `%TEMP%\BeeZip-shell-<random>.dll`;
  3. if the move fails too, leave it in place;

  and for any file left behind, add an HKCU `RunOnce` value that deletes it at the next sign-in: `cmd.exe /d /c del /f /q "<path>"`.
- **On uninstall,** the install folder can then be removed even while Explorer holds the old DLL.
- **The Windows 11 menu** doesn't need any of this in practice. The surrogate lets go within seconds.

## 6. Job mode

### 6.1 `shell.plan`
Effect ReadOnly, `Surfaces::NO_MCP`, `beezip shell plan`. Input: a `JobRequest`. Output: `steps`, each one of these:

| Step | From items | Carried out by |
|---|---|---|
| `run { title, command, args }` | extract-here, extract-folder, test, add-* | a job window, in order |
| `open { paths }` | open | the main window, as tabs |
| `extract_dialog { archive }` | extract-to | the main window's extract dialog |
| `create_dialog { inputs }` | compress-to | the main window's create dialog |

- **Volume sets:** archives in the same set become one step. Selecting `a.7z.001` and `a.7z.002`, or `a.part1.rar` and `a.part2.rar`, extracts once. It uses core's volume naming (M3 §3.1).
- **Arguments:**
  - `extract-here` is `{ archive, dest: <its folder>, smart: true }`;
  - `extract-folder` is `{ archive, dest: <folder>\<stem> }`;
  - `add-*` is `{ output: <folder>\<name>.<ext>, inputs }`.

  The overwrite policy is left to config (default `ask`), so an existing output prompts in the job window.
- **Validation:** an unknown item, or a path that isn't absolute, is `InvalidArgs`. A path that has gone is `NotFound` for that step only.
- **Its uses:** the desktop runs it, and so can a script (`beezip run shell.plan --json @job.json`) or a test.

### 6.2 `BeeZip.exe --job <file>`
- **Arguments** are parsed properly. M3's `paths_from_args` skipped every flag, but would have taken the job file for an archive to open.
- **Where the job runs:**
  - **No BeeZip running:** this process becomes the instance. It reads the request (§3.3), runs `shell.plan` through its engine, and sends each step to its window: a job window for the `run` steps, the main window for the others, created only then.
  - **BeeZip already running:** single-instance forwards the arguments, and the running app does the same.
- **Windows exist only when needed:**
  - the main window is created on the first `open` or dialog step, or a plain launch;
  - each request with `run` steps gets one job window, labelled `job-<n>`.
- **Exiting:** the app exits when its last window closes, as Tauri does by default. Closing a window with jobs running asks first, as M3 §5.6 does for the main window.
- **Permissions:** `capabilities/default.json` covers `job-*` windows. tauri-utils 2.10.2 takes globs in a capability's `windows` list.
- **The main window** gains an `open-dialog` event (`{ dialog: "extract" | "create", paths }`) beside `open-paths`.
- **Identity:** from the Windows 11 menu the process carries the package identity (§5.2). PR 4 checks that the job window, single-instance forwarding and the WebView2 data folder behave the same as a plain launch (§12).

### 6.3 The job window
- **Size:** about 460 × 200, resizable, titled by its step ("Extracting a.zip").
- **What it shows:**
  - "2 of 5" when there are several steps;
  - a progress bar with bytes, rate and time left;
  - the current entry;
  - Cancel.
- **Prompts:** passwords and overwrites appear in the window, with M3's prompt components. Each prompt carries its job id, so nothing changes in IPC.
- **When it ends:**
  - **Success:** "Done", with "Open folder" through the opener plugin, which reveals the output. The window closes after 2 seconds when `[jobs] close_when_done` is true (the default) and nothing was skipped or renamed.
  - **Failure:** the error stays. `Unsafe` opens M3's report dialog.
- **Order:** steps run one after another. Requests run side by side, one window each, as the engine allows.
- **Same bundle:** it is one page in the same Vite bundle. `App.tsx` picks the job view from the window label, and the steps arrive in `window.__BEEZIP__.job`, like the startup paths.

## 7. Settings

### 7.1 `settings.get` and `settings.set`
Both are `Surfaces::NO_MCP`: an assistant that could set `[mcp] roots` could widen its own sandbox (§14).

- **`settings.get`** (ReadOnly, `beezip settings get`) returns:
  - the path, and whether the file exists;
  - every setting with its effective value, as one typed object: `Config` gains `Serialize`, `JsonSchema` and `TS`;
  - the warnings, and the error that makes the file unusable, if any.
- **`settings.set`** (Writes, `beezip settings set KEY=VALUE… [--reset KEY]…`) takes:
  - **on the command line,** VALUE as TOML (`19`, `false`, `['C:\a']`), with a bare word read as a string (`extract.overwrite=rename`);
  - **as JSON,** `{ "set": { "extract.overwrite": "rename", "shell.items.test": false }, "reset": ["levels.zstd"] }`.
- **How `set` writes:**
  1. Unknown keys are refused, with the list of known ones (M1 only warned, when loading). `levels.<name>` takes any codec or method name.
  2. The edits go into a `toml_edit::DocumentMut` of the current file, so comments, order and formatting stay.
  3. The whole result is parsed again with `Config::parse`, so a wrong type is `InvalidArgs` with the line, and nothing is written.
  4. The file is written through `Partial` (M3 §3.7): a temporary file, then a rename. A missing file is created with a one-line header.
  5. When `[shell]` changed, the mirror (§5.4) and, for the classic menu, the verbs (§5.1) follow.
- **Output:** the `settings.get` output plus `changed`, the keys whose value changed.
- **`access()`:** `settings.set` declares `Write(<config path>)`.

### 7.2 New sections

```toml
[shell]
cascade = true             # classic menu only: false puts each item at the top level
[shell.items]              # every item is shown unless set to false
test = false
add-tar-zst = false

[jobs]
close_when_done = true     # the job window closes itself after a clean success
```

### 7.3 The engine picks up changes
- **Before:** the engine holds the config as `Arc<Result<Config, CmdError>>`, read once at startup.
- **Now:** it sits behind an `RwLock`.
  - A job takes a snapshot when it starts.
  - `settings.set` replaces it through `JobCtx`, and the engine's policy limits follow `[limits]`.
- **Other processes** (a running `beezip mcp`, a CLI) read the file when they start, as now.

### 7.4 The settings page
- **Opening it:** from the palette, `Ctrl+,`, and the welcome screen.
- **The sections:**
  - **Extracting:** overwrite, links, Mark of the Web;
  - **Creating:** threads, the `beezip compress` codec, and levels, with sliders over the ranges `formats.list` reports;
  - **Limits;**
  - **Jobs;**
  - **MCP:** roots and read-only;
  - **Explorer menu** (PR 3): the status line from `shell.status`, Install, Remove and Repair (each confirmed, since they are System), the mode, the cascade switch (disabled in the Windows 11 mode) and a checkbox per item.
- **Saving:** a change calls `settings.set` at once, debounced for text, and shows any error beside the field.
- **"Open config.toml"** and the path are at the bottom.

## 9. Packaging
**`cargo xtask dist [--debug] [--sign-dev] [--version V]`:**
1. **The CLI and the DLL:** `cargo build -p beezip-cli -p beezip-shell`, into `target/dist-cli` as now.
2. **What gets staged as resources:**
   - `beezip_shell_<V>.dll`;
   - `sparse/AppxManifest.xml`, from the template with the version, the DLL name, the CLSIDs and the publisher (`CN=BeeZip Dev` until M6), and `sparse/StoreLogo.png`;
   - **with `--sign-dev` only,** `beezip-sparse.msix`: `makeappx pack /nv` and `signtool sign /fd SHA256` with the dev certificate, from the newest SDK under `Windows Kits\10\bin`. An unsigned `.msix` is never shipped, since nothing can install it (§5.2).
3. **The hooks** (`target/dist/hooks.nsh`, from `packaging/windows/hooks.nsh`):
   - **`NSIS_HOOK_PREINSTALL`:** M3's #51 (§15). For each association whose default is still BeeZip's, the saved backup goes back into the default before `APP_ASSOCIATE` saves it again.
   - **`NSIS_HOOK_POSTINSTALL`:** PATH as before, then `"$INSTDIR\bin\beezip.exe" shell install`, through `nsExec`, with no window.
   - **`NSIS_HOOK_PREUNINSTALL`:** `shell uninstall` before the files go, then the association and PATH steps as before.
   - **`NSIS_HOOK_POSTUNINSTALL`:** unchanged.
4. **`--version V`** overrides the version, so the upgrade check can build 0.1.0 and 0.1.1 from one tree.

**Upgrades:**
- **Interactive install over an older version:** Tauri's template runs the old uninstaller first (`PageLeaveReinstall`), so the old `beezip.exe` removes the old registration and the new one registers.
- **`/S` and `/UPDATE`:** these install over the top. The new `shell install` re-points the classic keys or updates the package, and clears the old DLL (§5.6).
- **A running BeeZip:** Tauri's `CheckIfAppIsRunning` already stops the installer while `BeeZip.exe` runs, job windows included.

**`cargo xtask shell [--mode classic|modern] [--remove]`** is the development loop:
- it builds the DLL and `beezip-desktop`;
- it copies the DLL to `target/shell/beezip_shell_<n>.dll`, a new name each time, so a rebuild never fights Explorer's lock;
- it writes the manifest to `target/shell/sparse/`, and runs `beezip shell install` with `--dll`, `--app target/debug/beezip-desktop.exe` and, for modern, `--dev`;
- it deletes the copies it can.

**`cargo xtask dev-cert`:**
- **The certificate:** `CN=BeeZip Dev`, for code signing, created in `CurrentUser\My`.
- **Exported** to `target/dev-cert/BeeZip-Dev.cer`.
- **Trusting it** needs an elevated `Import-Certificate -CertStoreLocation Cert:\LocalMachine\TrustedPeople`. The task prints that command and doesn't elevate on its own. It is only needed to try the signed installer path; everyday development uses Developer Mode (§14).

**The menu-dump example** (`cargo run -p beezip-shell --example menu_dump -- [--invoke TITLE] PATH…`) is the spike's harness.
- **What it shows:** it builds the classic context menu for a selection as Explorer's "Show more options" does (`IShellItemArray` → `BHID_SFUIObject` → `IContextMenu`, submenus opened with `WM_INITMENUPOPUP`). It prints the menu.
- **What it covers:** that menu includes packaged verbs, served from `DllHost.exe`. So one tool checks both registrations, on CI as well.

## 14. Decisions (taken while planning, 2026-11-04)
Each could reasonably go the other way. Say which to reverse, and I'll change it.
- **One registration per machine.** Windows 11 gets the package where it registers, and the classic keys otherwise. The alternative registers both and accepts BeeZip appearing twice under "Show more options".
- **The installer registers the Windows 11 menu only from a signed package.** Developer Mode registration is opt-in (`shell install --mode modern --dev`), so an M4 install gives Windows 11 the classic menu until M6's certificate. The alternative falls back to the unsigned registration whenever Developer Mode is on. That would give you the Windows 11 menu from the installer here today, but it makes release behaviour depend on a developer setting.
- **Development uses Developer Mode, not a certificate.** `xtask dev-cert` stays, for the signed path only. The alternative is PLAN's: dev-cert for everything, which needs admin once.
- **Jobs started from the Windows 11 menu keep the package identity,** with write virtualization off (tested). The alternative launches `BeeZip.exe` through Explorer's own `ShellExecute` (`IShellWindows` → `IShellDispatch2`), so it has no identity at all. That route is untested; it stays the fallback if PR 4's checks find a difference.
- **Items are shown or hidden, plus one classic-only `cascade` switch,** as 7-Zip does. PLAN had a per-item "flatten", which Windows 11 can't do (§16, item 5).
- **The menu also covers zip-based documents** (`.jar`, `.docx`, `.epub`…), which the file associations leave to their apps.
- **"Add to "a.zip"" over an existing `a.zip` asks** (Replace, or Keep both as `a (1).zip`). In M5 it can offer to add to it.
- **The installer adds the menu without asking.** Tauri's template has no page for a checkbox; the settings page and `beezip shell uninstall` remove it.
- **`settings.*` are hidden from MCP.** The alternative exposes `settings.get` read-only, and `settings.set` minus `[mcp]` and `[limits]`.
- **Windows 10 uses the classic menu** even where a package could register there.
- **windows 0.62.2,** not windows-core 0.100 with generated bindings (§1).
- **Four PRs** (settings, job mode, classic menu, Windows 11 menu) rather than M3's two. Each can be tried on its own.

## 15. M3's follow-ups
- **#51, the association backup lost on upgrade: folded in (PR 3).**

- **#35, reporting libbz2-rs-sys upstream: folded in as a draft, filed on your word.**
  - **The bug:** 0.2.6 is still the latest (2026-10-29), and upstream has no issue for it.
  - **The report** I'd file at trifectatechfoundation/libbzip2-rs: `decompress.rs`, state `BZ_X_CODING_3`, does `curr -= 1` and `curr += 1` on a `u8`. C's `UChar` wraps there and the range check after it (`curr < 1 || curr > 20`) rejects the data. In Rust with overflow checks (debug builds, cargo-fuzz) it panics instead. The fix is `wrapping_sub`/`wrapping_add`. The repro is `tests/fixtures/regress/fuzz-sevenz-bzip2-overflow.7z` (its BZip2 block, extracted).

6. **Selections:**
   - **Size:** the classic verb showed for 15, 16 and 20 files, with or without `MultiSelectModel`, and `Invoke` got all 20 in one call.
   - **Mixed:** a file and a folder together got both registrations' verbs.
7. **Explorer builds the whole cascade up front.**
   - **What it asks:** the root's `GetState` (with `fOkToBeSlow` true, and in "Show more options" again with it false), its title, its flags, then every subcommand's flags, title and state, one `Next(1)` at a time, before anything is shown.
   - **How long:** about 35 ms from `DllGetClassObject` to the last subcommand, across processes.
8. **Identity and virtualization:**
   - **The setup:** `Invoke` in the surrogate started a probe four ways: plainly, and with `PROC_THREAD_ATTRIBUTE_DESKTOP_APP_POLICY` 1, 2 and 4.
   - **Identity:** all four had the package identity (`GetCurrentPackageFullName`). A child of the classic handler had none.
   - **Writes:** with the sample manifest, the probe's `%APPDATA%` and `%LOCALAPPDATA%` writes landed in `…\Packages\BeeZipSpike_<hash>\LocalCache\{Roaming,Local}`; HKCU writes from its own children were real, except under policy 2.
   - **The fix:** with `desktop6:FileSystemWriteVirtualization` and `RegistryWriteVirtualization` disabled, every write landed in the real folders and HKCU.
9. **Locked DLLs:** a DLL loaded in a process couldn't be deleted, but could be renamed, and moved to `%TEMP%` on the same volume, while loaded. The moved copy couldn't be deleted until the process exited, and then could.
10. **Building the DLL:** link.exe warns `LNK4104: export of symbol 'DllCanUnloadNow' should be PRIVATE` for `#[no_mangle]` exports; a `.def` file fixes it. The spike DLL was 172 KiB in release.
11. **The windows crates:**
    - **What was published:** windows-rs's 2026-09-03 release took windows-core, windows-registry and the small crates to 0.100.0 (MSRV 1.95). It did not publish `windows` or `windows-sys` ("We may initially publish the release without `windows` and `windows-sys`"), so 0.62.2 is still the latest umbrella crate.
    - **What 0.62.2 has:** `IExplorerCommand_Impl`, `AddPackageOptions::SetExternalLocationUri`/`SetAllowUnsigned`, `RegisterPackageOptions::SetDeveloperMode`, and windows-future's blocking `join()`.
12. **No synthetic input.** The first Explorer script pressed keys with `keybd_event` after `SetForegroundWindow` had failed, so they went to the window in front: Windows Terminal, running another Claude Code session. They opened and closed its tab menu; that session carried on. The scripts after it, and §12's checks, only post messages to windows they opened, and use UI Automation.
13. **Tauri's NSIS template (`tauri-cli-v2.12.4`):**
    - **Hook order:** `NSIS_HOOK_PREINSTALL` runs before `APP_ASSOCIATE` (which is what #51's fix relies on), and `NSIS_HOOK_PREUNINSTALL` runs before any file is deleted.
    - **Upgrades:** an interactive upgrade runs the old uninstaller first with `_?=`; `/S` and `/UPDATE` don't.
    - **A running app:** `CheckIfAppIsRunning` covers the main binary in both directions.
