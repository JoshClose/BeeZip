# BeeZip — M12 (Microsoft Store) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M11.md`](M11.md) and keeps their
decisions. Azure Artifact Signing's identity check for Close Consulting, Inc is still pending, so
on 2026-11-14 the user asked what it would take for the Microsoft Store to sign BeeZip. The answer
is in [`STORE.md`](STORE.md): only an MSIX package, which Microsoft re-signs after certification.
An EXE or MSI installer must already carry our own signature. On 2026-11-16 the user chose this
route:
- **the Store gets an MSIX now;**
- **the Artifact-signed NSIS setup comes later**, outside the Store (GitHub, winget).

Partner Center is ready:
- **The company account:** Close Consulting, Inc, verified through its D-U-N-S number.
- **The product:** "BeeZip" is reserved as an MSIX app. Its identity:
  - `Package/Identity/Name`: `CloseConsultingInc.BeeZip`;
  - `Package/Identity/Publisher`: `CN=B81ECA8F-95E1-4C2B-B747-FE4DA97C8BFC`;
  - `PublisherDisplayName`: `Close Consulting, Inc`;
  - package family name `CloseConsultingInc.BeeZip_x5m1y1n6e4ce4`; Store ID `9P9HHSVMM3M3`.

Spikes on 2026-11-16 back the plan. The details are in `STORE.md` ("Spike results"), and the
scripts in `target/m12-spikes/`. Each used a full package built from the 0.6.0 debug build:
- **On this machine:** registered unpacked under Developer Mode.
- **On the BeeZip-Win10 VM:** packed, signed with a throwaway certificate and installed into
  `WindowsApps`, like a Store install. It ran beside an NSIS install.
- **The certification kit:** run by the user on this machine.

These findings shape the plan:
- **Nothing blocks the route.** The package's own manifest declares everything the NSIS hooks
  write today:
  - the Explorer menu: the existing DLL as a COM surrogate, with its modern root;
  - the file associations;
  - the command line: an alias `beezip.exe`, which works from any terminal with console output,
    pipes and exit codes. `beezip mcp` works through it too.

  Every way of starting BeeZip gives the package identity: Start, a file association, the menu,
  the alias.
- **Windows 10 shows the package's menu.** On 22H2 the classic menu has the whole "BeeZip >"
  cascade for files and folders from the package alone, and "Extract here" works. The Store build
  needs no registry verbs.
- **The certification kit passes: no required test fails.**
  - Two optional tests fail:
    - one app per package: Python's Store package has up to four apps;
    - S mode's "blocked executables";
  - **one required test warns:** `BeeZip.exe` doesn't declare DPI awareness in its manifest.
- **Virtualization, left at its default, is mostly harmless.**
  - **Not redirected:** `%TEMP%` (jobs, `entry.open`, drag-out, the DLL's log), and writes into
    folders that already exist in AppData, including new subfolders. An extraction into
    `%LOCALAPPDATA%\Programs\Tool` lands where other programs see it.
  - **Redirected:** only a brand-new folder directly under `AppData\Local` or `Roaming`, into
    the package's `LocalCache`, which is deleted on uninstall. That covers `%APPDATA%\BeeZip`
    on a machine that never had BeeZip, and WebView2's data. HKCU writes go to the package's
    private hive too.
  - **Turning redirection off isn't an option.** It needs the restricted capability
    `unvirtualizedResources`, which Microsoft says "is designed for certain types of desktop PC
    games … not intended to be used for other scenarios". The spike's variant B with it put
    everything where other programs see it.
- **Four things in BeeZip behave wrongly inside the package** (§3):
  - **Settings > Explorer menu** offers an Install, which would write keys Explorer never reads;
  - **the updater runs**: it checked GitHub on its first start;
  - **"Copy as CLI"** names `bin\beezip.exe` under `WindowsApps`;
  - **"Open config.toml" and "Show in folder"** pass other programs a path that only exists
    inside the package, when the settings file was redirected.
- **Two more problems found while reading the code:**
  - **The menu's item settings do nothing** on a Store-only machine: `shell::follow` writes them
    only when the menu's registry key already exists, and the package never creates it;
  - **with NSIS installed too, the Store package's menu starts NSIS's `BeeZip.exe`.** The DLL
    prefers the `App` value NSIS writes to the real HKCU (`invoke.rs`), and the package sees the
    real HKCU too.
- **Both installs on one machine give two of everything:**
  - two identical "BeeZip >" cascades;
  - two "Open with" entries;
  - `beezip` resolves to the Store's alias, which comes first on PATH;
  - the Store copy's `shell status` reports NSIS's menu as its own.

Nothing was built into the repo, committed or pushed while planning. The spike scripts stay in
`target/m12-spikes/`, and the VM is back at its saved state. The user approved every
recommendation in §11 on 2026-11-16.

## Scope

- **A Store package of BeeZip:** `BeeZip_<V>_x64.msix`, built by every Windows `cargo xtask
  dist` from the same programs as the installer and the portable zip (§2). It is unsigned:
  Microsoft signs it.
- **The release workflow keeps it as a workflow artifact,** not a release asset, for the user to
  upload to Partner Center (§5). Nothing can install an unsigned `.msix` from GitHub.
- **A "running as the Store package" mode** in the app, the CLI and the menu DLL, which fixes §3's
  problems.
- **A note when both installs are on one machine** (§4, decision 4).
- **The DPI warning fixed for every Windows build:** an app manifest declaring
  `PerMonitorV2` (§3.6).
- **The listing's text** (§5): description, certification notes, the `runFullTrust`
  justification. Also a privacy page on the site, and screenshots.
- **Unchanged:** the NSIS setup and its hooks, the portable zip, the updater outside the Store,
  Linux and macOS.

## 1. Dependencies

- **No new crates.** `windows` gains the `Win32_Storage_Packaging_Appx` feature, for
  `GetCurrentPackageFamilyName`. The `beezip-commands` crate already uses `PackageManager` for
  the sparse package (`shell/package.rs`). The menu DLL already depends on `windows`.
- **One more Windows SDK tool:** `makepri.exe`, for the logos' `resources.pri` (§2.2), beside the
  `makeappx.exe` that `sparse.rs` finds already. Both are on this machine and on CI's
  `windows-latest`.
- **The package's identity is fixed** (decision 5): name, publisher and family become constants
  in `beezip-commands` (`shell::store`), beside `PUBLISHERS`. The DLL has its own copy of the
  family name, checked equal by a test.

## 2. The package

### 2.1 The manifest

The template is `packaging/windows/store/AppxManifest.xml`, beside the sparse one, filled in by
`xtask` (`{{VERSION}}`, `{{DLL}}`, `{{ASSOCIATIONS}}`). It is the spike's variant A, with the real
identity:

- **Identity:** `CloseConsultingInc.BeeZip`, `CN=B81ECA8F-95E1-4C2B-B747-FE4DA97C8BFC`, x64,
  and version `X.Y.Z.0`. The Store requires the revision to be 0; `sparse.rs`'s
  `package_version` already gives that form. It drops a pre-release's suffix, which in the Store
  would collide with the release, so no Store package is built for a pre-release.
- **Properties:** display name `BeeZip`, publisher display name `Close Consulting, Inc`, the logo.
  No virtualization settings (decision 1).
- **Dependencies:** `Windows.Desktop`, `MinVersion` 10.0.19041.0 (Windows 10 2004, decision 9),
  `MaxVersionTested` 10.0.26100.0.
- **Capabilities:** `runFullTrust` only.
- **Application `BeeZip`** (`BeeZip.exe`, full trust):
  - **file associations:** one `uap:FileTypeAssociation` per extension, the 56 the installer
    associates. They come from `formats.list` through `dist::associations`, as the installer's
    do, and the spike generated them the same way. Windows makes none of them the default; the
    user picks BeeZip (§3.2).
  - **the menu:** `windows.comServer`, a `SurrogateServer` with the DLL
    (`beezip_shell_<V>.dll`, `ThreadingModel="STA"`) under a new **Store root** CLSID
    (`beezip_menu::clsid::STORE_ROOT`), served exactly as the modern root is. With it,
    `desktop4:FileExplorerContextMenus` for `*` and `Directory`.
  - **why a new CLSID:**
    - the spike used the modern root, which the sparse package declares too. Once NSIS is
      signed, its Windows 11 menu is that package, and two packages declaring one class is a
      collision no one has tried;
    - the classic root, which NSIS registers in HKCU, is a different CLSID already;
    - the DLL also learns from the CLSID that it is serving the Store package (§3.2).
- **Application `Cli`** (`bin\beezip.exe`, `AppListEntry="none"`): the alias `beezip.exe` with
  `desktop4:Subsystem="console"`. The console alias needs `SupportsMultipleInstances="true"`
  (makeappx error 80080204 without it). Two applications are decision 2. The app itself gets no
  alias. **Replaced in 0.7.2:** Partner Center refuses the hidden application, so the alias is
  the app's own, starting `bin\beezip.exe`, and there's no `Cli` application (§14.1).

### 2.2 Logos

The spike's single `Square44x44Logo.png`, `Square150x150Logo.png` and `StoreLogo.png` pass
certification, but Windows scales them and puts the taskbar icon on a coloured plate. Decision 6
recommends Windows' own sizes:
- **`Square44x44Logo`:** `targetsize-16, 24, 32, 48, 256`, each also `altform-unplated`, and
  scale-100 and 200;
- **`Square150x150Logo` and `StoreLogo`:** scale-100 and 200.

`xtask icons` already makes every icon from the logo (`brand-logo`, riff 108). It also writes
these, into `packaging/windows/store/Assets/`. They are committed like the other icons, and
`--check` covers them. `xtask` makes `resources.pri` with `makepri createconfig` and `makepri
new`; without it, Windows finds only the unqualified names. The spike didn't try the unplated
icons, so PR 1 checks the taskbar on the VM.

### 2.3 Building it

On Windows, `cargo xtask dist` gains a step 5:
1. **Lay out `bundle/store/layout/`:** the portable copy's tree (`BeeZip.exe`, `bin\beezip.exe`,
   the DLL, `LICENSE-*`, `THIRD_PARTY_NOTICES.md`, `README.txt`), plus `Assets\`, the manifest
   and `resources.pri`.
2. **Pack `bundle/store/BeeZip_<V>_x64.msix`** with `makeappx pack`, which validates the manifest.
   It is never signed (decision 3), whatever `BEEZIP_SIGN` or `--sign-dev` says, so a test
   certificate can't end up in a Store upload. The programs inside are signed when the
   installer's are.
3. **The layout stays beside it.** `Add-AppxPackage -Register bundle\store\layout\AppxManifest.xml`
   installs it under Developer Mode, with the real identity, for local checks.

`--debug` builds it too (`bundle/store` under `target/dist/debug`), so CI's debug dist exercises
it. With no Windows SDK, `dist` fails and names the missing tool, as it does for signing today.

## 3. Running as the Store package

### 3.1 Knowing it

- **The check:** `GetCurrentPackageFamilyName` succeeds and returns
  `CloseConsultingInc.BeeZip_x5m1y1n6e4ce4`.
- **Who asks:** `shell::store::running()` in `beezip-commands` (CLI and app), and the DLL's own
  copy in `beezip-shell`.
- **Other packages don't count:** the sparse package and the spike's give an identity under
  other families.
- **Tests:** debug builds take `BEEZIP_STORE=1` to act as the Store copy without a package, as
  `BEEZIP_SHELL_BASE` does for the menu, so unit and page tests reach every branch.

### 3.2 Explorer's menu

- **The DLL:** created as the Store root, or running in the Store package, it starts the
  `BeeZip.exe` beside it and ignores `App` (`invoke.rs`). This fixes the VM's NSIS-beside-Store
  case, where the package would have started NSIS's copy.
- **`shell.status`:**
  - a new `ShellMode::Store`, with the package's full name and install folder, and the hidden
    items;
  - no classic keys or sparse package of its own. What NSIS registered is reported as another
    install (§4), not as this copy's menu.
- **`shell.install` and `shell.uninstall`** refuse with `UnsupportedOperation`: "The Microsoft
  Store package provides Explorer's menu. To remove it, uninstall BeeZip." The CLI and the page
  show that message.
- **`settings.set` of `[shell]`:** in the Store copy, `follow` always writes the mirror's
  `Hidden`, creating the key, which lands in the package's private hive. The DLL reads that hive,
  as the spike showed. `cascade` doesn't apply, since the package's menu is always a cascade, so
  Settings leaves it out.
- **Settings > Explorer menu:**
  - says "Provided by the Microsoft Store package", with the item checkboxes;
  - no Install, Remove, repair or cascade;
  - a **"Default apps"** button opens Windows' page for BeeZip, where the user makes it the
    default for archives: `ms-settings:defaultapps?registeredAUMID=<family>!BeeZip` on Windows 11,
    and `ms-settings:defaultapps` on Windows 10. Where Windows ignores the parameter, PR 2 opens
    the plain page instead. The page is opened, never written, since Windows protects those
    choices.

### 3.3 Updates

- **The Store copy never checks or installs:**
  - `cmd_update_check` answers `Checked::Off` with "The Microsoft Store keeps this copy of
    BeeZip up to date.";
  - `cmd_update_install` refuses;
  - About shows that sentence in place of "Check for updates", and Settings hides `[updates]
    check`.
- **`portable()` is false in the package.** Only the updater asks it today.
- **Same binaries, run-time switch** (decision 7): the Store package holds the same programs as
  the installer. When Artifact Signing works, the signed programs go into both.

### 3.4 Copy as CLI and MCP

- **`cli_program`** (`open.rs`) returns `beezip` in the Store copy, when the alias folder
  `%LOCALAPPDATA%\Microsoft\WindowsApps` is on PATH, as it is by default. Otherwise it returns
  the alias's full path, never `bin\beezip.exe` under `WindowsApps`.
- **MCP:** `beezip mcp` through the alias. The README's and `docs/MCP.md`'s client examples gain
  a Store line: `"command": "beezip"`.

### 3.5 config.toml's path

`settings.get` reports the path other programs can open. In the Store copy, a path under
`%APPDATA%` or `%LOCALAPPDATA%` becomes
`%LOCALAPPDATA%\Packages\<family>\LocalCache\{Roaming,Local}\…` when the file is there. That is
the case on a machine that never had BeeZip. It is the real path the package's own reads go to,
and other programs can read it. "Open config.toml" and "Show in folder" use it. Where an older
BeeZip left `%APPDATA%\BeeZip`, nothing is redirected and the path stays as it is. Settings says
that a Store-only copy's settings go when it is uninstalled.

### 3.6 DPI awareness

`build.rs` gives tauri-build its own app manifest
(`WindowsAttributes::app_manifest`) for every Windows build. It keeps tauri's Common Controls 6
dependency and adds `<dpiAwareness>PerMonitorV2</dpiAwareness>`. tao sets the same awareness at
run time today, so nothing visible changes. The certification kit's "not DPI aware" warning goes
for the Store copy, and for the installer and the portable zip too.

## 4. Both installs on one machine

Some people will have the NSIS copy and later install the Store copy, or the other way round.
Neither notices the other today. Recommended (decision 4): **each says so, and nothing is hidden**.
- **`shell.status` gains `others`,** what the other copy installed:
  - **from the Store copy:** NSIS's uninstall key in HKCU and its menu (the classic keys, or
    the sparse package), read through the package's view of the real HKCU and `PackageManager`;
  - **from the NSIS or portable copy:** the Store package, by `PackageManager` with §1's name and
    publisher.
- **Settings > Explorer menu** then says: "BeeZip from the Microsoft Store is also installed, so
  Explorer shows two BeeZip menus. Uninstall one of them." The Store copy names the installer
  instead. `beezip shell status` prints the same line.
- **Nothing else changes.** The two menus stay, served by different DLLs. The `beezip` the
  terminal finds is the Store's, and the README says so.

## 5. Releasing

- **The release workflow** (`release.yml`): the Windows job already runs `cargo xtask dist`. It
  uploads `bundle/store/*.msix` as a second artifact, `windows-store`, kept 14 days, not as a
  release asset. A step checks the package:
  - its manifest's identity and version;
  - that every program in it is one the portable zip holds, with the same bytes.
- **CI** (`ci.yml`): the Windows job's debug dist builds the package. A step registers the layout
  under Developer Mode and runs `beezip --version` and `beezip shell status` through the alias,
  expecting `store`. GitHub's runners are administrators, so the step can turn Developer Mode on.
  If the alias doesn't resolve outside a desktop session (the VM's PowerShell Direct couldn't see
  winget's), the step runs the CLI by `Invoke-CommandInDesktopPackage` instead.
- **Each release, by hand** (decision 3):
  1. The user downloads `windows-store` from the release run.
  2. In Partner Center they start a submission and upload it.
  3. They submit, and certification takes up to three business days.

  The release runbook artifact gains this as a step. The first submission also needs the listing.
- **The listing** (I draft it in `packaging/store/listing.md`; the user enters it):
  - **description and features:** from the README;
  - **screenshots:** four at 1920×1080, from a release build over WebView2's DevTools protocol, as
    in earlier manual checks (decision 8);
  - **category:** Utilities & tools;
  - **support:** GitHub issues; the site as the website;
  - **the privacy policy:** a new `site/src/privacy.html`. BeeZip collects nothing. The installer
    and portable copies ask GitHub for updates once a day unless that's turned off. The Store
    copy makes no network requests;
  - **certification notes:** what BeeZip is, how to try it (open a `.zip`, the Explorer menu,
    the `beezip` alias), and the `runFullTrust` justification. It is a desktop archive manager
    that reads and writes files wherever the user chooses, and adds File Explorer commands through
    its COM server;
  - **pricing:** free;
  - **age rating:** the questionnaire, which the user answers.
- **The site's download page and the README** gain a Microsoft Store section once the listing is
  live, with the Store's own badge and link
  (`https://apps.microsoft.com/detail/9P9HHSVMM3M3`). Until then the section says it's coming.
  It goes in the PR after the listing goes live, a small one.

## 10. Not in M12

- **The Artifact-signed NSIS setup** (STORE.md's other route): it waits on Microsoft's identity
  check and is a separate milestone.
- **Automated Store submissions** (decision 3's alternative): the Partner Center submission API or
  the `msstore` CLI, which need an Entra ID app tied to the account.
- **An ARM64 package or a bundle:** BeeZip builds only x64 today.
- **Sideloading the `.msix` outside the Store:** nothing could install it without our own
  certificate.
- **Hiding one copy's menu when both are installed** (decision 4's alternative), and **both
  installs on Windows 11.** The VM is Windows 10; by inference, Windows 11 shows both menus too.
- **Windows 10 without WebView2.** The Store copy can't install it, as NSIS does. Windows 11 has
  it, and nearly every Windows 10 has it through Windows Update and Edge. BeeZip's message when
  it's missing is checked on the VM in PR 2, if WebView2 can be removed there.
- **S mode:** the "blocked executables" test is informational, and BeeZip starts its own programs
  and the user's default apps.

## 11. Decisions

For the user's approval. Each is a recommendation, followed by its alternative.

1. **Default virtualization** (variant A): no `unvirtualizedResources`. A Store-only copy keeps
   its settings in the package's `LocalCache`, which goes on uninstall. Its Open config.toml uses
   the real path (§3.5). An extraction into a brand-new folder directly under `AppData\Local` or
   `Roaming` lands there too, which is rare. *Alternative:* variant B (`unvirtualizedResources`
   with both virtualizations disabled). It behaves exactly as NSIS does, but Microsoft says the
   capability isn't meant for apps like BeeZip, so certification would probably refuse it.
2. **Two applications in one package:** the app, and the CLI with the console alias `beezip.exe`.
   The kit's optional "one app" test fails, but the Store accepts packages like Python's.
   **Refused by Partner Center:** a hidden application needs Microsoft's waiver, so 0.7.1's
   package has the app alone (§14). 0.7.2 gives the alias to the app itself, with no second
   application (§14.1).
   *Alternative:* the app alone, with no `beezip` command in a Store install.
3. **Built by every Windows `xtask dist`,** kept as the release run's artifact, and uploaded by
   the user in Partner Center. *Alternative:* automated submission through the Partner Center API,
   which needs an Entra ID app registration and a secret in GitHub; it could come later.
4. **Both installs on one machine: each copy says the other is there** (§4), and nothing is hidden.
   *Alternatives:* leave it unnoticed; or have the NSIS copy's menu hide itself while the Store
   package is installed. That needs a `PackageManager` lookup in Explorer's process or the
   installer, and both copies' menus have to agree.
5. **The identity as constants in the code,** since it never changes for this product.
   *Alternative:* `xtask dist` reads it from environment variables, as signing's settings are.
6. **Windows' own logo sizes** (target sizes, unplated, scales) **with `resources.pri`** (§2.2).
   *Alternative:* the spike's single files, which pass certification but look soft and sit on a
   plate in the taskbar.
7. **The updater switched off at run time,** with the same programs in the Store package as in the
   installer. *Alternative:* a Store build without the updater compiled in: separate binaries,
   and the "powershell" string the S-mode test flags would go.
8. **The listing drafted here and screenshots made over CDP** from a release build; a privacy page
   on the site. *Alternative:* the user writes the listing and takes the screenshots; no privacy
   page (Partner Center requires one only for apps that handle personal data).
9. **`MinVersion` 10.0.19041.0** (Windows 10 2004), the oldest supported family, checked on 22H2.
   *Alternative:* 10.0.17763.0 (1809), which the manifest's features allow but nothing checked.
10. **Two PRs** (§7), **each committed, pushed and merged when green without asking,** stopping
    before the release, as for M8–M11. *Alternative:* stop for the user's word before each merge.
11. **Ship in 0.7.0,** the first Store version. *Alternative:* a 0.6.1 with only the package, and
    the Store mode after. That's not recommended: without §3 the Store copy offers a broken
    menu install and runs the updater.

### 14.1 The command line back, as the app's own alias (0.7.2)

> 0.7.2 was never released on its own: 0.8.0 (M13) shipped first and carries this change.
> Where this section says 0.7.2, the version people get it in is 0.8.0.

An execution alias can start a different program from its application's: the `uap5:Extension`
takes its own `Executable` and `EntryPoint`. Windows Terminal's package gives its app the alias
`wt.exe` that way, and projects refused for a hidden app the same way have shipped with it. So
the package keeps one application, the visible BeeZip, and its extensions gain the console alias:

```xml
<uap5:Extension Category="windows.appExecutionAlias" Executable="bin\beezip.exe" EntryPoint="Windows.FullTrustApplication">
  <uap5:AppExecutionAlias desktop4:Subsystem="console">
    <uap5:ExecutionAlias Alias="beezip.exe" />
  </uap5:AppExecutionAlias>
</uap5:Extension>
```

The application gets `desktop4:SupportsMultipleInstances="true"`, which a console alias needs.
There's no `AppListEntry` anywhere, so nothing is headless.

**Spike (2026-11-16 and 17, on the host, `target/m12-spikes/alias/`):** 0.7.1's debug Store
layout with `bin\beezip.exe` added and the alias above, registered under Developer Mode:
- makeappx packs it, and the package has one application;
- through the alias, `beezip version` prints, `--output json` goes through a pipe, an error exits
  3, `shell status` shows the package's identity, and `beezip mcp` lists its 16 tools;
- a console break through the alias exits 130 and removes the partial file, as the program run
  by its path does;
- started from Start twice, the app stays one process: `SupportsMultipleInstances` lets Windows
  start a second `BeeZip.exe`, which hands its request to the first as it always has;
- the certification kit's overall result is **PASS**. "Application count" passes now, DPI
  awareness passes (§13), and only the optional "Blocked executables" fails, as before
  (docs/STORE.md).

**What 0.7.2 changes:** PR #59's merge reverted, then:
- **the manifest:** the alias on the BeeZip application, as above, with no `Cli` application;
  `store.rs`'s test checks for one application and no `AppListEntry`;
- **`store-package.ps1`:** the package holds `bin\beezip.exe` again, has one application whose
  alias starts it, and, registered in CI, runs `beezip --version` and `beezip shell status`
  through the alias, as the package;
- **the app:** Copy as CLI and Settings' MCP server section are back in the Store copy, and
  Copy as CLI names the alias (§3.4);
- **the docs:** the listing draft's command-line text, the README, `docs/MCP.md`, the site's MCP
  page and docs/STORE.md.

Partner Center only says whether it takes the package at upload, so 0.7.2 is the check. If it
refuses this layout too, reverting this PR's merge gives 0.7.1's package back.
