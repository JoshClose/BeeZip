# BeeZip — M9 (CHM) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M8.md`](M8.md) and keeps their
decisions. After 0.3.0 the user asked whether a CHM file could be read without 7-Zip
(2026-11-11). M8 left CHM with 7-Zip, along with NSIS, CramFS and MSI patches (M8 §8). CHM is the
nearest of these to what BeeZip already has. Its compression is the LZX that BeeZip's own
decoder reads for cabinets, WIM and WOF (`format/lzx.rs`), and its container is a small
directory.

A spike on this machine backs the plan (`target/m9-spikes/chm/`, with a `REPORT.md`; §14 sums it
up). It used every CHM on this machine (80 unique files, from Microsoft's HTML Help compiler,
Halibut, chmcmd and 7-Zip's help) and a 125 MB one that chmcmd built from Rust's `std` docs. A
prototype reader on a copy of `lzx.rs` with three measurement hooks was:
- checked against 7-Zip 26.00, byte for byte, file by file;
- fuzzed for 4 × 15 minutes with an allocation cap and a hang watchdog;
- timed against 7-Zip and BeeZip 0.2.0 (which reads CHM through 7-Zip, as 0.3.0 does).

These findings shape the plan:
- **BeeZip's LZX decoder reads CHM as it is.** Every file of the 81 samples (28,126 files) came
  out identical to 7-Zip's. The reset table gives each 32 KiB frame's first byte exactly. So each
  frame decodes from its own slice, one per call as a cabinet's data blocks do, with `reset()`
  at each reset point.
- **The last frame is always encoded whole.** Decoding it whole and cutting the output to the
  stated length works on all 81 files. Decoding only the bytes left fails on 6: an LZX match
  runs past the true end. They include an Office help file, StarCraft's, and every chmcmd file,
  among them BeeZip's own fixture (§3.3).
- **chmcmd 3.2.2's directory names the wrong first chunk.** In its multi-chunk file it says
  chunk 1, though chunk 0 also lists entries. 7-Zip reads every chunk, so BeeZip does too
  (§3.1); trusting the header loses 98 of 2,584 files.
- **Decoding runs at about 7-Zip's speed** on one thread (1.5 GB/s of HTML out). Extraction is
  then about creating files, where BeeZip's path through 7-Zip is slowest today (2.3 s and 5.8 s
  on the two largest samples, against 1.6 s and 2.3 s for `7z x`).
- **No crate.** libchm 0.3.1, the one pure-Rust library, opens files by path only and reads
  whole entries into memory. Its LZX code uses chmlib's (LGPL) names throughout, with no
  attribution. Auto mode also refused to build it here, so it wasn't run (§14).
- **`.chm` must not become BeeZip's.** `xtask dist` associates every Explorer-menu format that
  needs no backend (M8 decision 6). Without a change, installing BeeZip would take CHM files away
  from Windows' help viewer (§7).
- **Fuzzing found nothing.** 1.6 million mutated files gave no panics, no hangs and no large
  allocations; the heap peaked at 8 MiB.
- **A stale string, found on the way:** Settings' 7-Zip section still says WIM images and virtual
  disks open through 7-Zip, which hasn't been so since 0.3.0 (§7).

Nothing was built, committed or pushed while planning. The plan was approved on 2026-11-11
(§13), and PR `m9-chm` carries it (§9).

## Scope

- **CHM read by BeeZip** (§3–§5): list, test, extract, preview and `entry.read`, and Info, on
  every platform. CHM files using something BeeZip doesn't support go to 7-Zip, as in M7 and M8
  (§5.3).
- **Unchanged:** the format's name on the wire (`chm`), detection (`backend/sniff.rs`), the
  commands, and Explorer's menu on `.chm`. `formats.list` reports CHM with no backend.
- **Not associated:** `.chm` stays with Windows' help viewer (§7, decision 6).
- **Still through 7-Zip:** NSIS installers, CramFS, and MSI patches, transforms and merge modules
  (§6).

## 1. Dependencies

No new crates; `format/lzx.rs` is used unchanged.

Rejected, with the reasons in §14:
- **libchm 0.3.1** (MIT, published 2026-11-02): it opens by path only, so it can't read through
  BeeZip's `Source`; it reads whole entries into memory; its LZX code has unclear provenance;
  and it wasn't run here.
- **rustchm 0.1.2:** a command-line program, with no library.
- **chmlib 1.0.0 and chmlib-sys:** bindings to the C library (LGPL).

## 2. How it fits

- **Routing.** `External::native()` gains `Chm`, and `source.rs`'s `native()` opens it with
  `chm::open`. As in M7 and M8, `UnsupportedOperation` (never `Corrupt` or `NotFound`) goes to
  7-Zip when it's installed, with a note in Info. Without 7-Zip it fails with 7-Zip's
  `BackendUnavailable`, saying what BeeZip couldn't read.
- **CHM is its own `ArchiveReader`** (`format/chm.rs`), as MSI and WIM are. It reads through
  `Source` like the other readers, and decodes with `Lzx::new`, `reset` and `decode_frame`.
- **Detection doesn't change.** `ITSF` at offset 0 is already CHM (M6 §3.2).
- **`checks_data` stays false.** CHM stores no checksums, so `archive.test` means "decodes", as
  it does through 7-Zip, and says so (M6 §3.5).
- **Size:** the prototype's reading code is about 350 lines. With the `ArchiveReader`, Info,
  limits and errors, `format/chm.rs` should be about 900 lines, plus its tests.

## 3. The format, as the spike found it

### 3.1 The container

- **ITSF header:** version 3 (all 81) or 2. Its section table gives the directory's offset and
  length; the content offset is at 0x58 in version 3, and right after the directory in version 2.
  Offsets are read as given. 7-Zip's own help file keeps its directory at the end of the file,
  with content offset 0, so section 0 overlaps the header.
- **ITSP directory header:** the chunk size (4 KiB in 80 files, 8 KiB in one), the chunk count,
  the index depth and root, and the first and last listing (PMGL) chunk.
- **PMGL chunks:** entries from offset 0x14 up to the chunk's size less its free space (the
  field at offset 4). Each entry is an ENCINT name length, the UTF-8 name, and ENCINTs for
  section, offset and length. An ENCINT is big-endian 7-bit groups, with the top bit set on all
  but the last.
- **Every chunk is read, in order, and every PMGL chunk is taken** (decision 3). The header's
  first and last fields aren't trusted, since chmcmd 3.2.2 gets the first wrong (§14). The
  index (PMGI) chunks aren't needed for a full listing, and are skipped.

### 3.2 The sections

- **`::DataSpace/NameList`** names section 0, `Uncompressed`, and section 1, `MSCompressed`.
- **Section 0** is plain bytes, at the content offset plus the entry's offset.
- **Section 1** is described by three section-0 streams under
  `::DataSpace/Storage/MSCompressed/`:
  - `ControlData`: `LZXC`, its version, and the reset interval and window size, in 32 KiB units
    in version 2 and in bytes in version 1. All 81 files are version 2, with a 64 KiB window and
    reset interval except 7-Zip's help (128 KiB each).
  - `Transform/{7FC28940-9D31-11D0-9B27-00A0C91E9C7C}/InstanceData/ResetTable`: version 2,
    8-byte entries, a 0x28-byte header, the uncompressed and compressed lengths, then one entry
    per 32 KiB frame, giving its first byte in `Content`.
  - `Content`: the LZX stream.

### 3.3 Decoding section 1

- `Lzx::new(window bits)`, 15 to 21.
- Frame *i* decodes from `Content[entry[i]..entry[i + 1]]` (the last up to the compressed
  length), with `reset()` before every frame that starts a reset interval. In all 81 files this
  gives the same bytes as one bitstream per interval realigned after each frame, the way
  libmspack reads it, and the realigned frame ends land exactly on the next entries.
- **Every frame decodes whole, the last too, and the output is cut to the uncompressed length**
  (decision 2). Decoding only the bytes left fails on 6 of 81. Decoding on to the next reset
  interval, as if the data were padded to it, fails on 27.
- The E8 header is read at each reset point, as the decoder does for a cabinet. It was never on
  in the 81 files.
- An LZX block still unfinished at a reset point is dropped by `reset()`. None of the 81 files
  has one.

## 4. Reading

### 4.1 The listing

As 7-Zip lists it today (decision 4), so nothing changes for someone who had 7-Zip:
- paths without the leading `/`, with names ending in `/` as folders, and the root not listed;
- the help file's own files listed (`#SYSTEM`, `#TOPICS`, `$OBJINST`,
  `$WWKeywordLinks/Property`…), as 7-Zip lists them;
- the `::DataSpace/…` streams not listed (7-Zip shows them only for a file it can't read);
- method `LZX:<window bits>` for section 1 and `Copy` for section 0, as 7-Zip names them;
- sizes from the directory, and no times: CHM stores none for its files;
- a name that isn't UTF-8 read lossily (none of the 81 has one); collisions, reserved names and
  unsafe paths handled by `SafeFs`, as for every format.

### 4.2 Extraction

- **One pass, in data order:** section 0's files by offset, then section 1's by offset. Frames
  decode in order into one reused 32 KiB buffer, and each file's bytes are written as they come
  out.
- **Selected files only:** decoding starts at the reset point at or before the next selected
  file, so whole reset intervals with nothing selected are skipped.
- **Memory:** the decoder's window ring (twice the window plus 512 bytes: 128 KiB for the usual
  64 KiB window, at most 4 MiB) and one frame.
- **No shared data:** no two files in the 81 share or overlap bytes, so there's nothing like
  CAB's `same_as`.
- **One thread.** Decoding runs at about 1.5 GB/s (§14). Reset intervals are independent if
  that's ever not enough.

### 4.3 One entry

Preview, `entry.read` and `open_entry` decode from the reset point at or before the entry's
offset, then stream. That's at most one reset interval (64 KiB in 80 of the 81 files) of extra
work.

### 4.4 Test and Info

- **Test** reads every file through a `TestSink` in one pass (the default `test`). A frame that
  fails is `Corrupt`, naming the files it holds. The output says a CHM has no checksums to check.
- **Info:** the format, the title, default topic and language from `#SYSTEM` when it has them,
  the compiler `#SYSTEM` names, the LZX window and reset interval, and the sizes.

## 5. Limits and damage

### 5.1 Checked when it opens

- The header and directory within the file; a chunk size of 0x20 bytes to 1 MiB (§15), and the
  chunks within the directory's length.
- Entries within their chunk's used part, and ENCINTs of at most 9 bytes.
- A window of 15 to 21 bits, and a reset interval that's a non-zero multiple of 32 KiB.
- A reset table with an entry for every frame of the uncompressed length, entries that never go
  backwards and stay within `Content`, and a compressed length within `Content`.
- The existing ratio limit, applied to section 1's uncompressed length against `Content`'s
  size, as it's applied to a cabinet folder's.

### 5.2 Damage

`Corrupt`, and never handed to 7-Zip (decision 5):
- **A file cut after its directory** still lists whole. Every file whose frames are present
  extracts, and the rest fail as cut short; `archive.test` names them. Cut in half, english.chm
  gives 122 of 298 files whole and big.chm 1,493 of 2,584. 7-Zip writes all of them, the cut
  ones partly, and reports errors.
- **A file cut before its directory's end** can't be listed: "the directory is cut short".
  7-Zip lists such a file's raw names in a low-level mode, but can't decode its files either.
- **An entry pointing past its section's data** is listed, and fails when it's read.

### 5.3 What goes to 7-Zip

`UnsupportedOperation`, for 7-Zip when it's installed:
- an ITSF version other than 2 or 3;
- a section other than `Uncompressed` and `MSCompressed`, or a transform other than LZX;
- `LZXC` other than version 1 or 2;
- a reset table other than version 2 with 8-byte entries.

None of the 81 files has any of these.

## 8. Tests

- **Fixtures,** under `tests/fixtures/thirdparty/chm/`, small, made by a `make-chm.sh` in
  `make-7z.sh`'s container, with `expected.json` from 7-Zip 26.00:

    frame that has to be decoded whole. The existing `7zip/chmcmd.chm` stays as it is, and its

  - Halibut, PuTTY's documentation tool (MIT), whose own LZX encoder is a second, independent
    one. That needs Ubuntu 24.04's `halibut` package to write CHMs, which is checked when the
    script is written; without it, this fixture is dropped.
  - Crafted by the script from those: ITSF version 2 (content after the directory); the
    directory at the end with content offset 0 (7-Zip's help file's layout); `LZXC` version 1

- **Malicious corpus** (`xtask gen-fixtures`):
  - names with `..`, a drive, `:` (an alternate stream) and reserved names;
  - a reset table entry past `Content`, and one going backwards;
  - an uncompressed length of 2^63, and a 1 KB file claiming a terabyte (the ratio limit);
  - a 22-bit window, and reset intervals of 0 and 16 KiB;

- **Fuzz target `chm`**: open, list, then extract into a `TestSink`, on the fixtures, as `wim`.
- **An opt-in comparison** over a folder of CHM files (`BEEZIP_CHM_SAMPLES`), byte for byte

## 13. Decisions

Approved by the user on 2026-11-11: every recommendation ("approve").

1. **BeeZip's own reader on `format/lzx.rs`**, with no crate (§1). *Alternative:* libchm 0.3.1.
   It opens by path only, so it can't read through `Source`. It reads whole entries into memory,
   its LZX code carries chmlib's names with no attribution, and it wasn't run here.
2. **Decode the last frame whole, and cut it to the stated length** (§3.3). *Alternative:*
   decode only the bytes left, which fails on 6 of 81 files, among them every chmcmd file and so
   BeeZip's own fixture.
3. **Read every directory chunk and take every listing chunk,** ignoring the header's first and
   last (§3.1), as 7-Zip does. *Alternative:* trust the header, which loses 98 of 2,584 files in
   chmcmd's multi-chunk file; Microsoft's files read the same either way.
4. **List what 7-Zip lists today** (§4.1): the `#` and `$` files shown, the `::DataSpace`
   streams hidden. *Alternative:* list only the pages, images and other content, hiding the `#`
   and `$` files, so an extraction holds only what the help shows.
5. **A damaged CHM is `Corrupt`, never handed to 7-Zip** (§5.2). A file cut after its directory
   lists whole and gives every file before the cut. *Alternative:* hand damaged files to 7-Zip's
   low-level mode, which lists raw names but can't decode the cut files either.
6. **`.chm` isn't associated** (§7): it joins `DOCUMENTS`, and Explorer's menu keeps BeeZip's
   items. *Alternative:* associate it as the other menu formats are, so that double-clicking a
   help file opens BeeZip instead of the help.
7. **Fixtures made by script** (chmcmd, Halibut if Ubuntu's package writes CHMs, and crafted
   ones), with this machine's real files only in the opt-in comparison (§8). *Alternative:* also
   commit PuTTY's `putty.chm` (MIT, 367 KB), as a real-world file made by Halibut.
8. **Ship it in 0.4.0:** `CHANGELOG.md`'s `## 0.3.1` (the settings fixes from #41) becomes
   `## 0.4.0`, since a new reader is a feature, as M7 and M8 each were. Released after the PR
   merges, on the user's word. *Alternative:* ship it as 0.3.1.
9. **The PR is committed, pushed and merged when green without asking,** stopping before the
   release, as for M8's PRs. *Alternative:* stop for the user's word before merging.

## 14. Found while planning

The spike's folder is `target/m9-spikes/chm/`. Its `REPORT.md` has the details, `scan.txt` and
`check.txt` the last runs.

- **Samples:**
  - 80 unique CHM files from this machine (111 found): Windows' own help (MMC, ODBC, the IMEs,
    an HP driver's 33 languages), Office, Visual Studio, the Windows SDK, SQL Server, 7-Zip,
    PuTTY, NSIS, PyWin32, StarCraft's editor, BeeZip's chmcmd fixture, and M6's damaged PuTTY
    copy.
  - `big.chm`: Rust 1.99.1's `std` docs (2,578 files, 124.6 MB) built by chmcmd 3.2.2, 11.1 MB.
- **Correctness:** all 81 decode, and every file (25,542 plus 2,584) is byte-identical to 7-Zip
  26.00's extraction, with nothing that only one of them extracts.
- **Producers** (`#SYSTEM` code 9): HHA 4.74.8702 (71, though chmcmd and 7-Zip's help also claim
  it), HHA 4.73.8198 (4), HHA 4.74.9273 (3), Halibut (2).
- **Directories:** chunks of 4 KiB (80) or 8 KiB (1); one level (20) or with an index (61).
- **Frames:** each frame's slice from the reset table gives the same bytes as continuous,
  realigned decoding in all 81 files. No block was unfinished at a reset point; E8 translation
  was never on.
- **The last frame:** decoded whole, it works on 81 of 81. Decoding only the bytes left works on
  75; the 6 that fail are 7-Zip's help, both chmcmd samples, `big.chm`, Office's `PSS10R.CHM`
  and StarCraft's `StarEdit.chm`. Decoding to the next reset interval works on 54.
- **chmcmd 3.2.2's first chunk:** in `big.chm` the ITSP header says the first PMGL chunk is 1,
  but chunk 0 is a PMGL chunk too (its next is 1), with 108 entries. All 80 others name it
  right. Added to `docs/UPSTREAM.md`.
- **7-Zip's help file:** directory at the end, content offset 0, and a first header section of
  0x28 bytes. It reads with the offsets as given.
- **Cut files:** a reader that decodes until the cut gives english.chm (cut in half) 2 of 2
  stored and 120 of 296 compressed files whole, and `big.chm` 1,493 of 2,584 (cut in half) or
  2,576 (cut 132 KB short). Cut inside the directory, neither it nor 7-Zip lists anything.
- **Speed,** alone on the machine, best of 3–5:

  | | big.chm (124.6 MB out) | pywin32.chm (13.9 MB, 6,864 files) |
  |---|---|---|
  | prototype, streamed through one 32 KiB buffer | 83 ms (1.5 GB/s) | 14 ms |
  | `7z t`, one thread or several alike | 100 ms (72 ms in-process) | 50 ms (40 ms start-up) |
  | prototype extract (plain `fs::write`) | 1.87 s | 2.91 s |
  | `7z x` | 1.61 s | 2.27 s |
  | BeeZip 0.2.0 `x` (through 7-Zip) | 2.35 s | 5.84 s |

  The product extracts through `FsSink` with its write-behind pool (M8 §6.3), not `fs::write`.
- **Fuzzing:** a mutation fuzzer ran on 11 samples, three in four mutations aimed at the headers,
  directory and metadata streams. 4 seeds × 15 minutes: 1,623,633 runs, 1,588,439 opened and
  1,407,203 read whole. It found no panics, no hangs (20 s watchdog), no run over 2 s and no
  allocation over 512 MiB; the heap peaked at 8 MiB. The product's `chm` target runs under
  cargo-fuzz in CI.
- **libchm 0.3.1** (trypsynth/libchm, MIT, ~1,900 lines, no `unsafe`): auto mode refused to build
  the downloaded crate ("Code from External"), so it was read, not run.
  - It decodes whole blocks, so the six files above should read.
  - It opens by path (`std::fs::File`), returns whole entries as `Vec`s, and keeps a 5-block
    cache.
  - Its `lzx.rs` uses chmlib's identifiers and table sizes throughout (`window_posn`,
    `intel_started`, `intel_curpos`, `LZX_LENTABLE_SAFETY`, table bits 6/12/12/7) with no
    attribution. chmlib is LGPL and took its LZX code from libmspack and cabextract (LGPL).
- **rustchm 0.1.2** has no library target. **chmlib** binds C (LGPL).
- **Settings' 7-Zip section** still names WIM images and virtual disks (stale since 0.3.0),
  fixed in this PR (§7).

## 15. Found while building

PR `m9-chm`, as built on 2026-11-11:

1. **`format/chm/`:** the reader (`mod.rs`), its unit tests (`tests.rs`), and `write.rs`, a CHM
   writer of BeeZip's own whose section 1 is LZX in uncompressed blocks. It's `#[doc(hidden)]
   pub`, as ACE's `encrypt` is, so the unit tests, `xtask gen-fixtures` and fuzzing seeds share
   one writer, and every layout §8 lists can be written, or broken, field by field.
2. **A chunk over 1 MiB is `Corrupt`** (§5.1). Real directories use 4 or 8 KiB chunks, and a
   chunk is read whole, so the claim is refused before anything is allocated from it.
3. **"A 1 KB file claiming a terabyte" isn't a ratio case.** The reset table must have an entry
   for every frame (§5.1), so `chm-1tb.chm` fails its section-1 files as `Corrupt` before
   anything decodes. The ratio limit applies to each file's stream, as for a cabinet's files
   (`Source::guard`).
4. **Halibut 1.3 writes CHMs** (`--chm`): `halibut` joined `make-7z.Dockerfile`, and
   `halibut.chm` is a fixture. Its LZX ends at the stated length, as Microsoft's compiler's
   does; both chmcmd fixtures need the whole last frame.
5. **The crafted layouts aren't script fixtures** (§8). The hand-made writer covers them in
   `format/chm/tests.rs`: ITSF version 2, the directory last with content offset 0, `LZXC`
   version 1, a 2 MiB window, a reset every frame, small chunks with a misnamed first chunk,
   cut files, and each unsupported and damaged field. `tests/chm.rs` also rewrites
   `chmcmd-big.chm` itself to ITSF version 2 and to `LZXC` version 1, and cuts it at three
   lengths. The fixtures are `chmcmd-chunks.chm` (5 listing chunks and an index, the first
   misnamed), `chmcmd-big.chm` (13 frames, 7 reset intervals) and `halibut.chm`; `expected.json`
   is 7-Zip 26.00's extraction of each, the chmcmd trees checked against it.
6. **Malicious corpus** (`xtask/src/fixtures/chm.rs`, `tests/malicious/chm.rs`):
   `traversal.chm`; `chm-chunk-4gib.chm` and `chm-long-encint.chm`, which fail as they open;
   `chm-1tb.chm`, `chm-reset-back.chm`, `chm-window-4mib.chm`, `chm-reset-0.chm` and
   `chm-past-end.chm`, which list and fail only their own files. Each case is done in under
   2 s.

13. **A failed extraction on several workers may leave fewer files.** CHM extraction writes
    small files behind the reader (`write_behind`, M8 §6.3), as CAB and MSI do. When a later
    file is damaged, the sink is dropped with the error and its workers stop, so a small file
    still queued isn't written; on one worker it already was. CI's Windows and macOS runners hit
    it in `chm-1tb.chm` (`#SYSTEM` left on one worker, nothing on four), so the CHM claims test
    checks each worker count on its own instead of comparing them. Both fail as `Corrupt`, and
    nothing lands outside the destination.
