# BeeZip — M2 (MCP) Plan

This plan builds on [`PLAN.md`](PLAN.md), [`M0.md`](M0.md) and [`M1.md`](M1.md) and keeps their decisions, except where §9 corrects PLAN.md. The rmcp APIs named here were checked in the rmcp 3.8.0 sources on 2026-11-03, and the protocol rules against the MCP specification, revision 2026-07-28 (elicitation, tools, and multi round-trip requests).

## Scope
- **beezip-commands:**
  - a policy per call: `Engine::invoke_with_policy`;
  - two caps on `Policy` for front ends that pay per byte, `max_list_entries` and `max_read_bytes`;
  - an `[mcp]` section in `config.toml` (`roots`, `read_only`).
- **beezip-mcp:**
  - **sandbox:** writes confined to `--root` directories, narrowed by the client's roots where the client still has them;
  - **`--read-only` and `--unrestricted`**;
  - **progress notifications** for requests that carry a `progressToken`;
  - **cancellation:** `notifications/cancelled` cancels the job (it already did in M0; M2 tests it end to end);
  - **elicitation** for overwrite questions, over both lifecycles (§3.3);
  - **paging:** `archive_list` pages hold at most 500 entries and `entry_read` returns at most 256 KiB;
  - server instructions that tell the model the rules above.
- **beezip-cli:** `beezip mcp --root <DIR>… [--read-only | --unrestricted]`, which loads the config like every other subcommand.
- **Docs:** [`docs/MCP.md`](MCP.md), covering Claude Code (`claude mcp add`), Claude Desktop and the MCP Inspector, plus a README section.

**Out of scope:**
- **Streamable HTTP:** PLAN §1 already says "stdio first; HTTP later". It isn't scheduled; nothing in M3–M5 needs it.
- **Asking for passwords:** the spec forbids form-mode elicitation for secrets (§3.3). URL mode would need a local web server that verifies who opens the page.
- **Logging notifications:** they are deprecated (SEP-2577). The outputs already carry what was skipped and why.
- **Resources, prompts and the Tasks extension:** BeeZip has nothing to offer through them yet.

## 3. beezip-mcp

### 3.1 Options and policy
```rust
pub struct McpOptions {
    pub roots: Vec<PathBuf>,        // --root, else [mcp] roots
    pub read_only: bool,            // --read-only or [mcp] read_only
    pub unrestricted: bool,         // --unrestricted: no write confinement at all
    pub prompt_timeout: Duration,   // how long a parked job waits for its retry; 10 minutes
}
```
- **Startup:** each root is canonicalised. A root that doesn't exist, or isn't a directory, fails startup with `InvalidArgs`.
- **The base policy:** the config's limits, `read_only`, `max_list_entries: Some(500)` and `max_read_bytes: Some(256 KiB)`.
- **Per call, `Sandbox::policy(cx)`:**
  - `unrestricted` sets `roots: None`;
  - otherwise `roots` is the effective set (§3.2), which can be empty.
- **Before invoking:**
  - if a command that writes meets an empty effective set, the call fails with `OutsideSandbox` and a reason the model can relay: "started without `--root`", or "the client's roots (…) don't overlap `--root` (…)";
  - the engine's `Policy::check` then confines each declared write path. Its `OutsideSandbox` message now names the allowed roots.
- **`--read-only`:** write tools leave `tools/list` entirely, and calling one is `UnsupportedOperation`.
- **Reads aren't confined.** This keeps PLAN's "writes are sandboxed" decision; §10 lists it.

### 3.2 Client roots
- **2026-07-28 removed them.** Roots are deprecated (SEP-2577), and that revision allows server-to-client requests only through MRTR. So only legacy sessions use them: clients that ran `initialize` with 2025-11-25 or older and declared the `roots` capability.
- **When they're fetched:** lazily, on the first tool call that writes. `notifications/roots/list_changed` marks them stale, and the next write fetches them again. A write therefore never races a fetch still in flight.
- **Turning them into paths:** `file://` URIs become paths with `url::Url::to_file_path`. Other schemes, and paths that don't exist, are ignored.
- **Intersection:** for each server root S and client root C, keep the deeper of the two when one contains the other.
- **No narrowing in two cases:**
  - an empty client list ("nothing shared" from a client that supports the capability);
  - a failed `roots/list`. A warning goes to stderr, and `--root` alone applies.

### 3.3 Jobs, progress and prompts (`call.rs`)
Each tool call starts its job with `invoke_with_policy` and a `McpInteractor`. A driver task owns the job's channels:

```rust
enum Step {
    Progress(Progress),
    Prompt { prompt: Prompt, reply: oneshot::Sender<Result<PromptReply, CmdError>> },
}
struct Job { cancel: CancelToken, steps: UnboundedReceiver<Step>, done: JoinHandle<Result<Value, CmdError>> }
```

- **Progress:** the event sink forwards `Progress` events into `steps`. When the current request carries a `progressToken`, the driver sends `notifications/progress`:
  - `progress` is `bytes_done` and `total` is `bytes_total`, both of which only grow;
  - `message` is the current entry.

  After the job ends, the driver drains `steps`, so the final update goes out before the response.
- **Cancellation:** when the request's `ct` fires, the job's `CancelToken` is cancelled and any pending reply is dropped. The job then ends as `Cancelled` and cleans up its partial file, as it does in the CLI.
- **Passwords:** `McpInteractor` answers a password prompt itself, with `PasswordRequired` (`details: {param: "password"}`). The message says to ask the user and pass `password`. Form-mode elicitation "MUST NOT" request passwords.
- **Overwrite questions** go to the driver, which answers them one of three ways:
  - **No form elicitation in the client's capabilities:** a `Conflict` error naming the `overwrite` argument, as `NonInteractive` gives.
  - **Legacy session:** the driver sends `elicitation/create` and waits for the answer, still racing `ct`.
  - **2026-07-28 session (MRTR):** the driver parks the job and returns `InputRequiredResult`, with one `elicitation/create` request under the key `overwrite` and a `requestState`.
    - The `requestState` is a random v4 UUID that indexes the parked job; nothing is encoded in it.
    - **The retry:** the handle is removed on use, so it works once. The retry must name the same tool with the same arguments; anything else is refused and the job stays parked.
    - A retry with a missing or invalid answer gets the same question again, as MRTR's error-handling rules ask.
    - A handle that is unknown, used or expired fails with `InvalidArgs`, saying so.
    - **No retry:** after `prompt_timeout` the job is cancelled. Servers "MUST NOT assume that clients will … retry".
- **The question:**
  - The message is "`<path>` already exists. Replace it?".
  - The schema is one required `choice`, a titled single-select enum: `replace`, `replace_all`, `skip`, `skip_all` and `rename`. The default is `skip`.
  - Declining or cancelling ends the job as `Cancelled`.

### 3.4 Results
- **Output:** `structuredContent`, plus the same JSON as text, as M0 did.
- **Errors:** `isError: true` with the `CmdError` as `structuredContent`, and the JSON as text. The TypeScript SDK skips output-schema validation when `isError` is set (checked in `client.ts` on 2026-11-03), so an error that doesn't match a tool's `outputSchema` is fine.

### 3.5 Instructions
`get_info().instructions` is written for the model. It covers:
- **Paths:** use absolute paths. Relative ones resolve against the server's working directory, which the instructions name.
- **Where writes may go:** the roots, or that the server is read-only, unrestricted, or has no roots.
- **Paging:** at most 500 entries per `archive_list` call, so page with `offset` while `has_more` is true. At most 256 KiB per `entry_read` call, so continue from `offset + bytes_read` until `eof`.
- **Passwords:** BeeZip never asks for them, so on `PasswordRequired` ask the user and pass `password`.
- **Errors:** they carry a stable `code`.

## 4. beezip-commands
- **`Engine::invoke_with_policy(name, args, interactor, sink, policy: Arc<Policy>)`:** `invoke` calls it with the engine's policy. `Engine::policy()` returns that policy, so MCP can build on its limits.
- **`Policy` gains two fields,** both `None` in `Policy::unrestricted()`:
  - `max_list_entries: Option<u64>`: `archive.list` caps `limit` at it, whether given or not. `has_more` already tells the caller to page.
  - `max_read_bytes: Option<u64>`: `entry.read` caps `max_bytes` at it. `eof: false` tells the caller to read on. The 16 MiB ceiling stays an `InvalidArgs` error (M1 §11.26), because asking for more than that is a mistake. Under the MCP cap, a request between 256 KiB and 16 MiB is simply shortened.
- **Config `[mcp]`:** `roots = ["C:\\work"]` and `read_only = false`.
  - `--root` replaces the config's roots; it doesn't add to them.
  - `--read-only` and the config's `read_only` are combined with OR.

## 5. CLI
`beezip mcp`:

| Flag | Meaning |
|---|---|
| `--root <DIR>` | Repeatable; directories BeeZip may write under. |
| `--read-only` | Refuse every command that writes. |
| `--unrestricted` | Write anywhere. Conflicts with `--root`. |

- It loads the config the way `run` does; warnings go to stderr, since stdout carries JSON-RPC.
- Its `--help` gets a trycmd snapshot.

## 6. Tests
- **`beezip-mcp` unit tests:**
  - `sandbox.rs`: intersection, nested and disjoint roots, file URIs, and junctions resolved by canonicalisation;
  - `prompt.rs`: schema shape and answer parsing.
- **`beezip-mcp/tests/server.rs`** runs an rmcp client in-process over `tokio::io::duplex`. Its registry is the real one plus three test commands:
  - `test.ask`, which asks an overwrite question and returns the answer;
  - `test.wait`, which reports progress until it is cancelled;
  - `test.write`, a `Writes` command that declares a path.

  Cases:
  1. **Legacy elicitation:** answering `replace_all` returns `ReplaceAll`. Declining returns `Cancelled`.
  2. **No elicitation capability:** `Conflict`, naming `overwrite`.
  3. **MRTR:** `call_tool` drives the rounds and gets `ReplaceAll`. With `call_tool_once`:
     - the result is `InputRequiredResult` with an `overwrite` request;
     - a retry with different arguments is refused;
     - a reused handle is refused;
     - an empty answer gets the question again.
  4. **Expiry:** a 200 ms `prompt_timeout`. A late retry fails, and the job is gone from `Engine::jobs()`.
  5. **Cancellation:** cancelling `test.wait` after its first progress notification ends the job.
  6. **Progress:** notifications arrive with growing `progress` (§11 explains why "only when a token was sent" isn't a test).
  7. **Client roots (legacy):**
     - a write inside the client's root passes;
     - a write that is inside `--root` but outside the client's root fails with `OutsideSandbox`;
     - after `roots/list_changed`, the new list applies;
     - an empty list doesn't narrow.
  8. **Passwords:** `PasswordRequired` with `details.param == "password"`, against the AES fixture.
  9. **The caps:** `archive_list` caps a `limit` of 1000 at 500, on a 600-entry zip made with `archive_create`; `entry_read` caps 1 MiB at 256 KiB.
- **`beezip-cli/tests/mcp.rs`** runs the real binary. It keeps the M0 cases and adds:
  - `--root` with `archive_extract` of a fixture into the root: the call succeeds, files appear, and progress notifications arrive;
  - extracting outside the root gives `OutsideSandbox`, and the message names the root;
  - no `--root` gives `OutsideSandbox`, and the message mentions `--root`;
  - `--read-only` lists no write tools;
  - the 2026-07-28 lifecycle (`ClientLifecycleMode::Discover`) lists and calls tools;
  - a root that doesn't exist fails at startup with exit code 2.
- **The parity test** is unchanged: with default options, every MCP-visible command is listed.

## 9. PLAN.md corrections (applied)
1. **MCP elicitation (§1, Interactor and Front ends):**
   - Spec 2026-07-28 forbids server-to-client requests, so elicitation goes out inside an `InputRequiredResult`, and the job waits, parked, for the client's retry.
   - Sessions that negotiated 2025-11-25 or older still get a plain `elicitation/create`.
   - Passwords are never elicited, because form mode must not carry secrets: `PasswordRequired` always comes back. Elicitation is for overwrite questions.
2. **Client roots (§1, Front ends):** only legacy sessions have them. Roots are deprecated and MRTR-only in 2026-07-28. An empty list doesn't narrow `--root`.
3. **`--read-only` (§1):** it also hides the write tools from `tools/list`.
4. **Progress (§1):** sent only for requests with a `progressToken`. BeeZip sends no logging notifications, which are deprecated.
5. **The MCP limits (§1):** they come from two new `Policy` caps, which the CLI and GUI leave unset.
6. **HTTP (§1):** it stays unscheduled. Nothing in M2 needs it.

## 10. Decisions (taken while planning, 2026-11-03)
Each could reasonably go the other way. Say which to reverse, and I'll change it.
- **Passwords:** the model asks the user, and passes the password as an argument. The alternative is URL-mode elicitation with a local page.
- **Reads aren't sandboxed.** Only writes are, as PLAN decided. The alternative is `--root` confining reads too, which would stop the model from opening archives in Downloads unless it is given that root.
- **An empty client root list doesn't narrow.** The alternative, refusing every write, is the strict reading of "intersect", but it breaks clients that support roots and share none.
- **Over-cap requests are shortened, not refused,** for `archive_list` and `entry_read`. The output says there is more.
- **Parked jobs wait 10 minutes** for their retry.
- **`--read-only` hides write tools.** Without `--root`, they stay listed and explain how to enable writes.

## 11. Found while building
The rmcp APIs matched §3. Building settled these details:

**rmcp**
1. **`RequestContext::ct`** is a tokio-util `CancellationToken`, which rmcp doesn't re-export. So `beezip-mcp` depends on tokio-util, at the version already in the lock.
2. **Progress tokens:** rmcp's client attaches a `progressToken` to every request. So no test can show that a request without one gets no notifications. `Reporter` sends nothing without a token, and that path is simple enough to read.
3. **Negotiation:** rmcp answers a 2026-07-28 `initialize` with 2025-11-25 and records the negotiated version. So `RequestContext::protocol_version()` tells a legacy session from a 2026-07-28 one, which is how the driver chooses between `elicitation/create` and MRTR.

**Interfaces**

4. **`Engine::invoke_with_policy`:** the job's context moves to its thread in one `JobSetup` struct, rather than as eight arguments.
5. **`commands::register_all` is public,** so a test can build a registry of the real commands plus its own.
6. **The cap test moved in-process.** `archive_list` capping at 500 is tested in `beezip-mcp/tests/server.rs` rather than against the binary. Building the 600-entry zip through `archive_create` needs a root, which that suite already has.
7. **The help texts** for `--limit` and `--max-bytes` name the MCP caps. The schemas, and so the doc comments, are shared by every front end.

**Rules settled**

8. **Intersection** drops a root that lies inside another, so `--root C:\a` with client roots `C:\a` and `C:\a\b` gives `C:\a`.
9. **Messages show paths as people write them,** without the `\\?\` prefix canonicalising adds on Windows (`policy::display_path`).
10. **`--unrestricted`** conflicts with `--read-only` as well as with `--root`.
11. **A bad config doesn't stop `beezip mcp`.** `[mcp]` is ignored with a warning, and the commands that need the config fail as they do in the CLI.
12. **Shutdown:** when the client disconnects, running jobs are cancelled. The runtime then waits up to 10 seconds for them to remove their partial files.

**Verification**

13. **The MCP Inspector check (§8) is still to run.** Its `npx` download was blocked as external code. The tests cover both lifecycles with rmcp's client, but that is the server's own SDK. A client on the TypeScript SDK, such as the Inspector or Claude, is worth one run before relying on it.
