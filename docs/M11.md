# BeeZip — M11 (BeeZip without 7-Zip) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M10.md`](M10.md) and keeps their
decisions. After 0.5.0 the user asked whether the last formats only 7-Zip reads could be read
without it (2026-11-13): MSI patches (`.msp`), transforms (`.mst`) and merge modules (`.msm`).
M7 left them to 7-Zip (M7 §14 decision 5): `format/msi/` refuses a patch or transform by its
root CLSID and a merge module by its ModuleSignature table, with `UnsupportedOperation`. While
that plan waited for approval, the user asked for more: that 7-Zip never be used, so BeeZip
reads what 7-Zip still read for it (the variants its readers refuse) and the 7-Zip backend goes.
They offered WSL2's Ubuntu or a Hyper-V machine for Linux, and CI for macOS.

A spike on this machine backs the plan (`target/m11-spikes/`, with a `REPORT.md`; §14 sums it
up). It builds only on crates BeeZip already has:
- **A prototype,** a copy of `beezip-core`: about 500 lines in `format/msi/` for the three MSI
  formats, and the variants 7-Zip reads (§6): CramFS, QCOW, NTFS, WIM, and LZMS on Linux through
  wimlib's library. It was checked against 7-Zip 26.00 file by file, fuzzed, and timed; the
  Linux build ran in Docker (the `beezip-pr6h:jammy` image to build, the fixtures image, which
  has wimlib, to run).
- **Every refusal checked against 7-Zip:** the ~60 places BeeZip's readers hand a file to 7-Zip,
  each against 7-Zip 26.00's source (tag 26.00, read only) and, where a file could be made, a
  `7z l`/`7z t` run (`variants.md`).
- **Every place the backend is wired in** (`removal.md`), from core to the site.

The MSI samples:
- **Patches:** the three in `C:\Windows\Installer` (Adobe Acrobat Reader updates of 55, 60 and
  148 MB), and a 28 KB patch made here by the Windows SDK's own `MsiMsp.exe` (patchwiz.dll).
- **Transforms:** 631 real ones:
  - 581 embedded in five of the 477 installers cached here (LibreOffice, Epic Games Launcher
    and SQL Server 2022), taken out as files;
  - 48 from the patches above (a patch carries two transforms for each product it targets);
  - two made by the SDK's `MsiTran.exe` and by Windows Installer's own `GenerateTransform`.
- **Merge modules:** Microsoft's nine Visual C++ 14.51 x86 modules (41 files), downloaded from
  Microsoft's Visual Studio feed with the user's agreement, and two made here by Windows
  Installer's own API (msi.dll) and `makecab.exe`, with what Microsoft's lack: folders under the
  merge point, short and long names, a Latin-1 name, two files at one path, MsiFileHash rows, a
  custom action's DLL, and LZX. wixl 0.103 can't make merge modules ("unhandled child Wix node
  Module").
- **The msi crate's** empty patch, transform and merge module, and crafted files (§8).

These findings shape the plan. For the MSI formats:
- **A merge module is a small MSI, and BeeZip's MSI reader reads it with one change.** It has
  no Media table: all its files are in one embedded cabinet, `MergeModule.CABinet`. Given one
  Media row for that stream, the reader lists every file where the module puts it
  (`SystemFolder/vcruntime140.dll`), where 7-Zip lists the module's 16 raw streams (`!File`,
  `MergeModule.CABinet`, `[5]SummaryInformation`…). **All 59 files of the eleven modules are
  identical to 7-Zip's extraction of their cabinets,** matched by File key.
- **Patches and transforms are listed as 7-Zip lists them:** each storage a folder, each stream a
  file, under 7-Zip's names for them (`!_StringPool`, `TGT_1ToUPG_1/!File`,
  `[5]SummaryInformation`), with `.cab` added to a cabinet's (`PCW_CAB_ACR.cab`, decision 3).
  **All 8,448 streams of the four patches and all 7,561 of the 631 transforms are identical to
  7-Zip's, under the same names.**
- **BeeZip doesn't open transforms today, through 7-Zip or otherwise.** Detection accepts only a
  package's and a patch's root CLSID, so every `.mst` is "not an archive" (M6 §16 item 13 noted
  it). The README, the site, Settings and `beezip 7zip install --help` say 7-Zip opens them. M11
  detects them (§2).
- **A patch's files can't be named by where they install without the target installer:**
  - A patch's cabinet holds the patched files under the target's File keys, and **most are
    binary deltas, not files**: 265 of 266, 299 of 300 and 431 of 1,097 in the Adobe patches
    (`PA19`, Windows' delta format, which only Windows Installer applies, to the installed file).
    The rest are files the patch adds.
  - A transform holds only the cells it changes. Its transforms name none of the files of two
    of the Adobe patches and 663 of the third's 1,097 (the added ones), and place none of them
    in a folder: their Component and Directory rows are the target's.
  - Decoding a transform needs the target's column types, which a transform doesn't carry for
    the tables it changes: Adobe's File.Sequence is 2 bytes, wixl's 4, and the wrong guess
    misreads every row.
- **Speed:** listing and testing take what 7-Zip takes (0.07 s and 0.17 s for the 148 MB
  patch). Extracting takes what BeeZip 0.4.0 takes through 7-Zip (2.2 s against 2.0 s; `7z x`
  1.3 s): the time is in writing its 3,890 small files (§14).
- **cfb refuses names with `/`, `\`, `:` or `!`** (MS-CFB forbids them; 7-Zip lists them): such
  a file is `Corrupt` (§5).

For the rest of 7-Zip's work:
- **Most of what BeeZip hands to 7-Zip, 7-Zip can't read either, or nothing writes.** Of the
  ~60 refusals, real tools write and 7-Zip reads only: NTFS with clusters over 64 KiB
  (`format /A:128K`–`2M`), QCOW version 1, HFS+ whose catalog spans more than eight extents,
  VHDX tables over 2^23 entries (over 8 TiB with 1 MiB blocks), ext volumes over 2^32 blocks,
  sealed APFS volumes, and LZMS images on Linux and macOS. A few more nothing is known to write
  (WIM chunks over 64 MiB from a wimlib option, 7-Zip's own CramFS variant, VMDK VMFSRAW, VDI
  undo images…), and WIM 1.09–1.12 from Longhorn's betas.
- **The prototype reads the ones that matter, as 7-Zip does or better:**
  - 7-Zip's CramFS variant: 17 images (LZMA and zlib, blocks of 4 to 512 KiB), every file as
    7-Zip extracts it;
  - QCOW version 1: five images from qemu-img, plain, compressed and with a backing file, every
    file as from the raw disk; 7-Zip fails the compressed ones and the child;
  - NTFS with clusters of 128 KiB to 2 MiB, a ten-line patch to fstool: five mkntfs volumes,
    every file as 7-Zip extracts it;
  - WIM chunks up to 1 GiB, within `decoder_memory`;
  - LZMS on Linux through wimlib's own library, loaded at run time as `cabinet.dll` is on
    Windows: all 15 WIM and ESD fixtures test (every SHA-1), and a 92 MB tree round-trips through
    three LZMS images in 0.72 s, where wimlib's own `apply` takes 0.54 s.
- **Fuzzing found nothing:** 514,211 MSI runs, and 109,289 more over the variants on Windows and
  LZMS through wimlib on Linux (§14).
- **7-Zip's fallback isn't always right.** When it can't open a disk, it scans inside and opens
  a partition table or file system it finds there; BeeZip took that as the disk read, which for
  a dynamic disk is wrong data past the first block.
- **Two fstool problems** (`docs/UPSTREAM.md`): it tests APFS's sealed-volume flag as `0x80`
  where Apple's reference and 7-Zip say `0x20`, so a sealed volume (macOS 11+'s system volume, in
  a DMG too) is probably read wrong today; and it refuses an HFS+ catalog in more than eight
  extents, which a DMG then fails.
- **What would still be lost** (decision 12): ext volumes over 2^32 blocks (16 TiB with 4 KiB
  blocks: fstool's ext is 32-bit there and keeps every group's bitmaps in memory), and WIM
  1.09–1.12 (2003–05 betas; no samples exist).
- **The backend is about 6,500 lines of code and 4,500 of test data** (`removal.md`): it all goes,
  with Settings' 7-Zip section, Install 7-Zip and `beezip 7zip install`. 7-Zip stays a test
  oracle.

Nothing was built into the repo, committed or pushed while planning. The user approved every
recommendation in §13 on 2026-11-13.

## Scope

- **Merge modules read by BeeZip's MSI reader** (§3.1, §4.1): listed where the module puts its
  files, with test, extract, preview, `entry.read` and Info.
- **Patches and transforms read by BeeZip** (§3.2, §3.3, §4.2): listed as their compound file,
  as 7-Zip lists them, with the same commands. Transforms are detected for the first time. A
  compound file of another kind named like an installer is listed the same way.
- **The variants 7-Zip reads, read by BeeZip** (§6), but for decision 12's two.
- **LZMS on Linux and macOS** through wimlib's library when it's installed (§6.2).
- **The 7-Zip backend removed** (§7): no fallback, Settings section, Install 7-Zip,
  `beezip 7zip install` or 7-Zip fields in `formats.list` and `archive.info`. 7-Zip stays only as
  a test oracle.
- **Unchanged:** the format's wire name (`msi`), the commands, Explorer's menu and the
  associations: none of `.msi`, `.msp`, `.msm` or `.mst` is associated or in the menu.

## 1. Dependencies

- **No new crates.** cfb 0.16.0 reads the compound file, as for MSI, and BeeZip's CAB reader the
  cabinets. The msi crate stays a dev-dependency (test packages). lzma-rust2 decodes the CramFS
  variant's LZMA, as for NSIS.
- **fstool 0.5.2, vendored** in `vendor/fstool` with BeeZip's patches (decision 11), as
  hadris-iso is: NTFS clusters over 64 KiB, HFS+ overflow extents, APFS sealed volumes (§6.3).
- **libc** becomes a dependency on Linux too (it is on macOS), for `dlopen` (§6.2).
- **wimlib's library isn't a build dependency.** It's the system's, LGPLv3+, loaded at run time
  only when an LZMS image is read on Linux or macOS, as `cabinet.dll` is Windows' (§6.2). No
  wimlib code is in BeeZip.

## 2. How it fits

- **One format, three readers' worth of rules.** `External::Msi` keeps every Windows Installer
  file. `format/msi/mod.rs`'s `open` reads the root CLSID first:
  - a package's (or none), with a ModuleSignature table or not: `MsiReader`, as today, with the
    merge module's change (§4.1);
  - a patch's, a transform's or any other: `format/msi/compound.rs`, new (§4.2). Another kind
    only reaches the reader by its name, when its directory is beyond the bytes detection reads;
    it's listed as its compound file, as 7-Zip lists it, with a note saying what it is.
- **Detection** (`backend/sniff.rs`) accepts the transform CLSID `{000C1082-…}` as `Certain`, as
  the package's and the patch's are, and `.mst` joins `.msi`, `.msp` and `.msm` for the name
  fallback, `formats.list` and the site's table.
- **Neither reader has anything unsupported to refuse.** Damage is `Corrupt`, as in M7–M10 (§5).
- **A patch's or transform's test reads every stream** and says so in its note: a compound file
  has no checksums. A merge module's checks the CAB checksums and MsiFileHash, as an MSI's does.
- **Size:** the prototype's `compound.rs` is 360 lines and the MSI reader's change about 110.
  With the cabinet names, Info, limits and tests: about 600 lines in `format/msi/` and a
  PowerShell fixture script (§8).

## 3. The formats, as the spike found them

### 3.1 Merge modules

- **The same database as an MSI,** with the package's root CLSID, and:
  - a ModuleSignature table (ModuleID `Name.GUID`, Language, Version), ModuleComponents, and
    others the merge reads (ModuleInstallExecuteSequence in Microsoft's; ModuleDependency,
    ModuleExclusion and ModuleConfiguration in some);
  - **no Media table:** every file is in the stream `MergeModule.CABinet`, under its File key, in
    Sequence order;
  - keys carry the module's GUID (`vcruntime140.dll_x86.F1670FCA_6780_…`), which the merge
    keeps, so they don't collide with the product's.
- **Folders:** the module's Directory table hangs under TARGETDIR, which the merge replaces by the
  product's folder chosen for it (WiX's `<Merge>` in a `<Directory>`). A folder under TARGETDIR
  with DefaultDir `.` (WiX's `MergeRedirectFolder`) is that folder itself. Standard folders are
  modularized (`SystemFolder.F1670FCA_…`, DefaultDir `System`) and set by a custom action, or
  kept as they are when the author suppressed it.
- **Microsoft's modules** put every file in `SystemFolder.<GUID>` (the CRT's nine DLLs, MFC's
  four, MFCLOC's ten), compressed with MSZIP, with no MsiFileHash (versioned files have none).
- **Configurable merge modules** (ModuleConfiguration, ModuleSubstitution) change cells at merge
  time, including DefaultDir values (`[=Name]`). None of the eleven is one.

### 3.2 Patches

- **A compound file with the patch CLSID `{000C1086-…}`,** holding:
  - its own database: `_StringPool`, `_StringData`, `_Tables`, `_Columns`, MsiPatchMetadata
    (display name, description, manufacturer, classification…) and MsiPatchSequence;
  - for each target product, two transforms as storages: `TGT_nToUPG_n` (the changes to the
    product's tables) and `#TGT_nToUPG_n` (the patch's own rows: Patch, PatchPackage, Media,
    and `Patch.<key>.<seq>` header streams);
  - its cabinets, named by the patch transforms' Media rows (`PCW_CAB_ACR`), the only streams
    that start with `MSCF`;
  - the summary: the patch code and the patches it replaces (Revision), the target product
    codes (Template, 23 for each Adobe patch), the transforms (Last saved by:
    `:TGT_1ToUPG_1;:#TGT_1ToUPG_1;…`).
- **The cabinet's files are the target's File keys** (`SingleClientServicesUpdater.exe`,
  `nppdf32.FRA1`), most of them `PA19` deltas against the installed file, as above.

### 3.3 Transforms

- **A compound file with the transform CLSID `{000C1082-…}`**: a string pool, and one stream
  for each table it changes (`!File`, `!Property`…), plus `_Tables` and `_Columns` rows for
  tables and columns it adds, and streams for binary cells it sets (`Binary.ADelRCP`).
- **Each table's stream is rows, not columns** (a database's are columns): each row a 16-bit
  mask of the cells present, then the cells. Keys are always present; a mask of 0 deletes the
  row. The widths come from the target's column types (Wine's `table.c`).
- **The summary:** Template (platform and language), Revision (the target's and the result's
  product codes and versions, and the upgrade code), and the validation flags.
- **Where they come from:** saved beside an installer (`msiexec TRANSFORMS=x.mst`, the Office
  and Adobe customization tools), embedded in it as storages (LibreOffice's 125 language
  transforms), or in a patch.

## 4. Reading

### 4.1 Merge modules

- **The listing** is the MSI reader's (M7 §8.2), unchanged:
  - TARGETDIR adds no level, so the files the module puts in the product's folder are at the
    top, with `.` folders under it adding none either (`readme.txt`, `Documentation/guide.txt`);
  - a standard folder, or the module's copy of one, starts at the top under its name
    (`SystemFolder/vcruntime140.dll`, `ProgramFiles64Folder/BeeZip Module/tool.dll`);
  - the long half of `short|long`, `[Binary]/` streams (custom actions), two files at one path
    as M7 decision 5 has it (`dup.<File key>.txt`).
- **The data:** when the database has a ModuleSignature table and no Media rows, the reader takes
  one Media row covering every Sequence, whose cabinet is the embedded `MergeModule.CABinet`.
  Everything after that (the CAB reader, sizes, MsiFileHash, write-behind) is the MSI reader's.
- **A missing cabinet stream** fails each file, as an MSI's missing cabinet does, saying the
  merge module's cabinet isn't in it.
- **Info:** the module's ID, version and language (ModuleSignature), the summary's subject and
  author (`Visual C++ 14.51 CRT (X86)`, `Microsoft Corporation`), and a note: files are listed
  where the module puts them; those at the top go where the product merges it. Levels `msm` and
  `cab`.

### 4.2 Patches and transforms

- **The listing:** every storage a folder, every stream a file, under 7-Zip's name for it
  (7-Zip's `MsiName_To_FileName`):
  - Windows Installer's packed characters unpacked (two of `[0-9A-Za-z._]` in one code point
    from U+3800, one alone from U+4800);
  - the table mark (U+4840) as `!`: `!File`;
  - a control character as `[n]`: `[5]SummaryInformation`;
  - an empty name as `[]`; anything else as it is.
- **Order** (decision 4): folders first, then files, each by path ignoring case, as the MSI
  reader puts its folders first. (7-Zip's is its directory tree's, which reads as random.)
- **Cabinets get `.cab`** (decision 3): a stream that starts with `MSCF` and whose name doesn't
  end in `.cab` is listed as `PCW_CAB_ACR.cab`, so the app opens it in a tab on a double-click
  (`lib/opened.ts` goes by the name) and an extracted one opens anywhere. That's the only name
  that differs from 7-Zip's.
- **Sizes** are the streams'; **times** the storages' (as 7-Zip shows them); streams have none.
- **Data:** each stream as it's stored, through `CfbStream`, checked against its length.
  Extraction writes on other threads, as for MSI.
- **Info:**
  - a patch: MsiPatchMetadata's DisplayName, Description, ManufacturerName, Classification,
    TargetProductName and MoreInfoURL when it has them; the patch code (the first GUID of
    Revision); the number of target products (Template) and of transforms; and a note: the
    cabinets hold the patched files under the target's keys, most as changes to the installed
    files that only Windows Installer applies.
  - a transform: the target's and the result's product codes and versions and the upgrade code
    (Revision), the platform and language (Template), the title, subject and author; and a note:
    each table's changes are listed in Windows Installer's own form.
  - another kind: its CLSID, and a note that it's named like an installer but isn't one.
  - Levels `msp`, `mst` or `compound`.
- **Test** reads every stream. A compound file stores no checksums, so the note says what it
  checked, as for disk images.

## 5. Limits and damage

### 5.1 Checked when it opens

- **cfb's own checks** at open (sector chains, the directory tree), fuzzed in M7 (2.4 million
  inputs) and here (§14).
- **Patches and transforms:**
  - at most 64 levels of storages and 4,096 bytes a path; deeper ones are left out with a
    warning (`deep.mst`'s 300 levels list 64);
  - the names together at most 128 MiB, and no more entries than `max_entries` (200,000 streams
    list in 1 s);
  - each stream's length against the file's.
- **Merge modules:** everything the MSI reader checks (M7 §6, §8): table and string-pool sizes,
  folder depth, path length, the CAB reader's limits.

### 5.2 Damage

`Corrupt` (decision 7):
- **A stream claiming more than the file** is listed, and fails when it's read (the rest
  extract). 7-Zip can't open such a file at all (`huge-claim.mst`).
- **A name with `/`, `\`, `:` or `!`:** cfb refuses the whole file ("Object name cannot contain /
  character"), as MS-CFB §2.6.1 forbids them. 7-Zip lists them (`/` and `\` as `_`). Windows
  Installer never writes one. The file is `Corrupt`.
- **Names that are unsafe on disk** (a packed `..`, `CON`) are listed as they are and left to
  `SafeFs`, as for every format: `..` and its file are skipped, `CON` becomes `_CON`.
- **A merge module's missing or damaged cabinet** fails its files, as an MSI's does.

and the evidence. What M11 does with them:

### 6.2 LZMS on Linux and macOS (decision 10)

- **On Windows,** `cabinet.dll`'s decoder, as in M8.
- **On Linux and macOS,** `format/wim/lzms_wimlib.rs` (about 140 lines,
  `#![allow(unsafe_code)]`, joining PLAN §1's unsafe places) loads wimlib's library the first
  time an LZMS image is read: `libwim.so.15` by its soname on Linux; `libwim.15.dylib` from
  Homebrew (`/opt/homebrew/lib`, `/usr/local/lib`) or MacPorts (`/opt/local/lib`) on macOS. It
  calls wimlib's public compression API (`wimlib_create_decompressor`, `wimlib_decompress`,
  `wimlib_free_decompressor`), one decoder per worker, a chunk at a time, exactly as
  `lzms_win.rs` calls Windows'. The WIM reader picks one or the other by platform.
- **Without wimlib** an LZMS image is `UnsupportedOperation`, saying how to install it
  (`apt install libwim15`, `dnf install wimlib`, `brew install wimlib`). The `.deb` and `.rpm`
  recommend the package if Tauri's bundler can say so; the site says it either way.
- **The spike** (Linux, wimlib 1.14.4): all 15 WIM and ESD fixtures test, every SHA-1 checked,
  including the four only Windows read until now; a 92 MB tree round-trips through a solid ESD,
  a WIM of 1 MiB chunks and a solid ESD of 256 MiB chunks (7-Zip reads all three); BeeZip
  extracts it in 0.72 s, `wimlib-imagex apply` in 0.54 s. Fuzzing: 52,183 runs, no crash (§14).
- **macOS** runs the same code; it's checked in the PR's CI, on the macOS runner with
  `brew install wimlib`, since nothing is pushed while planning.
- *Alternatives:* drop LZMS on Linux and macOS; or a clean-room decoder, which M8 §5.3 put at
  8–15 weeks with high risk, written by someone who never read wimlib's or 7-Zip's LZMS code.

### 6.3 fstool, vendored and patched (decision 11)

- **A copy of fstool 0.5.2 in `vendor/fstool`,** with `[patch.crates-io]`, as hadris-iso's is,
  trimmed to the modules BeeZip's features build if fstool's `cfg`s allow it (its whole source is
  10 MB). Each change is marked `BeeZip:` and listed in `docs/UPSTREAM.md`.
- **The patches:**
  - **NTFS:** `BootSector::decode` takes a sectors-per-cluster byte over 0x80 as 2^(256 − v)
    sectors, and keeps the cluster size in bytes (done in the spike, about ten lines);
  - **HFS+:** the catalog and attributes forks read with their overflow extents
    (`from_inline_plus_overflow`, which fstool has, after the extents-overflow file itself);
  - **APFS:** the sealed-volume flag as `0x20`, and a sealed volume's file extents read from its
    file-extent tree (`apfs_fext_tree_oid`, keyed by object ID and logical address).
- **The APFS fix matters without 7-Zip too:** today a sealed volume isn't recognised, and in a
  DMG it's read without its extents.
- **Samples:** NTFS from mkntfs, as in the spike. A fragmented HFS+ catalog and a sealed APFS
  volume made on the macOS CI runner (`hdiutil`, `newfs_hfs`, `apfs_sealvolume`) if it can make
  them; otherwise crafted from a small volume by script. If a sealed volume can be had neither
  way, the user is asked before an IPSW is downloaded; failing that, the flag is fixed and sealed
  volumes are refused, which is still better than today.

### 6.4 Refused, as 7-Zip refuses them

Encrypted QCOW2 images and ESDs, pipable WIMs, unknown WIM solid methods, LZX chunks over 2 MiB,
VMDK seSparse, vmfsSparse and RDM extents, VHDX version 2 and unknown required regions or
metadata, VDI blocks with extra bytes, NTFS records over 64 KiB, ITSF other than 2 and 3,
NSISBI's flags, ext's dirdata and external journals. Also refused where 7-Zip gives stale or
wrong data: an unreplayed VHDX log, a VMDK whose embedded descriptor names other extents, a disk
7-Zip can't open and scans inside. These stay `UnsupportedOperation`, with the reader's own
words and nothing about 7-Zip.

### 6.5 Lost (decision 12)

- **ext volumes over 2^32 blocks** (16 TiB with 4 KiB blocks, 4 TiB with 1 KiB): fstool reads
  the superblock and group descriptors as 32-bit and keeps both bitmaps of every group in memory
  (1 GiB for 16 TiB). Reading them means opening ext without fstool, though BeeZip already maps
  blocks, reads folders and replays the journal itself.
- **WIM 1.09 to 1.12,** written by Longhorn's and Vista's betas in 2003–05: an older header and
  folder-entry layout, with no samples anywhere to check against.
- **A WIM split part read through a codec or inside a numbered set** (`split.swm.gz`), which 7-Zip
  reads only in part.

## 13. Decisions

For the user's approval. Each is a recommendation, followed by its alternative.

1. **Merge modules through BeeZip's MSI reader,** listed where they put their files (§4.1).
   *Alternative:* 7-Zip's view, as for patches: the raw streams, with `MergeModule.CABinet` to
   open as a cabinet whose files are named by their keys.
2. **Patches and transforms listed as their compound file, with 7-Zip's names** (§4.2), not by
   where a patch's files install. The transforms name none of two Adobe patches' files and 60 %
   of the third's, place none in a folder, and most of the files are deltas. *Alternative:* name
   what the transforms name and list the rest by key, which looks complete but isn't.
3. **A cabinet stream gets `.cab` added to its name** (`PCW_CAB_ACR.cab`), so it opens with a
   double-click and opens anywhere once extracted. *Alternative:* 7-Zip's exact names; the
   cabinet opens after it's extracted and renamed.
4. **Folders first and names sorted** in a patch or transform. *Alternative:* the compound file's
   own order, or 7-Zip's.
5. **Transforms detected** by their CLSID, and `.mst` added to the MSI format's extensions, not
   associated and not in Explorer's menu (as `.msi`, `.msp` and `.msm`). *Alternative:* also
   associate `.msp`, `.mst` and `.msm`, which nothing else opens (Windows runs a `.msp`).
6. **Fixtures made by script** (on Windows for MSI: msi.dll, makecab, the SDK's MsiTran and
   MsiMsp; in the fixtures container for the variants) and committed, with Microsoft's merge
   modules and the Adobe patches only in the opt-in comparison (§8). *Alternative:* commit
   Microsoft's CRT merge module (700 KB), redistributable with an application under Visual
   Studio's licence but not under BeeZip's.
7. **A damaged file is `Corrupt`** (§5.2), as in M7–M10, including names cfb refuses.
   *Alternative:* list what cfb refuses by reading the directory without cfb.
8. **Remove the 7-Zip backend** (§7): BeeZip never runs 7-Zip; Settings' 7-Zip section, Install
   7-Zip and `beezip 7zip install` go; 7-Zip stays only as a test oracle. *Alternative:* keep the
   backend, off by default, for §6.4's and §6.5's files, with Install 7-Zip.
9. **Read §6.1's variants as 7-Zip reads them,** including those nothing is known to write, so
   that removing 7-Zip loses nothing it read but decision 12's. *Alternative:* only what real
   tools write (NTFS, QCOW version 1, HFS+, APFS, the VHDX table, WIM chunks), refusing the rest.
10. **LZMS on Linux and macOS through wimlib's library when it's installed** (§6.2), as
    `cabinet.dll` on Windows: nothing built in, an error saying how to install it otherwise.
    *Alternatives:* LZMS on Windows only; or a clean-room decoder (M8 §5.3: weeks, high risk).
11. **fstool vendored with BeeZip's patches** (§6.3) for NTFS clusters over 64 KiB, HFS+
    overflow extents and sealed APFS volumes, each listed in `UPSTREAM.md` (nothing is filed
    upstream, as decided before). *Alternative:* BeeZip's own NTFS boot-sector and HFS+/APFS
    code around unpatched fstool where it can, and the rest refused.
12. **Accept losing ext volumes over 2^32 blocks and WIM 1.09–1.12** (§6.5). *Alternative:* open
    ext without fstool (BeeZip already maps blocks and reads folders itself), and the old WIM
    layout from 7-Zip's description, with no sample to check it.
13. **Compatibility:** remove `beezip 7zip install`; ignore an old config's `[seven_zip]` keys
    without a warning, and say they were removed if someone sets one; remove the 7-Zip fields
    from `formats.list` and `archive.info` (§7). *Alternative:* keep the command as a stub that
    explains, and the fields as always null, for one release.
14. **Four PRs** (§9), **each committed, pushed and merged when green without asking,** stopping
    before the release, as for M8–M10. *Alternative:* stop for the user's word before each
    merge, or before the last.
15. **Ship in 0.6.0,** after the last PR. *Alternative:* 0.6.0 after the MSI PR and the variants,
    and the removal in 0.7.0.

## 15. Found while building

### PR 1 (`m11-msi`)

1. **The compound file is opened once.** `msi::open` reads the root CLSID and hands the open file
   to the MSI reader (a package's CLSID or none) or to `compound.rs` (any other); the prototype
   opened it twice, sending a patch on by an error.
2. **A merge module's files are all read from `MergeModule.CABinet`,** whatever its word count or
   a file's attributes say: a module has no source image, and the module built in `tests/msi.rs`
   says its files aren't compressed.
3. **A raw `.` or `..` name** (not Windows Installer's packed one, which §5.2's `msp-names.msp`
   has) is followed by cfb as a path step, so a stream under it would read another stream. Such
   a stream is listed and fails as `Corrupt`.
4. **A stream that claims more than the file stops an extraction,** as any damaged entry does in
   BeeZip; §5.2's "the rest extract" holds for a test, which reads past it and fails only that
   stream (`mst-claim.mst`), and for a selection without it. On four workers a stream written
   before it may be dropped with the sink, as M9 §15 found for CHM, so the corpus checks each
   worker count alone.
5. **The malicious MSIs are written by `tests/msi.rs`'s `write_the_malicious_msis`,** as M7's
   are, not by `xtask gen-fixtures` (§8). The msi crate writes GUIDs and times, so the run
   rewrote M7's five too; only the seven new ones were kept.
6. **`make-msi-extras.ps1` builds the two wixl products itself,** in the fixtures image, instead of
   `make-7z.sh` (§8), which would have had to run whole. It ports the spike's `gen-msm.ps1` and
   `gen-patch.ps1`. wixl's `Compressed="no"` warnings (`docs/UPSTREAM.md`) show as it runs.
7. **The opt-in comparison is a test of its own,** `real_patches_transforms_and_modules_read_as_7zip_extracts_them`,
   with `7z x` as the oracle, so PR 4 needn't change it. `BEEZIP_MSI_SAMPLES` now names folders
   separated as PATH is, searched to any depth for these. On the spike's samples (`samples/{msp,
   msm,msm-made,made,mst-split,skeleton}` and `work/embedded`): 650 files, 16,034 streams of
   patches and transforms (§14's 8,448 and 7,561, and the msi crate's empty patch and transform)
   and 59 files of merge modules, all as 7-Zip extracts them.
8. **Info:** a module's ID, version and language (ModuleSignature) and its summary's subject and
   author; a patch's MsiPatchMetadata, its patch code and the counts of target products and
   transforms; a transform's codes and versions split out of Revision (`Target product code`,
   `Target version`, `Result product code`…), its title, subject, author, platform and language.
   The notes don't name 7-Zip, which goes in PR 4.
9. **Words:** the README, the site, `docs/MCP.md`, Settings and the CLI said 7-Zip opens MSI
   patches; until PR 4 they say it opens ESD images on Linux and macOS and the few files BeeZip
   doesn't read itself. The changelog's 0.6.0 section starts here, not in PR 4 (§9).

### PR 2 (`m11-variants`)

1. **wimlib's package names differ by release:** Ubuntu 24.04 and Debian 13 call the library
   `libwim15t64`, older ones `libwim15`. The error says `apt install wimtools` (which pulls the
   library in on every release), `dnf install wimlib` or `brew install wimlib`; the `.deb`
   recommends `libwim15t64 | libwim15` and the `.rpm` the library's soname
   (`libwim.so.15()(64bit)`), each checked by `linux-bundle.sh`. CI installs it on Linux, on the
   macOS runner and for the `wim` fuzz target, and sets `BEEZIP_REQUIRE_LZMS=1`, so a missing
   one fails; elsewhere the tests check that the error names wimlib. Checked in Docker on
   Linux, with wimlib (all WIM, fixture and malicious tests) and without.
2. **`format::wim::lzms_available()` is public,** for the tests to know which way to check.
3. **`7zip/wimlib-solid.esd` has a native record now** (`native-records.py`, marked
   `"lzms": true`): one image at the top, one hard link and two symlinks.
4. **CramFS:** flags above bit 15 are ignored with a warning on any image, as 7-Zip ignores them,
   not only on 7-Zip's variant; bits 12–15 without version 2's flag stay refused. Method 3 is
   `UnsupportedOperation` as the image opens (7-Zip lists it and extracts nothing). zlib with
   4 KiB blocks is method 1: method 0 with bits 11–13 clear is Linux's own layout.
   `make-cramfs.sh` makes `sevenzip-{lzma,zlib}-{4k,64k,512k}.img` and `bit31.img`, with
   records, and checks that 7-Zip extracts the same files from each.
5. **WIM:** `chunk-256m.esd` holds 65 MiB of zeros in one solid LZMS chunk, 1.4 KB in all, so it
   passes the ratio limit, as it should; its test opens it without one. wimlib's images aren't
   byte-for-byte reproducible (creation times libfaketime doesn't reach), so the new ones get
   GUIDs of their own and the committed ones were kept; the crafted three come from that run's
   `xpress.wim`. A lookup table flagged compressed in an image that isn't compressed is
   `Corrupt`; in an XPRESS one it reads. `wim-chunk-1g.esd` (chunks of 1 GiB claiming 2 GiB)
   opens and fails as damaged at once within the default `decoder_memory` (1 GiB), and is
   refused as it opens with 256 MiB.
6. **CHM:** section 1's name is `NameList`'s second (`MSCompressed` without one), and
   `Transform/List` isn't read at all. A file in a section past 1 stays `Corrupt` ("BeeZip reads
   sections 0 and 1"): 7-Zip reads a third section as LZX, but nothing is known to write one.
   The four variants are `chmcmd-chunks.chm` edited by `make-chm.sh`; 7-Zip extracts the same
   251 files from each.
7. **The CLI's 7-Zip tests needed a file only 7-Zip reads;** the CramFS variant isn't one now, so
   they use an AES-encrypted QCOW2 until PR 4 removes them.
8. **Virtual disks** (built by a helper alongside, in its own worktree):
   - **QCOW version 1:** `make-vdisk.sh` makes `q-v1.qcow` (read now), `q-v1-c.qcow`
     (compressed) and `q-v1-child.qcow` (512-byte clusters with 4 KiB written over its backing
     file, as qemu makes one), each recorded in `expected.tsv` from qemu-img's reading. qemu-img
     8.2.2 exits 1 without a message after writing a sound compressed version 1 image, so the
     script checks it with `qemu-img compare`. A rerun changed no other image.
   - **Block tables are read in 1 MiB pages for VHD too,** not only VHDX: a shared `Paged` table
     in `vdisk/mod.rs` keeps 16. Opening walks every entry a page at a time without keeping them.
     Two tests build big disks at run time (their tables are 64–68 MB, not committed): a VHDX of
     8 TiB + 64 GiB in 1 MiB blocks, 8,456,207 entries (the spike's 8,456,208 was one too many:
     MS-VHDX gives blocks + ⌊(blocks − 1)/chunk⌋), opening in 0.7 s in a debug build; and a VHD of
     2^24 + 1 entries.
   - **VHD versions aren't checked, in detection either:** `sniff.rs` required version 1.0 in the
     footer, so a fixed VHD saying 2.0 wasn't detected at all. Another version gets a note in Info.
   - **VHD blocks up to 2 GiB,** the most the header can say: a block is read where it is, and only
     its sector bitmap (at most 512 KiB) is held.
   - **VMDK grains up to 1 GiB:** a stored one is read where it is; a compressed one must fit
     `decoder_memory`, which now reaches the disk readers (`Files::with_memory`), or it's
     `LimitExceeded`. A grain whose bytes couldn't decode to it (deflate's 1,032:1), or that runs
     past the file, is `Corrupt` before anything is allocated, and only the extent's part of a last
     grain is kept (else `vdisk-grain-1g.vmdk` would allocate 1 GiB for its 256 KiB disk).
   - **VMFSRAW reads as FLAT** (VMFSRDM and VMFSRDMP stay refused); **a VDI undo image is read
     alone**, its free blocks as zeros, with method "Undo" and a note; **a VHDX parent locator of
     any type** is read for its keys.
   - **The variant files come from `make-vdisk.sh`,** into `thirdparty/vdisk/` with `expected.tsv`,
     not from a separate script: VHDs from `thirdparty/vhd`'s `fat-dyn.vhd` and `fat-fixed.vhd`
     (each reads as `fat-fixed.vhd`'s SHA-256 in `SHA256SUMS`), VMDKs that read as `disk.img`, and
     `d-undo.vdi`, now read. A test checks that each is detected as its format.
   - **Malicious:** `vdisk-qcow1-l1.qcow` (L1 past the file, `Corrupt` at open);
     `vdisk-qcow1-clen.qcow` (every compressed cluster past the file: damaging only the first
     left the files extractable, since extraction never read it); `vdisk-vhdx-table.vhdx` (64 TiB
     in 1 MiB blocks, 67,125,247 entries claimed in 3 MiB: `Corrupt` at open, nothing allocated).

### PR 3 (`m11-fstool`)

1. **The vendored copy is trimmed** to fstool's source for the four file systems BeeZip builds
   (5 MB of its 12): every other file system is behind its feature, so leaving them out needed
   no other change; the binary's, examples' and tests' targets left `Cargo.toml`, and one line
   keeps a dead-code warning quiet on Windows (`patches/trim.diff`). `vendor/fstool/BEEZIP.md`
   lists the patches, `code-taken-in.md` names the copy, and `docs/UPSTREAM.md` marks the three
   bugs patched.
2. **HFS+:** fstool's `open` also calls `open_writable`, which walks the whole catalog for its
   writer and read it inline-only too; both build the fork with `special_fork`, and so does
   BeeZip's own resource-fork reader (`apple.rs`), which opened the catalog itself.
3. **The HFS+ and APFS samples are crafted** by `make-apple-variants.py` from the committed bare
   volumes, as §6.3's fallback allowed, rather than made on the macOS runner, and 7-Zip extracts
   the same files from each as from its source. A crafted sealed volume needs its extent records
   out of the fs-tree, as a real one has them: 7-Zip takes a file's extents from the file-extent
   tree only when the fs-tree has none. Through fstool's old flag, every file of it reads as
   zeros (the bug `docs/UPSTREAM.md` couldn't reproduce before). Both are 74 and 79 KB as `.xz`.
4. **NTFS:** `make-ntfs.sh` makes `c128k.img.xz` and `c2m.img.xz` (97 and 193 KB, with Python's
   lzma: the image has no `xz`), with `clusters.json` for their files. Negative-form cluster
   sizes on a volume laid out in 4 KiB clusters are damage now; only clusters over 2 MiB are
   `UnsupportedOperation` ("NTFS's are at most 2 MiB").
5. **Words:** the example of what 7-Zip still reads, until PR 4, is an ext volume over 16 TiB.
