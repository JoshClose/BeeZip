# BeeZip — M6 (Long tail + ship) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M5.md`](M5.md) and keeps their decisions, except where §13 corrects PLAN.md. Versions, licenses, prices and release dates were checked on 2026-11-07 against crates.io, npm, GitHub and the vendors' pages. The APIs named here were checked in the sources of zip 9.4.1, sevenz-rust2 0.25.0, lzma-rust2 0.25.0, unarc-rs 0.8.1, zar 0.2.0, apple-xar 0.20.0, gzp 2.0.4, mtzip 4.0.3, tauri-bundler 2.10.4 (Tauri CLI 2.12.4), tauri-plugin-updater 2.14.1, tauri-driver 2.1.0, drag 2.1.1 and cargo-about 0.9.3.

M6 is the last milestone. After it come the one look-and-feel pass over the finished app and the hand-over of the upstream bug list; the first public release follows those (§14).

Spikes on this machine back the plan; §16 "Found while planning" has their results. These change what PLAN says:
- **unarc-rs isn't used.** Its HA, UC2 and JAR decoders are translations of GPL-2, LGPL-3.0 and proprietary code, published under MIT OR Apache-2.0. Every module is compiled whatever you use, and so is a RAR *writer* of unchecked origin. It also holds whole entries in memory and loses name bytes. ARJ, ACE and ZOO come from its license-clean modules, taken in as BeeZip's own code with their notices. ARC is written in-house. HA, UC2, JAR, HYP and SQZ aren't read (§4).
- **No XAR crate is usable.** zar fails cargo-deny's advisories and doesn't build on Windows; apple-xar opened none of 21 test archives. Both crash on crafted input. BeeZip reads XAR itself, read-only, and lists a `.pkg` as `pkgutil --expand-full` unpacks it (§5).
- **The 7-Zip backend streams.** One `7z x -so` process per job feeds FsSink directly, with no staging folder: 3.4–4.3× faster on Windows' own images, with no second copy on disk. Staging is only for NSIS installers, whose listed sizes 7-Zip only estimates. It needs 7-Zip 25.01 or newer, the first without the 2025 symlink-extraction CVEs (§3).
- **The installer stays NSIS only.** Tauri's MSI is per-machine, writes associations with no backup, adds no PATH entry and runs none of the hooks. Intune can deploy the NSIS installer with `/S` (§9.3).
- **Signing is a purchase and an identity check only you can make** (§9.2). Until then, everything keeps building unsigned, and Windows 11 gets the classic menu from the installer, as now.
- **Two BeeZip bugs** came up and are fixed here:
  - a second `BeeZip.exe` started soon after the first can lose its archive (§8.1);
  - two entry names that become the same name on Windows (`a.` and `a `) overwrite each other without the overwrite policy being asked (§3.4, §11 PR 1).
- **The speed work is BeeZip's own code** (§6):
  - **why:** gzp needs C to prime its blocks, mtzip writes entries in random order and without Zip64, the zip crate has no parallel writer, and lzma-rust2's multithreaded xz decoder neither limits its memory nor verifies blocks;
  - **gzip:** 2 552 MB/s at level 6 on 32 threads, against 144 on one;
  - **zip writing:** 7–20× faster;
  - **xz decoding:** 10× faster (3 664 MB/s on 16 threads);
  - **extracting small-file zips:** 2.2–2.6× faster, once a lock that serialises BeeZip's partial files is fixed.

## Scope
- **Formats:**
  - the `SevenZipCli` backend: WIM/ESD, CHM, MSI, NSIS, VHD/VHDX, VMDK, QCOW2, VDI, MBR/GPT disks, FAT, NTFS, ext2/3/4, HFS+, APFS and CramFS images (§3);
  - ARJ, ACE, ZOO and ARC, read only (§4);
  - XAR and macOS `.pkg`, read only (§5).
- **Speed:** parallel gzip, parallel zip writing, parallel extraction of non-solid zips, multithreaded xz decoding (§6), and `bench.run` with a chart in the desktop (§7).
- **Shipping:**
  - a generated `THIRD_PARTY_NOTICES.md` for the Rust crates and the npm packages in the bundle (§9.1);
  - a signing pipeline that takes a production certificate when you have one (§9.2);
  - installer fixes (§9.3);
  - `tauri-plugin-updater` (§9.4);
  - a release workflow that makes draft releases (§9.5);
  - a winget manifest for `CloseConsulting.BeeZip` (§9.6);
  - Linux (deb, rpm, AppImage) and macOS (DMG) bundles built on CI (§9.7).
- **Desktop:** the early-launch fix (§8.1), the updater's UI (§8.2), what changes on Linux and macOS (§8.3), a tauri-driver E2E test (§10), and drag-out to Explorer as a stretch goal (§8.4).
- **Dependencies:** zip, sevenz-rust2 and lzma-rust2 bumped together. hadris is rechecked and stays vendored (§1).

**Out of scope:**
- **After M6:** the one look-and-feel pass over the finished app; the upstream bug list handed over; the first public release, with the trademark check and the domain PLAN §5 asks for (§14).
- **Not planned:**
  - HA, UC2, JAR, HYP and SQZ (license or unknown origin), Amiga LZX/DMS/ADF, Pack-Ice, and the retro disk images unarc-rs also reads (§4.1);
  - writing XAR or `.pkg`, and expanding Apple Archive payloads (§5);
  - real file names inside MSIs (7-Zip shows the installer's internal keys, §3.6);
  - opening executables, ELF, Mach-O or Office files through 7-Zip;
  - editing anything the 7-Zip backend reads;
  - the optional libarchive backend (PLAN §2), which stays unbuilt;
  - parallel bzip2 decoding, and parallel extraction of formats other than zip (§6.5);
  - an MSI installer (§9.3);
  - universal macOS builds (arm64 only), Flatpak or Snap, and E2E tests on macOS (tauri-driver has no macOS driver).

## 3. The 7-Zip backend
PLAN §2 gives the long tail to an installed 7-Zip. The spike ran 7-Zip 26.00 over samples of every format below, made here (in Docker for the Linux file systems) or found on this machine (§16).

### 3.1 Finding 7-Zip
- **Where it looks, in order:** `[seven_zip] path` in the config; `HKCU` then `HKLM\SOFTWARE\7-Zip` `Path64`, then `Path`; `7z`, `7zz` and `7za` on PATH; `%ProgramFiles%\7-Zip\7z.exe`.
- **What it needs:** 7-Zip 25.01 or newer. 25.00 and 25.01 fixed CVE-2025-11001, -11002 and -55188 (link extraction), and `-slmu` and `-slsl` (UTC times, `/` separators) came in 24.03. The version is read from the banner (`7-Zip 26.00 (x64) : …`); a console 7-Zip that calls itself something else (NanaZip's) is accepted when it takes `-slmu` (an unknown switch exits 7 before any archive is read).
- **When it's missing or too old:** `BackendUnavailable`, "Opening a WIM image needs 7-Zip 25.01 or newer. Install it from 7-zip.org, or set its path in Settings."
- **Not bundled.** 7-Zip is LGPL with the unRAR restriction; running a separate, installed program keeps BeeZip's own license clean (PLAN §5). Ubuntu 24.04's `7zip` package is 23.01, too old, so on Linux the backend wants 7-Zip's own `7zz`.
- **`[seven_zip] enabled = false`** turns the backend off.
- **Cached** per process with the file's size and modified time, so a newly installed 7-Zip is found without a restart.

### 3.2 Formats and detection
BeeZip's own sniffers claim these formats, with 7-Zip's signatures, so `file.detect` names them whether or not 7-Zip is there:

| Format | Signature | Extensions |
|---|---|---|
| WIM, ESD, SWM | `MSWIM\0\0\0` at 0 | `.wim`, `.esd`, `.swm` |
| CHM | `ITSF` at 0 | `.chm` |
| MSI (and MSP, MSM) | the Compound File header, with an MSI root CLSID | `.msi`, `.msp`, `.msm` |
| NSIS installer | `EF BE AD DE NullsoftInst` in a PE overlay (in the overlay scan, beside 7z and RAR SFX) | `.exe` |
| VHDX | `vhdxfile` at 0 | `.vhdx` |
| VHD | `conectix` at 0, or in the last 512 bytes (a fixed VHD has only the footer) | `.vhd` |
| VMDK | `KDMV` at 0, or a descriptor | `.vmdk` |
| QCOW2 | `QFI\xFB` at 0 | `.qcow2`, `.qcow` |
| VDI | the VirtualBox magic at 64 | `.vdi` |
| GPT, MBR disk | `EFI PART` at 512; `55 AA` with a sane partition table, ranked below ISO, FAT and NTFS | `.img`, `.raw` |
| FAT | a BIOS parameter block that checks out | `.img`, `.ima` |
| NTFS | `NTFS    ` at 3 | `.img` |
| ext2/3/4 | `53 EF` at 1080 | `.img`, `.ext4` … |
| HFS+, HFSX, APFS | `H+`/`HX` at 1024, `NXSB` at 32 | `.hfs`, `.apfs`, `.img` |
| CramFS | its magic at 0 or 512 | `.cramfs` |

- **One `FormatId::External`** carries the kind (`wim`, `vhdx`…), its display name and its extensions, so the wire names and `formats.list` grow without a variant per format.
- **Not claimed:** executables (other than NSIS installers), ELF, Mach-O, Office documents, SWF, Base64 and Intel HEX, which 7-Zip also opens. Claiming them would turn every `.exe` and `.docx` into an archive.
- **Nested containers:** 7-Zip opens the levels of a disk image itself (`VHDX > GPT > NTFS`, `VMDK > MBR > ext4`), so BeeZip passes no `-t` and checks that the outermost level is the format it sniffed. A disk with several partitions lists each as a file (`0.data.fat`, `1.linux.img`), as 7-Zip does; one is opened by extracting it.
- **Pseudo entries** in file systems (`[SYS]/Journal`, `[SYSTEM]/$MFT`, `[DELETED]`, `lost+found`) are listed as 7-Zip lists them.

### 3.3 Listing
```
7z l -slt -sccUTF-8 -scsUTF-8 -slmu -slsl -sns- -bse2 [-p] -- <archive>
```
- **The process:** `DETACHED_PROCESS` (no console host), stdin null, the archive path absolute and after `--`. `-p` with nothing after it stops 7-Zip asking for a password; a password goes in through stdin, which is then closed, so it never appears on a command line.
- **The output:** a banner, a block per level (`Path`, `Type`, `Physical Size`, then the handler's own keys), `----------`, then one block per entry, then `Warnings: N` / `Errors: N`.
  - Each handler prints a fixed set of keys on every entry, even empty ones. The parser learns them from the first entry and treats any other line as the previous value going on, since comments (a VMDK descriptor, PE resources) run over several lines and can contain ` = `.
  - Lines are split on `\n` only: 7-Zip turns `\n` in a name into `_`, so a name can't forge a field (tested), but `\r`, tabs and escapes come through.
  - Bytes that aren't UTF-8 arrive as U+EF80–U+EFFF (byte = char − 0xEF00); BeeZip turns them back into bytes, so `encoding` (M5 §6) applies to FAT, ext and NTFS names too.
  - Times are UTC (`-slmu`): 100 ns for WIM and NTFS, nanoseconds for ext4 and APFS, 2 s for FAT. Without `-slmu`, 7-Zip prints local times at today's offset, so a file from May shows an hour off.
  - `-ba` isn't used: it drops the level blocks.
- **Entries:** path, kind (folder from `Folder`, or a 0-byte entry with a child under it, since CHM and APFS have no `Folder` key), sizes, times, attributes or mode, CRC, encrypted, method, link target. `Entry.method` and `ArchiveInfo.methods` become owned strings (`Cow<'static, str>`) for 7-Zip's methods (`LZX:15`, `LZMS:17`).
- **Parsed as it streams**, into compact entries: install.esd's 904 344 entries are 473 MB of text, which the spike's first parser held at 3.3 GiB. The listing counts against `max_entries` while it's read.
- **Errors** come from stderr (`ERROR:`, the `ERRORS:` group, `Open ERROR:`) and the exit code (0, 1 warning, 2 error, 7 bad switch, 255 break): "Wrong password" → `WrongPassword`, "Cannot open the file as archive" → `UnsupportedFormat`, "Unexpected end of archive" and "Headers Error" → `Corrupt`.
- **The cache** (M3 §4.2) keeps the listing, keyed as for every format; no 7-Zip process outlives the job.

### 3.4 Extracting
**Streaming is the default:**
```
7z x -so -bsp0 -bse2 -sns- -spd -ssc [-i@<list>] -sccUTF-8 -scsUTF-8 [-p] -- <archive>
```
- **One process per job.** 7-Zip writes every non-folder item to stdout, in listing order, exactly its listed size; symlinks write their target. BeeZip hands each one to FsSink as a `Take(size)` reader, builds folders and links from the listing, and drains what it skips. Nothing of 7-Zip's touches the disk, so every SafeFs rule applies to the names 7-Zip lists, not to what 7-Zip would make of them.
- **Why not staging:** on boot.wim (46 384 entries, 3.79 GB) streaming took 87 s and staging 370 s; on one image of install.esd (102 209 files, 15.3 GB) 273 s against 935 s, plus 15.3 GB staged. Most of staging's time is reading back files just written (§16).
- **Selections:** `-spd` makes `*`, `?` and `[` literal, `-ssc` makes case count, and the list is checked first with `7z l -i@<list>`, which counts what it matches. Names a list file can't carry (leading or trailing spaces, `\n`, `\r`) fall back to streaming everything and discarding what wasn't selected.
- **NTFS streams:** `l` hides alternate data streams but `x` writes them, so `-sns-` goes on both.
- **Limits** are checked against the listed totals before the process starts (install.esd claims 106 GB), then on the bytes received. The ratio limit compares output with the archive's physical size, since 7-Zip's reads can't be counted.
- **Progress** is bytes received over the listed total.
- **Cancel** kills the process by its handle; FsSink drops the partial file it was writing. The spike's prototype took up to 13.6 s, because it checked only between entries; reading in 1 MiB pieces puts that under a second.
- **Staging for NSIS only:** 7-Zip lists an NSIS installer's sizes from its script, and they can be wrong (BeeZip's own installer has a plugin listed at 13 316 bytes that extracts to 7 680; §16). So NSIS goes through `7z x -o<staging>`, a private folder beside the destination, then each staged file goes to FsSink: opened without following reparse points, named from the listing by 7-Zip's own rewrite rules, links taken from the listing and never from staging. The staging folder is deleted at the end, on cancel too.
- **`open_entry`** (preview, `entry.read`, `entry.open`) is one `7z x -so -i!<name>` process.
- **The FsSink fix that came with this (PR 1):** the spike's `trail.` and `trail ` both become `trail_` on Windows, and FsSink treated the second as "the same path twice" (an appended tar), so it replaced the first without asking. "The same path" now means the same name in the archive; two names that only meet after they're made safe go to the overwrite policy (asked by default), as case-only clashes already do. It affects every format, not only 7-Zip's.

### 3.5 Testing and info
- **`archive.test`** runs `7z t` and reports its per-entry errors (`CRC Failed : path`, `Data Error : path`). For disk images this means "decodes", not "verified": a flipped byte in a QCOW2 or a CHM passes, since those formats carry no checksums, and `archive.test` says so in its output.
- **`archive.info`** gains `backend` ("7-Zip 26.00") and `levels` (`["vhdx", "gpt", "ntfs"]`), and fills the rest from the level blocks: physical size, methods, solid, blocks, headers size, images (WIM), label, cluster size.

### 3.6 MSI
7-Zip shows an MSI's files under their cab keys (`filFF4C…`) and its tables as raw streams (`!File`, `[5]SummaryInformation`). BeeZip shows the same, and `archive.info` warns that the names are the installer's internal keys. A native reader would give real names: the msi crate (0.11.1, MIT) for the tables, BeeZip's own CAB reader for the files. It isn't planned (§14).

### 3.7 Commands and front ends
- **`formats.list`** marks the backend's formats `backend: "7-zip"` with `available`, and their caps are list and extract only.
- **The CLI and MCP** reach them like any format; MCP's sandbox is unchanged, since 7-Zip only reads the archive and FsSink writes.
- **Settings:** `[seven_zip] path` (empty: find it) and `enabled`; the settings page shows what it found, and its version, with a Browse button.
- **Associations:** none of these extensions. Windows mounts VHD and VHDX and installs MSIs, and the others are rare. Explorer's menu offers BeeZip's archive items on `.wim`, `.esd`, `.swm`, `.chm`, `.vhd`, `.vhdx`, `.vmdk`, `.qcow2` and `.vdi`; without 7-Zip the job window says what's missing.

## 4. ARJ, ACE, ZOO and ARC
PLAN asked for unarc-rs once its license was checked. It can't be a dependency (§16): HA's decoder is HA 0.999's C translated and renamed (GPL-2), UC2's comes from ULTRACMP.CPP and its dictionary (LGPL-3.0 since 2015), and JAR's is a "faithful port" of a disassembled JAR32.EXE. Its other modules have clean origins, and its own license is MIT OR Apache-2.0, so BeeZip takes those in as its own code.

### 4.1 Where each one comes from

| Format | From | Notice kept | Lines | Changes |
|---|---|---|---|---|
| ARJ | unarc-rs's `arj` (© Mike Krüger) | MIT | ≈ 1 000 without GOST40 | methods 1–3 through delharc (already used for LHA), method 4, garble; GOST40 left out (§14) |
| ACE 1.0 and 2.0 | unarc-rs's `ace`, a port of acefile (© Daniel Roethlisberger) | MIT, and acefile's BSD-2-Clause | ≈ 1 750 | Blowfish through `blowfish`; ACE 2.0's EXE, DELTA, SOUND and PIC modes refused (§14) |
| ZOO | unarc-rs's `zoo` (headers) | MIT | ≈ 330 | its LZW on BeeZip's `.Z` decoder, LH5 through delharc |
| ARC | BeeZip's own | — | ≈ 600 (estimate) | stored, packed (RLE), squeezed, crunched, squashed; PAK's crushed and distilled refused (§14) |

**Each module, as it comes in:**
- **Behind `ArchiveReader`, streaming:** entries are decoded into the sink, not into a `Vec` per entry (unarc-rs's 1 GiB-per-entry buffers go).
- **Names as bytes, through `NameDecoding`,** defaulting to the system's OEM code page as zip names do. unarc-rs decodes ACE, ARC and ZOO names with `from_utf8_lossy`, which loses OEM bytes.
- **Every header field bounded before use:** crafted 9–58-byte ARJ files panicked its parser at three places (§16).
- **ARJ fixes:**
  - archives made on Unix store Unix times, so they're read as Unix times; unarc-rs and 7-Zip show 2033 for a file from today;
  - ARJ 3.10's volume sets (`.a01`…) read, which unarc-rs refuses with a size mismatch, although the data decodes. They're found like RAR's parts.
- **ACE volumes** (`.c00`, `.c01`) read as sets the same way.
- **CRCs** checked on every entry, as `archive.test` expects; UC2's never were, but UC2 isn't taken.
- **Passwords:**
  - ARJ garble and ACE's Blowfish go through `Ctx::password`.
  - ARC has no encryption flag, so a password XORs every entry, plain ones included. BeeZip asks only when an entry's CRC fails without one.

Caps: list and extract. No writing: the tools that make these formats are gone, and nobody needs new ones.

## 5. XAR and pkg
- **The reader** (from the spike's 931 lines):
  - the header (`xar!`, version 1) and the zlib-compressed XML table of contents, through quick-xml;
  - **bounded:** the table at most 64 MiB packed and 256 MiB unpacked, and exactly its declared length; 1 000 000 entries and text nodes of 1 MiB at most. quick-xml's pull parser reads it without recursion, so deep nesting costs nothing, and only XML's five predefined entities are expanded, so a billion-laughs table fails at once;
  - files, folders, symlinks and hard links;
  - names given in base64 (`enctype="base64"`) decoded;
  - data stored, or compressed with gzip/zlib, bzip2, xz or lzma, through BeeZip's codecs;
  - the table's checksum (SHA-1, MD5, SHA-256 or SHA-512), and each file's archived and extracted checksums, checked by `archive.test` and while extracting;
  - heap offsets checked against the file.
- **pkg** (flat packages are XAR):
  - **Listed as `pkgutil --expand-full` unpacks them:** a component package's `Payload` and `Scripts` become folders of their cpio contents, its `Bom` and `PackageInfo` stay files. A product archive's `Distribution` stays a file and each component is a folder, expanded the same way. This is how deb.rs lists a Debian package (M5 §5.3).
  - **Payloads** are gzip'd cpio (odc), or pbzx, Apple's chunked xz, which BeeZip reads itself (≈ 120 lines).
  - **Apple Archive payloads** (macOS 12's `--compression latest`) are listed as one `Payload` file with a warning. Expanding them is a format of its own, and not planned.
  - 7-Zip shows a component package's Payload as one gzip member and doesn't open product archives.
- **Detection:** `xar!` at 0. Associations: `.xar` and `.pkg`, which nothing on Windows opens.
- **Caps:** list and extract. Writing XAR is about 400 lines, but it's barely used outside pkg, and a pkg that installs also needs a Bom and a signature.
- **Speed and safety in the spike:** a 40 MB file in 0.09–0.58 s; 180 000 mutated cases with no panic, abort or hang.

## 6. Speed
- **BeeZip's own code:** gzp, mtzip, the zip crate's `rayon` feature and lzma-rust2's `XzReaderMt` were each tried, and each lacks something BeeZip needs (below). What replaces them is BeeZip's own code on crates it already ships.
- **Scoped threads per job:** the workers are scoped threads, as the codecs' threads are now (PLAN §1). rayon, today only a test dependency (through trycmd), stays out of the shipped build.
- **Thread counts:**
  - writing follows `[create] threads`, which already exists (0 means one per core);
  - reading follows a new `[extract] threads`;
  - 1 turns either off.
- **The timings** are the spike's (§16), on 16 cores and 32 threads. The extraction, xz and small-zip runs were repeated on a quiet machine; the gzip and big-zip runs shared it with the other spikes (others' load 11–50 %), so those are, if anything, low.

### 6.1 Parallel deflate (gzip, zlib, raw deflate)
- **How (`codec/deflate_par.rs`, about 250 lines in the spike):**
  - the input is cut into 128 KiB blocks by offset;
  - each block is compressed by a fresh zlib-rs `Compress`, primed with the 32 KiB before it (`set_dictionary`) and ended with a sync flush; the last block finishes the stream;
  - workers also take each block's CRC-32 (Adler-32 for zlib), and the writer combines them in order;
  - the gzip header keeps BeeZip's name and mtime, as now.
- **The bytes depend only on the level:** 1, 4 and 32 threads gave identical output at levels 1, 6 and 9.
  - Reusing a `Compress` (`reset()`, then `set_dictionary`) gives different bytes on zlib-rs, a bug for the upstream list.
  - A fresh one per block costs 12 % at level 1, and nothing measurable at level 6.
- **One thread stays on flate2's encoder,** which is 3–20 % faster there, so `threads = 1` writes today's bytes.
- **Speed** (MB/s; the toolchain as a 1.09 GB tar; the size is against flate2's):

  | Level | flate2 | 1 thread | 4 | 16 | 32 | Size |
  |---|---|---|---|---|---|---|
  | 1 | 629 | 509 | 1 732 | 5 510 | 6 407 | −0.8 % |
  | 6 | 153 | 144 | 525 | 1 973 | 2 552 | −0.6 % |
  | 9 | 57 | 60 | 223 | 852 | 1 341 | −0.03 % |

  On the toolchain's HTML alone (462 MB), level 6 goes from 343 to 5 053 MB/s.
- **Memory:** under 40 MiB at 32 threads, since the blocks in flight are bounded.
- **Checked:** flate2, `7z t` and `gzip -t` read every output. The inputs included an empty one, one block, one block plus a byte, three blocks and 3 MB of random data.
- **Used for** `.gz`, `.tgz`, zlib and raw deflate streams, and big zip entries (§6.2).
- **Decoding stays on one thread:** a deflate stream can't be split without an index.
- **Not gzp 2.0.4:**
  - its default build is C (zlib-ng, libdeflate);
  - without C, it compresses each block with no dictionary, up to 16 % bigger on text;
  - its header has no name or mtime;
  - its `Drop` unwraps `finish()`.

### 6.2 Zip writing
- **Per entry (`format/zip_par.rs`):**
  - workers compress, and encrypt, whole entries, each as a one-entry zip from the zip crate with BeeZip's own options;
  - each goes into memory up to 64 MiB, and into a temporary file beside the destination beyond that;
  - the job thread appends them in BeeZip's order, moves each central record to its new offset, and writes the directory, with M5's byte-copy pieces (`zip_edit`), never `raw_copy_file`.
- **Inside big entries:** an unencrypted Deflate entry of 16 MiB or more is compressed with §6.1 instead, after a local header that BeeZip writes and then patches (Zip64 when needed). An encrypted big entry stays on one thread.
- **Bounded:** at most 8 × threads entries and 512 MiB of input in flight.
- **Same order, same entries:** the entries come out in BeeZip's order at any thread count, each with the bytes one thread would write. The only exception is the big entries of the point before.
- **Edits** (M5's add and convert) send their new entries the same way; entries copied from the old archive stay byte copies.
- **Cancel and progress:** workers check the job's cancel flag; progress counts the input read.
- **Speed** (deflate level 6):

  | Set | Machine | Today | 16 threads | 32 |
  |---|---|---|---|---|
  | 20 000 files, 652 MB | quiet | 4.64 s | 0.77 | 0.67 (6.9×) |
  | the same, AES-256 | quiet | 14.86 s | | 1.17 (12.7×) |
  | 6 files, 931 MB | others at 11–40 % | 7.30 s | 0.50 | 0.37 (19.7×) |

  - **The 6-file row** is with deflate inside big entries. Per entry alone, it stops at 2.2 s, held up by its 462 MB entry.
  - **There's room left:** mtzip wrote the 20 000 files in 0.49 s at 16 threads. BeeZip's path writes each entry as a one-entry zip and then copies it once more; PR 2 measures whether writing the local data directly is worth it.
  - **AES on many small files** derives a key per entry (PBKDF2, 1 000 rounds), which is why it's more than 3× slower on one thread. Spreading the entries over workers spreads that cost.
- **Checked:** all 40 zips (every thread count, AES and ZipCrypto) pass `7z t` and BeeZip's own test.
- **Not mtzip 4.0.3:**
  - its entries come out in completion order;
  - it has no encryption, no Zip64 (sizes are silently truncated past 4 GiB in release builds) and no cancel;
  - it labels Stored entries Deflate, which `7z t` refuses.
- **Not the zip crate's `rayon` feature:** it adds only parallel extraction (§6.3).

### 6.3 Parallel extraction of zips
- **Which archives:** single-file zips (not split sets) with 64 files or more, extracted to disk: Extract, Extract here, the CLI's `x`, MCP's `archive_extract`.
  - Previews, `entry.read` and streams stay sequential.
  - So does every other format.
- **Workers:** one per logical CPU by default, as `[create] threads = 0` means; `[extract] threads` sets it, and 1 turns it off.
  - A destination on a spinning disk (Windows' seek-penalty query) gets one worker. That case isn't measured, and parallel small writes make a disk seek more.
- **The job thread keeps every decision,** in entry order, before any data is written:
  - names: sanitising, `strip_components`, the case and collision rules (with §3.4's fix), the Rename policy's free names;
  - folders, made and checked inside the destination (0.6 s for 20 000 files in the spike);
  - overwrite decisions, prompts included (Replace all, Skip all, Newer);
  - the password, unlocked before the workers start;
  - `max_entries`;
  - after the workers: links and folder times, as now, and the report, in entry order.
- **The workers do the rest,** one entry at a time:
  - read the entry at its offset through their own handle;
  - decode it, and check its CRC and size;
  - write the partial file and rename it;
  - set its time, attributes and Mark of the Web.
- **Limits:**
  - the total-bytes budget is shared, as an atomic;
  - the ratio check moves from the one input counter to each entry's own counts.
- **Progress and cancel:** the job thread polls the workers' counters every 20–50 ms, so the `Ctx` stays on one thread. Cancelling stops the workers, and every partial file is deleted, as now (`abandon_all` included).
- **The partial-file registry first:**
  - **the problem:** `Partial::create` holds the process-wide registry's mutex while it creates the file, and `persist` holds it across the rename, so the workers queue on it;
  - **the fix:** a lock held only to add and remove entries, with renames under a read lock.
- **Speed** (BeeZip's zip of 20 000 files, 124 MB to 652 MB, quiet machine, best of 3):

  | | Today | 4 workers | 16 | 32 |
  |---|---|---|---|---|
  | Mark of the Web off | 12.8–15.2 s | 7.9 | 6.5 | 5.8 (2.2–2.6×) |
  | Mark of the Web on | 19.4 s | 12.3 | 9.5 | 7.5 (2.6×) |
  | With today's registry lock, off | | 10.2 | 10.3 | 10.3 (1.2–1.5×) |

  - **The workers' rows** are without the registry at all; the fixed lock is meant to come close, and PR 2 measures it.
  - **Small files are bound by the per-file cost,** most of it Defender scanning each new file: one thread writes about 1 300 files a second, against about 1 GB/s for big files. Workers overlap that cost; the CPU stays under 15 %.
  - **Six big files** (931 MB) went from 0.99 s to 0.33 s (3×), held up by the 462 MB entry.
- **Same result:** the names, sizes, CRCs and times of all 20 000 files matched the sequential extraction.
- **Not the zip crate's `par_extract`:** it writes straight to the final path, with no partial file, overwrite policy, limits or Mark of the Web.

### 6.4 Multithreaded xz decoding
- **How (`codec/xz.rs`, on lzma-rust2's public `Lzma2Reader`):**
  - **a scan** reads each stream's footer and index and each block's header, from the end as `xz --list` does, all CRC-checked, and takes each block's LZMA2 dictionary;
  - **workers** decode whole blocks, at most two per worker in flight, and verify each block's check (CRC-32, CRC-64 or SHA-256) and size;
  - **the job thread** writes the blocks out in order.
- **Within `decoder_memory`:**
  - the bound is the number of workers × the dictionary's decoder memory, plus the blocks in flight (the largest block, packed and unpacked);
  - BeeZip takes the most workers that fit, at most one per core, as 7z's LZMA2 decoding already does (M3);
  - at -6 (24 MiB blocks), 16 workers are bounded at 995 MiB and used 863 MiB, inside the default 1 GiB.
- **When:**
  - xz is the outermost layer of a file BeeZip can seek (`.xz`, `.txz`, `.tar.xz`);
  - and the file has two blocks or more: from `xz -T0`, pixz, or BeeZip's own threaded writer.
- **Otherwise one thread, as now,** which also reports any error:
  - one block (`xz -T1`);
  - filters other than LZMA2 alone (BCJ);
  - an index that doesn't read;
  - an xz inside a zip entry, or from a pipe.
- **Speed** (the toolchain's HTML as one 785 MB tar, `xz -6 -T0`, 32 blocks, quiet machine):

  | Threads | 1 | 4 | 8 | 16 | 32 |
  |---|---|---|---|---|---|
  | MB/s | 363 | 1 404 | 2 475 | 3 664 | 3 821 |
  | Peak memory | 56 MiB | 223 MiB | 447 MiB | 863 MiB | 1.03 GiB |

  XZ Utils 5.4.5 (in WSL) takes 1.31 s on one thread and 0.22 s on 16; BeeZip's takes 2.17 s and 0.21 s.
- **Not `XzReaderMt`:**
  - it has no memory limit;
  - it holds whole blocks, and an unbounded queue of finished ones;
  - **it doesn't verify block checks:** a flipped CRC-64 byte decodes "fine" in 0.23 and 0.25, where `XzReader` refuses it. That's a bug for the upstream list.
  - **Speed:**
    - at 16 threads it's level with BeeZip's (3 330–3 866 MB/s, against 3 609–3 664);
    - at 4 and 8 it's faster, with more memory (3 373 MB/s at 8, using 657 MiB, against 2 475 with 447 MiB);
    - PR 2 looks at whether BeeZip's reads ahead too little at low worker counts.

### 6.5 Not in M6
- **zstd decoding:** BeeZip's writer makes one frame whatever the thread count, so there's nothing to split.
- **bzip2 decoding block by block,** as lbzip2 does: it's feasible, but libbz2-rs-sys has no block-level API, so it means bit-shifted copies of each block and handling false matches of the 48-bit block magic (§14).
- **Deflate decoding** (gzip, zip entries): a stream can't be split.
- **Parallel extraction of other formats:** non-solid 7z, cab, rar (§14).

## 7. `bench.run`
- **What it does:** compresses and decompresses a sample in memory with each codec at the levels and thread counts asked for. For each cell it reports:
  - the packed size and ratio;
  - MB/s each way;
  - peak memory each way;
  - the time.

  Each round trip is checked by hash.
- **Input:** `{sample, grid}`.
  - **`sample`** is either a file or BeeZip's built-in sample:
    - **a file** is read as 16 slices spread evenly across it, 8 MiB in all by default (`bytes`), so a big file isn't judged by its start;
    - **the built-in sample** is 8 MiB, seeded: English-like text, JSON and code-like lines, binary tables and 10 % random data.
  - **`grid`** is `default`, `full`, `threads`, or a list of `{codec, level?, threads?}`.
- **Grids:**
  - **default** (about 11 s, estimated from the spike's cells): gzip 1/6/9, bzip2 9, xz 1/6/9, zstd 1/3/9/19, lz4, brotli 5/9, snappy, lzop;
  - **full:** every codec at every level, 113 cells and 108 s on the spike's loaded machine. Brotli 10–11, xz, lzma and lzip at 4 and up, and zstd at 16 and up take most of it.
  - **threads:** zstd 3 and 9, and xz 1 and 6, at 1, 4 and all threads, on a 64 MiB sample. On 8 MiB, xz fits in one block and threads barely show (zstd -3 goes only from 217 to 266 MB/s).
- **Output:** `{sample: {source, bytes}, cpus, cells: [{codec, level, threads, packed_bytes, ratio, compress_mbps, decompress_mbps, compress_mem, decompress_mem, ms}], total_ms, cancelled}`.
  - Cells go out as job events as they finish, so the chart fills in.
- **Memory** is the growth of the process's private bytes during the cell, sampled every millisecond, so allocations in C code count. In the desktop, other jobs running at the same time count too.
- **Cancel:** checked every 256 KiB; a cancelled run returns the cells it finished.
- **Progress:** cells done out of the total, with the current one ("xz -6, all threads, compressing").
- **Front ends:**
  - the CLI: `beezip bench [FILE] [--grid …] [--bytes …]`, which prints a table, or JSON with `--output json`;
  - MCP: `bench_run`;
  - the desktop: a Benchmark dialog, from the palette, for the selected file or the built-in sample.
- **The chart (`BenchChart.tsx`):**
  - ratio upwards and compression MB/s across, on a log scale;
  - a colour per codec, with its levels joined and labelled, and the marker showing the threads;
  - a switch puts decompression speed across, and hovering shows the memory;
  - drawn in SVG by BeeZip, so no chart library joins the bundle or the notices;
  - a table under it has the same numbers, and is what a screen reader reads;
  - its looks wait for the final pass.
- **From the spike's full grid** (compress / decompress, MB/s):
  - **the fast cells:** lz4 483 / 2 105, snappy 716 / 1 206, zstd -1 357 / 994, gzip -1 329 / 718;
  - **the slow one:** BeeZip's lzop writer manages 10 MB/s, to be looked at in PR 2 (§16).

## 8. Desktop

### 8.1 Launches that arrive early
- **The bug:** a second `BeeZip.exe` started while the first is still starting loses its archive. `open::forward` emits `open-paths` as soon as the main window exists, before the page has registered its listener. Explorer starts one process per selected file when several archives are opened at once, so this is easy to hit. The E2E spike lost the first archive in 9 of 10 runs with the second launch 0–800 ms after the first, and in none of 3 at 1 s or more (`target/m6-spikes/e2e/race.ps1`, over CDP, no input).
- **The fix:**
  - forwarded launches go into a queue in managed state;
  - the page drains it with one call once its listener is registered;
  - after that, events go straight through;
  - windows are created only on the main thread, so the forward thread can't race `setup` into making a second, empty main window.
- **The check:** the E2E test opens an archive by a second launch right after the first (§10), as the spike did.

### 8.2 The updater's UI
- **A check at startup,** at most once a day, when `[updates] check = true` (the default; Settings has the switch). It fetches `latest.json` from GitHub Releases and nothing else.
- **A banner when there's an update,** naming the version and linking to its release notes, with "Update and restart". Nothing downloads before that click.
- **While jobs run,** the button waits ("Update when the jobs finish") rather than cancelling them.
- **The About dialog shows the version** and has "Check for updates".
- **The CLI and MCP never check.** `beezip version` prints the version only.

### 8.3 Linux and macOS
- **Hidden off Windows:** the Explorer section of the settings page, and the `shell.*` commands in the palette. `shell.status` already fails there with "Explorer's menu is only on Windows".
- **macOS:**
  - **Opened files** arrive as `RunEvent::Opened { urls }`, not as arguments, so `lib.rs` handles that event the way `forward` handles a second launch.
  - **Quarantine:** extracted files get the archive's `com.apple.quarantine` attribute, as Archive Utility does, so Gatekeeper still checks an app that came in a download. `safefs/quarantine.rs` is `motw.rs`'s counterpart; `[extract] mark_of_the_web` turns both off.
- **Linux:** nothing marks downloads, so there's nothing to carry over.

### 8.4 Drag-out to Explorer (stretch)
- **How 7-Zip does it:**
  - its data object names files in `%TEMP%\7zE…` that don't exist yet;
  - while the button is held it lists only that folder;
  - when it's released over a target that accepts, the target's first `GetData(CF_HDROP)` makes it extract, synchronously;
  - it allows copy and move, so Explorer moves the files out of temp on the same volume;
  - the temp folder goes when `DoDragDrop` returns.
- **BeeZip does the same with its own data object.** The spike's IDataObject and IDropSource (386 lines on windows 0.62.2) compile, and two tests without input pass: only the folder is listed before the release, extraction runs once on the first `GetData` after it, and a refused drop extracts nothing.
- **Not the `drag` crate.** It needs the files to exist before the drag starts, its "data" items are a stub on Windows, it panics when a path can't be turned into an ID list, and it brings a second `windows` (0.52) with eight more crates.
- **In the page:** a `dragstart` on selected rows, an `invoke` that starts `DoDragDrop` on the main thread while the button is held, and BeeZip's own drop handling refusing a drop that comes from itself.
- **Limits:**
  - a selection over 2 GiB (by listed size) doesn't drag: it offers Extract to… instead, since Explorer hangs until the extraction ends, as it does with 7-Zip;
  - a password needed during the drop gets BeeZip's prompt;
  - "move" never removes anything from the archive.
- **Timeboxed:** five days, the last PR. If it isn't solid by then, it's left out and Extract to… stays the way out (PLAN §5).
- **The real drag needs your mouse** (§12).

### 9.2 Signing
- **What Tauri signs:**
  - With `bundle.windows.signCommand`, Tauri 2.12 passes 10 files to the command: BeeZip.exe, the two resources it recognises as code (`bin\beezip.exe` and the shell DLL, signed in place at their source paths), five NSIS plugins, the uninstaller and the setup.
  - **It misses `nsExec.dll`**, which hooks.nsh uses, so a signed installer carries one unsigned DLL, and Smart App Control blocks unsigned code. `xtask dist` signs Tauri's cached copy before the build (`%LOCALAPPDATA%\tauri\NSIS\…`). This is a Tauri bug, for the upstream list.
  - **It doesn't sign the `.msix`,** so `xtask dist` signs it before `tauri build` as now, through the same script, with the publisher as an argument.
  - Every signature is timestamped (`/tr … /td SHA256`), so it stays valid after the certificate expires.
- **`packaging/windows/sign.ps1`** is the one place that signs, chosen by `BEEZIP_SIGN`:
  - `none` (the default): nothing is signed, as now;
  - `dev`: the M4 development certificate (`--sign-dev`, unchanged);

### 9.3 The installer
- **NSIS only.** The MSI spike built (after working around a Tauri bug that packs the renamed shell DLL twice, ICE30), but:
  - Tauri's MSI template is per-machine (Program Files, UAC);
  - it writes 41 associations with no backup of what they were;
  - it adds no PATH entry, and runs none of hooks.nsh.
  - Making it equal would mean WiX fragments with deferred custom actions for `shell install|uninstall`, PATH and the association backup, and a per-machine design of the Explorer registration.
  - Administrators who deploy with Intune can run the NSIS installer with `/S` in the user's context.
- **`bundle.publisher = "Close Consulting, Inc"`** (unset, Apps & features would say "beezip"), the company that signs releases (§9.2), so the signature, Apps & features and winget name the same publisher. Tauri's NSIS writes it as the uninstall entry's Publisher, and keeps the install folder under `HKCU\Software\Close Consulting, Inc\BeeZip`. It's fixed once a release is out: changing it moves that key and breaks winget's match (§9.6). `PublisherDisplayName` in the sparse package's manifest is the same string.
- **A running CLI:** Tauri's `CheckIfAppIsRunning` checks only `BeeZip.exe`. A `beezip mcp` server (Claude Desktop starts one) holds `bin\beezip.exe` open, and the file copy fails. `NSIS_HOOK_PREINSTALL` moves a locked `bin\beezip.exe` aside, to `%TEMP%`, deleted at the next sign-in by `RunOnce`, as M4 does for the DLL. The running server keeps working until its client restarts it.
- **A running BeeZip during `/S` or `/P`** (winget, the updater) is closed without asking (Restart Manager, forced). Interactively, the installer asks, as M4 found. Jobs cut short that way leave their `.beezip-partial` files, as a crash does (M5 §3.8); the updater avoids it by cancelling jobs first (§9.4).
- **A stale `--job` file:** the updater restarts BeeZip with the arguments it had. A `BeeZip.exe --job <request>` whose request file is gone now starts as a plain launch instead of failing.

### 9.4 The updater
- **tauri-plugin-updater 2.14.1:**
  - `bundle.createUpdaterArtifacts` makes a `.sig` for the installer, after Authenticode signing;
  - `plugins.updater.pubkey` holds the public key;
  - the endpoint is `https://github.com/JoshClose/BeeZip/releases/latest/download/latest.json`;
  - `windows-x86_64-nsis` is the platform key;
  - `requireSignedVersion` is on, so a signature made for another version is refused.
- **The key** is a minisign pair from `pnpm tauri signer generate`. The private key and its password are repository secrets (`TAURI_SIGNING_PRIVATE_KEY`, `…_PASSWORD`), set by you (§14). The spike's signature checked out with the plugin's own verifier, and a one-byte change was refused.
- **How it installs:** after checking the download, the plugin runs `on_before_exit`, then starts the installer with `/P /UPDATE /R` ("passive": a progress bar, no questions) and exits the process at once, so `RunEvent::Exit` never runs.
- **What that means for BeeZip:** `on_before_exit` does what `RunEvent::Exit` does now, cancelling running jobs and waiting for their partial files to go.
- **Per-user, so no UAC prompt.** `/UPDATE` installs over the top without uninstalling first, the path M4 tested with `/S`: PREINSTALL (#51's association fix), the files, `APP_ASSOCIATE`, POSTINSTALL (PATH, `shell install` with the new DLL). The per-version DLL needs nothing new.
- **Checked on the Windows 10 VM** (§12): 0.1.0 installed, `beezip mcp` holding the CLI open, a job running, then the update to 0.1.1 from a local `latest.json`; plus a tampered signature and a downgrade, which must install nothing.

## 14. Decisions (taken while planning, 2026-11-07)
Each could reasonably go the other way. Say which to reverse, and I'll change it. The ones marked **(yours)** need you to act, buy or publish; the plan works without them until then.

**Formats**
- **unarc-rs isn't a dependency.** ARJ, ACE and ZOO come from its license-clean modules as BeeZip's code, with their notices; ARC is BeeZip's. The alternatives: the crate whole, with GPL- and LGPL-derived code inside; or ARJ only, through 7-Zip.
- **HA, UC2, JAR, HYP and SQZ aren't read,** nor the Amiga formats, Pack-Ice and the retro disk images unarc-rs reads. The license-clean Amiga LZX, DMS and ADF modules (≈ 2 800 lines) could come in later the same way.
- **ARJ's GOST40 encryption is left out:** its key setup follows GPL ARJ 3.10's, restructured. Garbled ARJs work.
- **ACE 2.0's EXE, DELTA, SOUND and PIC modes are refused** (`UnsupportedOperation`), not decoded, since there's no sample to test them on; acefile has them, so they can follow if one turns up.
- **ARC's PAK-only methods (crushed, distilled) are refused:** unarc-rs's are reverse-engineered from PAK.EXE with its tables copied.
- **XAR and pkg are read by BeeZip's own reader,** read-only, and a pkg is listed expanded, as `pkgutil --expand-full` unpacks it. 7-Zip shows the Payload as one file. Apple Archive payloads stay one file.
- **The 7-Zip backend streams** (`x -so` into FsSink); staging only for NSIS. The alternative, staging everything as PLAN said, is 3–4× slower here and needs the space twice.
- **7-Zip 25.01 or newer, installed by you, never bundled.**
- **The formats in §3.2 are claimed; executables, ELF, Mach-O and Office files aren't,** although 7-Zip opens them.
- **Disk images with several partitions list them as files,** as 7-Zip does; opening one means extracting it.
- **MSI shows 7-Zip's raw view** (cab keys), with a warning. The alternative is a native reader on the msi crate and BeeZip's CAB, which would give real names (not spiked).
- **None of the 7-Zip formats are associated;** Explorer's menu offers BeeZip's items on the image and WIM extensions. `.xar` and `.pkg` are associated.
- **Pseudo entries** (`[SYSTEM]`, `[DELETED]`, `lost+found`) are listed as 7-Zip lists them.
- **Two names that clash only once made safe go to the overwrite policy,** instead of the second silently replacing the first.
- **sevenz-rust2 0.25's new "stop the block at a bad CRC" is undone:** BeeZip checks 7z CRCs itself and carries on to the next entry, as 7-Zip and BeeZip do today.
- **zip, sevenz-rust2 and lzma-rust2 move together in PR 1,** zip to its newest 9.x then. rmcp and the npm packages stay.
- **hadris stays vendored** until a release fixes both patched problems.

**Speed**
- **BeeZip writes its own parallel code,** not gzp, mtzip, the zip crate's `rayon` feature or `XzReaderMt`, each of which lacks something it needs (§6).
- **Scoped threads per job, no rayon** in the shipped build.
  - A job's threads follow `[create] threads` and the new `[extract] threads`.
  - The alternative, a shared rayon pool, would stop two jobs using twice the cores, but it runs blocking file I/O on compute threads.
- **Parallel gzip's output depends only on the level,** not on the thread count; one thread keeps flate2 and today's bytes. The blocks are 128 KiB.
- **Zip entries keep BeeZip's order.** Deflate is split inside an entry only for unencrypted entries of 16 MiB or more.
- **Parallel extraction:**
  - for zips of 64 files or more, with one worker per logical CPU (one on a spinning disk);
  - every decision stays on the job thread;
  - the registry lock is fixed first.
- **Multithreaded xz decoding stays within `decoder_memory`,** for seekable `.xz` files with several blocks.
- **Not in M6:**
  - parallel bzip2 decoding: medium effort, for `.bz2` files only;
  - parallel extraction of formats other than zip.
- **bench.run:**
  - an 11-second default grid;
  - the chart drawn in SVG by BeeZip, with no chart library;
  - in the CLI and MCP too.

### Found while building PR 1
1. **zip 9.4.1 is still the newest 9.x** when PR 1 starts (2026-11-07), so the spike's pins went in as they were. zip master's two security merges (§1) aren't released; they come with the next bump.
2. **The bump** is the spike's diff (§16 "Found while planning" item 1): the three pins, both locks (three packages each), and BeeZip's own 7z CRC check.
   - `SevenZReader::open` keeps each file's CRC and clears `has_crc`, so sevenz-rust2 never checks; `DecodeTag` hashes the entry and fails it with `7z: CRC mismatch` at its end.
   - A CRC mismatch isn't latched: the decoder is sound after it, so the block goes on to the next entry, as 7-Zip does.
   - `push_raw_block` (M5's 7z editing) takes the CRCs from the sub-streams, not from the files, so editing is unchanged.
   - sevenz-rust2 0.25.0 ending the block is on the upstream list (item 22). Item 5, short entries, is fixed in 0.25.0; `DecodeTag`'s length check stays as a second guard.
3. **FsSink's "the same path twice"** now compares archive names, not names made safe. The key (`name_key`) is the entry's path with `\` as `/` and without `.` or empty components, so `./d/f`, `d\f` and `/d/f` are one name, as tar treats them.
   - **Names that meet once made safe:** `trail.` and `trail ` (both `trail_`), and `a:b` and `a_b`, go to the overwrite policy, as case-only clashes did. Before, the second silently replaced the first.
   - **Names that meet once `strip_components` has gone** (`x/f` and `y/f` with 1) go to the policy too, which the plan didn't say. Before, the last one won silently; tar does the same, but a stripped clash loses a file as surely as any other.
   - **Hardlinks** find their target by archive name. Before, a link to `trail ` copied whatever file had taken `trail_`.

### Found while building PR 2
Three parts were built by helpers in worktrees from the plumbing commit, and cherry-picked: multithreaded xz decoding, parallel deflate, and `bench.run`. The zip work, the registry lock and lzop were done in the main session.

1. **The partial-file registry** (§6.3): a mutex over the map of live files, held only to add and remove one, and an `RwLock` on the abandon flag, read-held while a file is created or renamed. `abandon_all` takes it for writing, so every create and rename still lands before it or fails after it, as before.
2. **`[extract] threads`** reaches core as `OpenOptions::threads` and `Source::threads`.
   - The config's default is 0, one per core; core's own default is 1, so library callers and the archive cache read on one thread.
   - `OpenOptions::min_parallel_files` (64) keeps small zips on the job's thread; the tests set it to 1.
   - The settings page has the field beside the other extraction settings.
3. **Parallel zip extraction** (§6.3):
   - **The plan is FsSink's own code.** `FsSink::plan` runs the sink's rules in archive order on the job's thread, so names, folders, collisions, the overwrite policy (prompts included), the report's skips and renames, and `max_entries` are decided exactly as on one thread. `FsSink::write_job` is the write half, shared by the workers; `EntrySink::as_fs_sink` lets the zip reader find it.
   - **Workers decode Store, Deflate, BZip2, Zstd and XZ** with BeeZip's codecs, each reading through its own handle where the local header puts the data. They check the size and CRC with the zip crate's own messages, so errors read the same.
   - **Not as planned: encrypted entries stay on the job's thread,** after the workers, with LZMA, PPMd, Deflate64 and the legacy methods. The plan unlocked the password and gave encrypted entries to workers too. But decrypting means the zip crate's archive, and a worker can't have one of its own without the directory read again, or a reader the crate can clone.
   - **Two entries for one file:** only the last is written. The earlier one is still decoded, checked and counted, so the report and any error match one thread's.
   - **The `newer` policy** compares a later entry with an earlier one's time, since the earlier file may not be on disk yet. That's the time one thread would have found on disk.
   - **Hard links** aren't planned (an error); zips have none.
   - **A spinning disk:** Windows' seek-penalty query on the destination's volume gives one worker, but only when the thread count is left at 0. A count that was set is kept, since a virtual disk may report a seek penalty (the CI runners' may). `safefs/disk.rs` is core's second `unsafe` block: `CreateFileW` on the volume and one `DeviceIoControl`, the answer read through a struct of BeeZip's own so the `BOOLEAN` stays a byte.
   - **Every zip extraction test runs both ways:** the fixtures, the malicious corpus and the round trips compare one worker with four, files and reports. `tests/zip_parallel.rs` adds mixed methods with encrypted entries, duplicates and clashes under every policy, prompts before any data, cancel, both limits, and damage. `format::zip::parallel_extractions()` lets the tests see the workers ran.
4. **Parallel zip writing** (§6.2):
   - `ArchiveWriter::workers` and `add_all` let `ops` hand a writer every entry at once; the zip writer takes them when it has two or more files with data and the zip crate hasn't written anything yet.
   - Each entry is a one-entry zip from the zip crate with BeeZip's options, in memory up to 64 MiB, beyond that in a partial file beside the archive (`ZipWriter::spool_in`).
   - **The bytes are one thread's,** for all six methods, spooled entries included. Past 65 535 entries only the end records differ: BeeZip's Zip64 end record says version 4.5, as APPNOTE asks, where the zip crate says 1.0, and its classic end record gives the directory's size when that fits.
   - **Big entries:** an unencrypted Deflate entry of 16 MiB or more is written by the job's thread, with the zip crate's local header and central record (from the same entry with no data), parallel deflate on every worker, and the CRC and sizes put in. Entries of 3.75 GiB or more would need Zip64 fields inserted into that header, so they stay on one worker; that's a limit the plan didn't have.
   - **Edits that add files** go the same way, after the entries they copy. **Convert stays on one thread:** its entries come decoded, one by one, from the source.
   - **zip 9.4.1 does have parallel compression after all:** `ZipFileBuilder` and `add_prepared_file`, which the planning spike missed. It refuses encryption and holds each entry in memory, so it isn't used.
   - Writing the local data directly, without the one-entry zip (§6.2 "there's room left"), wasn't tried: the copy is what keeps the bytes one thread's.
5. **Parallel deflate** (§6.1; the helper's numbers, a 1.47 GB tar of the toolchain, others' load 6–12 %, MB/s):

6. **Multithreaded xz decoding** (§6.4; the helper's numbers, a 785 MB tar in 32 blocks from `xz -6 -T0`, others' load 3–13 %):

### Found while building PR 3
The listing parser and its fuzz target, the sniffers, and the fixtures were built by helpers in worktrees from the plumbing commit, and cherry-picked; the reader, finding 7-Zip, the commands and the desktop were done in the main session.

1. **Method names are `Cow<'static, str>`** (`Entry.method`, `ArchiveInfo.methods`). 7-Zip's are interned: an archive's entries share a few, so each costs a pointer; at most 256 are kept for the process, past which each entry owns its name.
2. **Finding 7-Zip** (§3.1) tries every candidate in order and takes the first 25.01 or newer, so an old 7-Zip in the registry doesn't hide a new one on PATH. A path set in the settings is the only one tried: falling back would hide that it's wrong. What each program is (its banner, and for a console that isn't 7-Zip's own, whether it takes `-slmu`) is kept per process with its size and time. The registry read is core's third `unsafe` block.
3. **CramFS names:** 7-Zip on Windows reads a CramFS name's bytes in the OEM code page, and its CramFS handler (and its WIM handler) refuse `-mcp`, which its ext handler takes; so a UTF-8 name lists as `bee-≡ƒÉ¥.txt`, and `7z x` writes it so. The parser maps such a name (and a link's target) back through the OEM table to its bytes and reads those as it reads every name (UTF-8 first, then `encoding`), when the listing came from Windows' 7-Zip (its lines end in CRLF); the name 7-Zip printed still selects the entry. 7-Zip for Linux lists the right names.
4. **Links ntfs-3g makes** (Interix links, not reparse points) are listed by 7-Zip as 28-byte files, but `7z x` makes them links. BeeZip extracts what's listed: files holding the Interix bytes. NTFS images made by Windows store reparse points instead, which the spike couldn't make here.
5. **A damaged entry 7-Zip finds after writing it** (a WIM file whose hash doesn't match) is reported on stderr once its data is out. The job then fails naming it, but the file is on disk; BeeZip's own readers check before the file is kept. Testing (`7z t`) reports it as for any format.
6. **`archive.test`** runs `7z t` through a new `ArchiveReader::test`, which `ops::test` uses too; its progress is 7-Zip's `-bsp1` percentage of the listed size. `TestReport.note` and the output's `note` say, for every format but WIM, that the test shows the files can be read, not that they're intact.
7. **`archive.info`** gains `backend`, `levels`, `properties` (13 of the level keys: label, file system, method, images, cluster and sector size, headers size, free space, times, creator, code page, host OS) and `notes` (an MSI's names are its internal keys; a disk 7-Zip stops at lists its partitions as files).
8. **`formats.list`** gains `backend`, `available` and `menu` per format, and `seven_zip` (the one found, where, or why none). The menu's generated extensions take only `menu` formats, and `xtask dist` associates none of the backend's.

2. **ARJ and ACE volume sets** are named the way old RAR sets are (`a.arj`, `a.a01`…; `a.ace`, `a.c00`, `a.c01`…), and opening any part opens the set when its first part is of that format. ARJ's names past `.a99` (`.100`…) are those of a numbered set's parts, so a set of more than 100 volumes isn't found.
3. **Associations:** the existing rule (every format BeeZip reads itself, but documents and what Windows owns) associates `.arj`, `.ace`, `.cba` (ACE comic books, as `.cbz` and `.cbr`), `.zoo`, `.arc`, `.xar`, `.pkg` and `.mpkg`. 4. **ARJ** (`format/arj/`, about 1 600 lines with unarc-rs's header layout, BeeZip's own streaming):

ARJ 3.10's sets read; unarc-rs refused them because it compared the joined size with a field ARJ 3.10 leaves at 0. 6. **ZOO** (`format/zoo.rs`, about 710 lines):

7. **Speed** (`parallel/`; the Rust toolchain's files as the corpora):
   - **Load:** the first runs shared the machine with the other spikes, at 13–85 % load from other processes. The xz, extraction and zip-writing runs were repeated on a quiet machine (1–5 %), where some times halved. PowerShell's performance-counter cmdlets hung on this machine during the reruns; `typeperf` didn't.
   - **gzp's `any_zlib`** (block priming) doesn't compile without C zlib, even with zlib-rs.
   - **zlib-rs's `reset()`** changes the bytes of what's compressed after it (§6.1).
   - **Defender:**
     - the first read of 20 000 freshly copied files took 359 s (56 files a second), the second 1.2 s;
     - extraction writes new files, so per-file cost dominates small files: 1 300–1 600 files a second on one thread, on a quiet machine;
     - parallel workers overlap that cost.
   - **Extraction's numbers moved by up to 20 % between quiet runs** (12.8 and 15.2 s for the same sequential extraction), so §6.3 gives ranges.
   - **AES zips of small files** spend most of their time deriving keys: writing 20 000 files took 14.9 s against 4.6 s unencrypted (quiet), and testing them 18.3 s against 1.1 s (loaded).
   - **The partial-file registry's mutex** serialises parallel workers (§6.3).
   - **lzma-rust2's `XzReaderMt`** returns the data of a block whose check is wrong.
   - **The spike's own xz decoder** at first read each block's check from before the block's padding, so it failed every valid multi-block file. It's fixed, and §10's fixtures cover every padding length.
   - **BeeZip's lzop writer** compresses at 10 MB/s (seen in the benchmark's full grid), to be looked at in PR 2.
   - **mtzip 4.0.3** labels Stored entries Deflate.
   - **Not run:**
     - pigz (not installed here);
     - a byte comparison of the parallel zip with BeeZip's own;
     - bzip2 block decoding;
     - the default bench grid as a whole (its 11 s is summed from the full grid's cells).
