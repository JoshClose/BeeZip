# BeeZip — M5 (Editing + breadth) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M4.md`](M4.md) and keeps their decisions, except where §13 corrects PLAN.md. Versions, licenses and release dates were checked on 2026-11-06 against crates.io and GitHub. The APIs named here were checked in the sources of zip 9.2.2 (and 9.4.1, for the bugs in §16), sevenz-rust2 0.24.2, tar 0.4.46, open 5.4.5 and the format crates in §1.

Spikes on this machine back the plan; §16 "Found while planning" has their results. These change what PLAN says:
- **The zip crate's raw copy is broken.** `raw_copy_file` drops the encrypted flag of ZipCrypto entries and the end-of-stream flag of LZMA entries, so the copies are corrupt; `new_append` drops the LZMA flag from the entries it keeps. Both are still there in 9.4.1. BeeZip copies zip entries itself, byte for byte (§3.3).
- **sevenz-rust2 0.24.2 can copy a 7z block without decoding it** (`push_raw_block`), renaming its entries on the way. So 7z edits copy every block they don't change, as 7-Zip does (§3.4). PLAN assumed 7z edits would recompress.
- **#54 is the zip crate's overlap check.** Opening the million-entry zip takes 5.2 s in core, and 4.6–5.0 s of it is `has_overlapping_files`, which reads every local header through a 64 KiB buffer it throws away on each seek. Reading the headers in file order does the same check in 35 ms (§4).
- **Most of PLAN's format crates aren't usable as they are.** `cab`, `ar`, `rpm`, `udif` and backhand's reader panic, or allocate gigabytes until the process aborts, on small crafted files; `cpio` reads two of its five variants; `cab` takes minutes for what 7-Zip does in a second. So cpio, ar, deb, RPM, CAB, `.Z`, the lzop container, the squashfs reader and the DMG container are BeeZip's own, on the codecs it already has (§5). The crates kept are delharc (LHA), lzokay (LZO blocks), lzxd (CAB's LZX), hadris-iso and hadris-udf 3.0 (ISO, and the UDF that Windows ISOs need), backhand (writing squashfs) and fstool (HFS+ and APFS inside DMGs).
- **deb is read-only**, shown as `dpkg-deb -R` unpacks it; PLAN had it writable.

## Scope
- **Editing** (`beezip-core` and `beezip-commands`):
  - `archive.add`, `archive.remove` and `archive.rename` (Destructive), and `archive.convert` (Writes). Each writes a new archive beside the old one and swaps it in (§3.1).
  - Raw copies: entries that don't change are copied as they are, without decoding: zip entries, 7z blocks, tar, cpio and ar members. This is PLAN's `add_raw_from` (§3.2).
  - `FormatCaps` `append`, `delete` and `rename` come on for the formats BeeZip edits (§3.9).
  - `entry.open` (Writes, hidden from MCP): an entry extracted to a temporary folder and opened with its default app (§7.6).
- **Formats** (PLAN §2): CAB, ISO 9660 with Joliet and Rock Ridge, cpio, ar and deb, RPM (read only), LHA/LZH (read only), Unix `.Z`, lzop, squashfs and DMG. §5 has each one.
- **Filename encodings:** names stored as bytes in a legacy code page (zip without the UTF-8 flag, tar, cpio, LZH…) decode with a chosen encoding: "auto", UTF-8, or one of the common code pages (§6).
- **The zip reader** is reworked for raw copies, and opens a million entries in under a second (#54, §4).
- **Desktop:** adding, deleting and renaming in the browser; dropping files on an open archive adds them (M3 offered a new archive); opening an entry with its app, and offering to update the archive when it changes; converting; the name encoding per tab (§8).
- **Explorer:** "Add to "a.zip"" when `a.zip` exists can add to it (M4 §14, §9).

**Out of scope:**
- **Not edited:** volume sets (`a.7z.001`…) and self-extracting archives; BeeZip refuses and offers `archive.convert` (§3.7). RAR is never written. The images (ISO, squashfs, DMG) and CAB are created, not edited (§3.9).
- **M6:** the `SevenZipCli` backend, `unarc-rs`, XAR, the benchmark, production signing, the updater, drag-out, the tauri-driver E2E test.
- **Not planned:** guessing a name encoding from the bytes (§6); editing several renames in one call (§7.3); preserving an APK's signing block or other bytes outside a zip's entries (§3.3).

## 3. Editing (`beezip-core`)

### 3.1 The safe rewrite
Nothing writes into an archive. Every edit writes a new one beside it and swaps it in:

1. **Check** the archive (`ops::edit`):
   - its canonical path: an archive reached through a symlink is edited at its target, and the link stays;
   - the format can be edited (§3.9), and it isn't a volume set or an SFX (§3.7);
   - it isn't read-only: `Io`, "a.zip is read-only; nothing was changed". A rename can't replace a read-only file (checked, §16).
2. **Stamp it:** its size, modified time and creation time.
3. **Write** the new archive to `.<name>.<random>.beezip-partial` in the same folder, through `Partial` (M3 §3.7), so the swap is a rename on one volume.
4. **Carry over** what belongs to the file rather than its contents:
   - the `Zone.Identifier` stream (Mark of the Web), through `motw`;
   - the hidden, system and not-indexed attributes, set when the partial is created (`OpenOptionsExt::attributes`);
   - the creation time (`FileTimesExt::set_created`).
5. **Check the stamp again.** If the archive changed meanwhile (another program wrote it), the edit fails with `Conflict`, "a.zip changed while BeeZip was editing it; nothing was changed", and the partial is deleted.
6. **Swap** with `Partial::persist`, std's `rename`.
   - **Our own handles don't block it:** std opens files with `FILE_SHARE_DELETE`, and Rust 1.99's rename replaces a file held that way. The holder keeps reading the old bytes (checked, §16). So the archive cache (M3 §4.2) and an open preview don't get in the way.
   - **Another program's handle can:** one opened without `FILE_SHARE_DELETE` makes the rename fail with `ERROR_ACCESS_DENIED`. BeeZip retries for 2 s, for scanners that let go quickly, then fails with `Io`, "a.zip is open in another program; nothing was changed".
7. **Afterwards:** the cache drops the archive's reader and listings (§7.7).

**What isn't kept:** permissions set on the file itself (the new file inherits its folder's, like any new file); other names of a hard-linked archive, which keep the old contents; alternate data streams other than `Zone.Identifier`.

**Disk space:** the new archive needs room beside the old one. A full disk fails the write, and the partial is deleted.

### 3.2 The edit plan
Core gets one entry point for all three edits and for convert:

```rust
/// One entry of the archive being written.
pub enum Item {
    /// An entry of the source, under `path`: its own, or a new name.
    Keep { id: usize, path: String },
    /// A file, folder or link from disk, as `ops::plan` finds them.
    New(Planned),
}

/// Writes `items` from `source` to a new archive at `target` (`ops::edit` for the three edits,
/// `ops::convert` for a new file).
pub fn rewrite(source: &mut dyn ArchiveReader, items: &[Item], spec: &WriteSpec, cx: &mut dyn Ctx) -> Result<RewriteReport>;
```

- **Raw copies:** `ArchiveWriter` gains
  ```rust
  /// Copies whichever of `keep` it can without decoding them, from `source` when that is a
  /// reader of its own format. Returns the ids it didn't copy; `rewrite` decodes those and
  /// adds them through `add`.
  fn copy_from(&mut self, source: &mut dyn ArchiveReader, keep: &[Keep], cx: &mut dyn Ctx) -> Result<Vec<usize>>;
  ```
  with a default that copies nothing. `ArchiveReader` gains `as_any_mut()`, so a writer can find its own format's reader behind the trait object.
- **Why not PLAN's `add_raw_from(reader, id) -> bool`:** 7z copies whole blocks, which one entry at a time can't say.
- **Order:** kept entries in the source's order, then new ones in `ops::plan`'s order. A replaced entry is dropped from the kept ones, and its new version goes with the new ones.
- **Decoding for re-encoding** uses the reader's `extract`, in archive order, so a solid source decodes once. A writer that packs solid blocks (7z) pulls entries; it gets them through a helper thread and the bounded pipe 7z's `open_entry` already uses (M3 §3.3).
- **Sizes:** `NewEntry.size` comes from the source's `Entry.size`. An entry whose size isn't known in advance (a bare stream) is spooled to a temporary file first, under the usual limits.
- **CRCs:** raw copies aren't checked, as in 7-Zip (`archive.test` checks them). Decoded entries are, and a failure fails the edit with nothing changed.

### 3.3 Zip
BeeZip copies zip entries itself, because the zip crate's copies are corrupt for ZipCrypto and LZMA entries (§16).

- **Spans:** the reader's scan of the local headers (§4) records each entry's span: its local header, data and data descriptor. The descriptor is there when flag bit 3 is set: an optional `PK\7\8`, then the CRC and two sizes of 4 bytes each, or 8 when the local header has a Zip64 extra.
- **A kept entry:**
  - its span is copied byte for byte;
  - its central-directory record is copied byte for byte, with the local header's offset changed: in the 32-bit field, or in its Zip64 extra. When the new offset needs 64 bits and the record has no Zip64 offset, a Zip64 extra is added or extended.
  - So unknown flags, extra fields, comments, data descriptors and both kinds of encryption survive.
- **A renamed entry:**
  - the local header and the central record get the new name in UTF-8, with flag bit 11 set;
  - the Info-ZIP Unicode Path extra (`0x7075`) is dropped from both, since it would override the new name; the other extra fields stay;
  - encrypted entries rename without a password: neither ZipCrypto nor AES covers the name.
- **New entries** are written by the M1 writer (the zip crate's `ZipWriter`, same options) into the same output, through a view that offsets its positions. So their data is written once. When it finishes, its central directory is read back and merged with the kept records. The merged directory overwrites it, and the file is cut to length.
- **The end:** the archive comment is kept. Zip64 end records are written when the entry count, an offset or the directory size needs them.
- **Not kept:** bytes outside the entries and the central directory, such as an APK's signing block (editing an APK breaks its signature anyway) or data before the first entry.

### 3.4 7z
- **Blocks whose entries all stay** are copied with sevenz-rust2's `push_raw_block`, renamed through its callback. Encrypted blocks are copied without decrypting them.
- **Entries without data** (empty files, folders) are written again with `push_archive_entry`, keeping their times and attributes.
- **A block that loses an entry,** or holds one being replaced, is decoded, and the entries it keeps are encoded again into new blocks, with the edit's method and level (§7.1). A block that was encrypted is encrypted again, with the password that decoded it. 7-Zip does the same.
- **New files** become new blocks, as `archive.create` makes them (`add_solid`).
- **The header** is encrypted again when it was, with the password the archive was opened with.
- **Checked in the spike:** solid, non-solid, BCJ2 and header-encrypted archives from 7-Zip 26.00, every block copied raw with one entry renamed; `7z t` passed each one (§16).

### 3.5 Tar
- **Spans:** with `Entries::raw(true)` (tar 0.4.46), every header comes back with its position, the pax (`x`, `g`) and GNU long-name (`L`, `K`) records included. An entry's span runs from its first extension header to the end of its padded data.
- **A kept entry:** its span is copied as it is. Global pax headers stay where they are.
- **A renamed entry** gets a pax header of BeeZip's with `path` set to the new name, followed by the entry's other pax records; its ustar header's name field is set to an ASCII stand-in and its checksum recomputed. A GNU long-name record it had is dropped.
- **Hard links:** renaming a link's target renames the target in its links (`linkpath`). Removing a target that a kept link points to fails with `Conflict`, naming the links: remove them too, or extract and create the archive again.
- **Under a codec** (`.tar.zst` and the rest), the stream is decoded once and encoded again, at the config's level for that codec: the stream doesn't record the level it was made with. The tar inside is still copied entry by entry, so nothing is re-read.
- **Kept as they are:** GNU sparse files, multi-volume tar parts, devices and FIFOs, and anything else the reader lists as `Other`.

### 3.6 cpio, ar and the general case
- **cpio and ar** members are contiguous (header, name, data, padding), so kept members are copied as they are, and a rename writes a new header (§5).
- **Every other case** decodes the entry and adds it through `ArchiveWriter::add`: entries of a block or stream that must be re-encoded, and `archive.convert` between different formats (§7.5).

### 3.7 Encrypted, solid, volume sets, SFX
- **Encryption is never dropped by an edit.** Raw copies keep it without a password; re-encoded 7z blocks are encrypted again (§3.4).
- **New entries in an encrypted archive:**
  - when the archive has encrypted entries and the edit adds some, it asks `Ctx::password` for the new entries' password. The CLI prompts, the desktop shows its password prompt, and MCP returns `PasswordRequired`;
  - `unencrypted: true` adds them in the clear instead, and the output says so;
  - a 7z with encrypted headers uses its header password for the new blocks too.
- **Passwords for removing and renaming:** none, except for a 7z whose header is encrypted (to read the names, as listing does) and for 7z blocks that must be re-encoded.
- **Solid archives:** a 7z edit re-encodes only the blocks it changes; a compressed tar is re-encoded whole. The output's `recompressed` count says how much was.
- **Volume sets are refused:** `UnsupportedOperation`, "a.7z.001 is split into volumes, and BeeZip doesn't edit split archives. Convert it to one file (`beezip convert`), or extract it and create it again." A set can't be swapped atomically, since it is several files and the number of parts can change, and 7-Zip refuses too.
- **SFX archives are refused** the same way: their stub would have to be kept, and a signed one breaks anyway.
- **RAR and the read-only formats:** `UnsupportedOperation`.

### 3.8 Cancelling and failing
- **Before the swap,** a cancel or an error drops the `Partial`, which deletes it. The archive is untouched. The CLI's second Ctrl+C deletes it through `partial::abandon_all`, as for create.
- **The swap** is one rename, and isn't interrupted: cancellation is checked before it.
- **A crash** can leave `.a.zip.<random>.beezip-partial` beside the archive, as an interrupted create does.

### 3.9 Caps

| Format | Add | Remove | Rename | How |
|---|---|---|---|---|
| zip | ✓ | ✓ | ✓ | kept entries copied byte for byte |
| 7z | ✓ | ✓ | ✓ | whole blocks copied; changed blocks re-encoded |
| tar, and tar under every codec | ✓ | ✓ | ✓ | entries copied; a codec's stream re-encoded |
| cpio, ar (deb) | ✓ | ✓ | ✓ | members copied |
| CAB, ISO, squashfs, DMG | – | – | – | created, not edited |
| RAR, RPM, LHA | – | – | – | read only |

Volume sets and SFX archives are refused when the command runs (§3.7), since their caps are their format's.

## 4. The zip reader (#54)
- **Measured** (release build, the million-entry `target/bigzip.zip` from `cargo xtask bigzip`, a copy of core with timers):

  | Step | Time |
  |---|---|
  | `ZipArchive::with_config` (the central directory) | 0.24 s |
  | `has_overlapping_files` | 4.6–5.0 s |
  | `central_times` (the directory again, for the times) | 0.06 s |
  | the loop building `Entry`s | 0.46 s |
  | **in all** (`open` → `entries`) | **5.2–5.8 s** |

- **Why the overlap check is slow:** it asks each entry's data start, which seeks to its local header. Each seek empties the 64 KiB `BufReader`, which refills it, so a million entries read about 64 GB from the cache.
- **The new check:** BeeZip reads the local headers itself, in file order, through a reader that seeks forward within its buffer. That gives each entry's exact data range, so the check is the same, and the spans editing needs (§3.3) come with it. In the spike it took 35 ms for the million entries.
- **The entry loop:** the DOS time is worked out only when there's no NTFS or Unix time, and a name that is valid UTF-8 isn't copied twice.
- **The aim:** under 1 s to open the million-entry zip in core, measured by an ignored test (`cargo test --release -- --ignored bigzip`) and recorded in §16. The desktop's first rows add the folder tree, about 0.45 s (M3 §11 #54).

## 5. Formats
The crate checks are in §16 "Found while planning". Of the nine crates PLAN names, M5 keeps four: delharc for LHA, lzokay for LZO blocks, hadris-iso for ISO (3.0, with hadris-udf beside it), and backhand, for writing squashfs only. Two are new: lzxd for CAB's LZX, and fstool for the volumes inside DMGs. Everything else is BeeZip's own: the crates panic or abort on crafted input, cover too few variants, or don't stream, and the formats are small enough. Each in-house reader bounds every size and count it reads before allocating, since an allocation that fails aborts the process (`catch_unwind` can't catch that).

### 5.1 Ids, detection, extensions

| ar | `Ar` | `!<arch>\n` | `.ar` (`.a` and `.lib` open by content, but aren't claimed: they're build files) |
| deb | `Deb` | an ar whose first member is `debian-binary` | `.deb`, `.udeb` |
| RPM | `Rpm` | the lead's `ED AB EE DB` | `.rpm` |

| LHA | `Lzh` | `-lh?-`/`-lz?-`/`-pm?-` at offset 2 with a valid header checksum; LHA SFX through the overlay scan | `.lzh`, `.lha` |
| ISO | `Iso` | `CD001` at 32 769 (and 34 817, 36 865); UDF's `BEA01`/`NSR02`/`NSR03` | `.iso` |

- **Compound names:** cpio also opens and writes under every tar codec (`.cpio.gz`, `.cpio.zst`…), as initramfs images are. `ArchiveKind` gains `Cpio(Option<CodecId>)` beside `Tar(..)`.
- **The two new codecs** join `TAR_CODECS`, `stream.compress`/`stream.decompress`, the codec fuzz target and `formats.list`.

### 5.2 cpio (in-house, read and write)
- **Reading** (about 400 lines), from a plain `Read`, so `.cpio.gz` needs no spooling:
  - newc (`070701`), crc (`070702`, whose checksum is checked), odc (`070707`, bsdcpio's default), old binary in both byte orders, and RPM's `07070X` large-file headers;
  - hard links: in newc and crc, the members that share an inode carry the data in the last one, so every member of a group is a `Hardlink` to the one with the data; in odc and binary, each carries its own data;
  - names as bytes, through §6; the `TRAILER!!!` member ends the archive, and anything after it is ignored.
- **Writing** (about 120 lines): newc. A file of 4 GiB or more can't be stored in it and fails with `InvalidArgs`, before anything is written.
- **Editing:** members are copied as they are; a renamed one gets a new header (§3.6).
- **Not used:** the `cpio` crate (0.4.2): robust, but it reads only newc and crc, takes only UTF-8 names, and its writer finishes a short entry without an error (§16).

### 5.3 ar and deb (in-house)
- **ar, read and write** (about 300 lines):
  - GNU (`//` name table, `/` symbol table, `/SYM64/`) and BSD (`#1/<len>` names, `__.SYMDEF`) archives. Symbol tables are skipped, not listed. Thin archives are refused (`UnsupportedFormat`): their members are other files.
  - Writing uses GNU's form: names over 15 bytes go in a `//` table at the start, which is possible because `ops::plan` knows every name before the first is written.
  - Editing: members copied as they are, as for cpio.
  - **Not used:** the `ar` crate (0.9.0, 2021). Files under 200 bytes make it ask for 9–16 GB, which aborts, and its fixes since 2022 are unreleased (§16).
- **deb, read only:**
  - **The listing** is the one `dpkg-deb -R` unpacks: `data.tar.*`'s contents at the top, and `control.tar.*`'s files under `DEBIAN/`. `debian-binary` isn't listed. Both tars go through the codecs (gzip, xz, zstd, bzip2, lzma or none) in one pass over the ar, in its order.
  - **Why not the ar members:** 7-Zip's default view goes into `data.tar` too, and a package's files are what people open one for.
  - **Not written:** building a package is `dpkg-deb`'s job; it checks the control fields, which BeeZip wouldn't know about. PLAN had deb as writable.

### 5.4 RPM (in-house, read only)
About 350 lines in all: the spike's 204-line parser plus the payload.
- **The lead and the signature header** are skipped: their sizes are read and checked; signatures aren't verified.
- **The header** gives the listing without touching the payload: file names (`BASENAMES`, `DIRNAMES`, `DIRINDEXES`), sizes (`FILESIZES`, `LONGFILESIZES`), modes, times, link targets (`FILELINKTOS`), and `PAYLOADCOMPRESSOR`. Every index entry's offset, count and type is checked against the data before use.
- **The payload** is a cpio (§5.2) under gzip, bzip2, xz, lzma or zstd, streamed through the codecs. Extracting decodes it once, so RPM has no random access.
- **Not used:** the `rpm` crate (0.30.2). With no default features it adds 33 crates to core, it panics or allocates up to 17 GB on about 9% of mutated headers (fixes are in open PRs), and its payload API returns each file as a `Vec` (§16).

### 5.5 CAB (in-house, read and write)
About 900 lines, on `lzxd` for LZX and flate2 for MSZIP.
- **Reading:**
  - none, MSZIP and LZX (through `lzxd` 0.2.7). Quantum is refused (`UnsupportedFormat`), as the crate does.
  - MSZIP blocks are raw deflate whose dictionary is the block before; flate2 1.1.10's `Decompress::set_dictionary` exists with zlib-rs.
  - Reserved header fields; cabinet sets, by following the next cabinet's name to a file in the same folder, so a file split across cabinets reads whole.
  - Names: UTF-8 when the attribute says so, otherwise through §6 (the ANSI code page). Times are local, as CAB stores them.
  - Extraction decodes each folder once, in order.
- **Writing:** none and MSZIP (`method`: `store` or `mszip`, default `mszip`). A new folder starts before 65 535 blocks. A cabinet over 2 GiB fails with `InvalidArgs`. Writing sets isn't offered.
- **Not used:** the `cab` crate (0.6.0, 2024). Extracting 2 000 files from one folder took 289 s, since every file decodes its folder from the start. It can't open sets, loses non-UTF-8 names, panics on bad input, and its writer needs every name before any data (§16).

### 5.6 LHA/LZH (delharc, read only)
- **The crate:** delharc 0.8.0 with `lhx` and `no-unsafe-assertions` (which turns its unchecked bounds hints into checks). It reads lh0, lh1, lh4–lh7, lhx, lzs, lz4, lz5, pm0–pm2 and directories, with header levels 0–3, from a plain `Read`.
- **What BeeZip adds:**
  - names from the raw bytes (the name field, and extended headers `0x01`/`0x02`) through §6, since delharc's own paths escape non-ASCII and split Shift-JIS names at a `0x5C` trail byte. The UTF-16 name headers `0x44`/`0x45` win when present;
  - symlinks (`-lhd-` with `S_IFLNK` and `name|target`), which delharc reports as directories;
  - the CRC-16, checked through `crc_check()` at each entry's end;
  - times converted to `SystemTime`;
  - LHA SFX executables, through the overlay scan.
- **Compared with 7-Zip** on 255 archives, delharc decoded the 58 that 7-Zip fails on (lh1, lz*, pm*, some level-3 headers), matching their expected CRCs.

### 5.7 Unix `.Z` (in-house codec)
- **The code** (about 420 lines, in the spike): a decoder as a `Read` with about 320 KiB of fixed memory, and an encoder as a `Write` with compress's rule for when to clear the table.
- **Checked:** libarchive's 49 `.Z` files decode the same in it, 7-Zip and gzip; its output at every code width up to 16, in block and non-block mode, decoded in gzip and in its own decoder.
- **Writing:** 16-bit block mode, with no levels, as `compress` writes by default. 161–200 MB/s to encode, 274–299 MB/s to decode.
- **Not used:** weezl, which handles 12-bit LZW only; compcol 0.7.8, whose `.Z` decoder fails when the padding after a CLEAR is split across reads (§16).

### 5.8 lzop (in-house container, lzokay for the blocks)
- **The container** (about 330 lines): the header (versions, method, level, flags, mode, times, name, header checksum), then blocks of uncompressed and compressed lengths, their Adler-32 or CRC-32 checksums, and the data, until a zero length. Concatenated members are read one after another.
- **The blocks:** lzokay 2.0.1 (pure Rust since 2.0.0) compresses and decompresses LZO1X. Its output is LZO1X-999's kind, so new files say method 3, level 9.
- **Checked against liblzo2** (WSL's, through ctypes): libarchive's lzop files, made by lzop 1.03, decode the same; liblzo2's LZO1X-1 and -999 output reads here, and this output reads in `lzo1x_decompress_safe`, 51 of 51 each way.
- **Speed:** lzokay compresses at 10–24 MB/s, slow beside lzop's LZO1X-1, which is what lzop is chosen for. Decompression runs at 345–1970 MB/s. A faster LZO1X-1 compressor of our own (about 250 lines) is a follow-up, not M5.
- **Bug worked around:** lzokay compresses an empty block to 4 bytes that every decoder rejects; BeeZip writes no block for empty input.

### 5.9 ISO 9660, Joliet, Rock Ridge and UDF (hadris-iso 3.0)
- **The crates:** hadris-iso and hadris-udf, `=3.0.0-rc.3` today. 3.0's API replaces 2.5's entirely; 2.5's branch gets only security fixes, and its writer duplicates a relocated folder in the Joliet tree and ignores the files' times. PR #350 says the breaking changes ship in rc.4 "before the API freezes". PR 5 is the last of M5, so it pins the newest 3.0 then (the final if it's out), and the adapter stays in `format/iso.rs`.
- **Reading** from any `Read + Seek`:
  - the tree comes from Rock Ridge, else Joliet, else the primary names (`Namespace::Preferred`), with Rock Ridge's relocated folders put back, multi-extent files joined and `;1` versions hidden;
  - **UDF:** when the volume has UDF's NSR descriptors and its tree has more entries than the ISO 9660 one, the UDF tree is listed. That is how Windows ISOs work: their ISO 9660 tree is empty. hadris-udf read Windows 10's ISO (993 entries, 4.9 GB) in 2.7 s, every file matching 7-Zip's;
  - folders already visited are skipped, since a crafted image can make a cycle;
  - zisofs-compressed files are listed, and extracting one is `UnsupportedOperation`, as in 7-Zip;
  - El Torito boot images aren't listed in M5.
- **Writing** ISO 9660 level 3 (files of 4 GiB and more in several extents) with Joliet and Rock Ridge:
  - files more than 8 folders deep are relocated, as Rock Ridge does; Joliet names are cut to 64 characters, and characters outside the BMP become `_`. hadris's warnings become the job's warnings;
  - hadris takes file data from bytes or host paths (`hadris_fs::host::file`), not from a `Read`. So `NewEntry` gains `source: Option<PathBuf>`, the file `ops::plan` found, and the ISO writer hands hadris paths. hadris opens each one only to measure it, then again while writing its data, one at a time (checked: with 2 000 files, never more than three open at once), and fails with `Corrupt` if a file's length changed. Entries with no file behind them (convert) are spooled to temporary files beside the output first;
  - **a patched copy of hadris-iso,** in `vendor/hadris-iso/` through `[patch.crates-io]`. Its name de-duplication retries every suffix for every colliding name, so 20 000 files whose long names share a prefix take 80 s to plan, at any ISO level, and no option or API avoids it (the primary names come from the same names as Joliet's and Rock Ridge's). The fix remembers the next suffix per name: 8 lines, after which the same tree plans in 0.12 s and `7z t` passes. The patch goes when upstream has the fix.
- **Not used:** `cdfs` doesn't build on Windows; `iso9660` calls itself incomplete; `isomage` lists Windows' ISO as empty and has no times or modes.

### 5.10 squashfs (in-house reader, backhand writer)
- **Reading** (in-house, about 1 000–1 500 lines): the superblock, the id, inode, directory, fragment and export tables, and block lists, through the workspace's codecs: gzip (flate2), xz and lzma (lzma-rust2), lzo (lzokay), lz4 (lz4_flex) and zstd.
  - names as bytes through §6;
  - hard links from inode numbers;
  - xattrs ignored;
  - a small cache of decoded fragments, not one per fragment for the reader's life;
  - every table size and block count checked against the image before use.
- **Why not backhand's reader:** on Windows a name that isn't UTF-8 panics, and a name with `\` fails the whole image; a symlink target of 256 bytes or more fails it everywhere; a 12 KB crafted image makes it allocate 1 GiB from a block count, which aborts; and its fragment cache is never trimmed (§16). It also hides inode numbers, so hard links can't be told apart.
- **Writing** with backhand `=0.25.5`, `default-features = false, features = ["error-strings"]`:
  - its compressors are BeeZip's, through backhand's `CompressionAction`, so no C liblzma and no second zstd wrapper are built;
  - `method`: `gzip` (the default, as mksquashfs's), `xz`, `zstd`, `lz4` or `lzo`. 7-Zip 26.00 can't read lz4 squashfs at all, `mksquashfs`'s own included;
  - backhand keeps every file's reader until it writes, then reads them one by one. So each reader it gets opens `NewEntry.source` (or a spooled file) on its first read and closes it at the end, and one file is open at a time (checked with 20 020 files);
  - its duplicate-file detection is off (`set_no_duplicate_files`): it compares only sizes and a 64-bit hash, and leaves stale bytes after the image's end (§16);
  - BeeZip writes the compression options itself; backhand writes gzip's as 7 bytes instead of 8, which unsquashfs rejects (§16).
- **License:** backhand needs `xxhash-rust`, which is BSL-1.0 (permissive, OSI-approved), so `deny.toml` gains a per-crate exception for it.

### 5.11 DMG (in-house UDIF, fstool for HFS+ and APFS)
A DMG has two layers: UDIF, the container of compressed chunks, and the disk inside it, usually an HFS+ or APFS volume. BeeZip lists the files in the volume, as 7-Zip does by default.

- **UDIF, in-house** (about 600 lines):
  - the `koly` trailer, then the plist's `blkx` tables (base64 `mish` blocks, read by a small bounded scanner of the plist's XML rather than a general plist parser), every count and length checked against the file before use;
  - chunks of zlib (flate2), bzip2, LZFSE (`lzfse_rust`), LZMA (lzma-rust2), ADC (in-house, about 60 lines), raw and zero-fill;
  - the disk is a `Read + Seek` that binary-searches the run holding a sector and decodes that chunk, with a cache of 16 decoded chunks. One cached chunk made a bzip2 image take 6.7 s; four took 0.54 s;
  - **encrypted images** (`encrcdsa` at the start, `cdsaencr` at the end) are refused with `UnsupportedFormat`, "encrypted disk images aren't supported";
  - **sparse images** (`.sparseimage`, `.sparsebundle`) aren't in M5.
- **The volume, through fstool** `=0.5.2` with only `hfs-plus` and `apfs`:
  - BeeZip's UDIF disk goes in through fstool's `BlockDevice` trait (about 15 lines: the reader, a `Write` that fails, 512-byte blocks). fstool's own DMG layer isn't used: it caches one chunk, so 10 000 files took 25 s through it and 0.18 s through ours, and its chunk size cap is 8 GiB;
  - the partition map (GPT, APM or none) is found with `detect_partition_table`; HFS+, HFSX and APFS (its first volume) are read with `AnyFs::open`, `list`, `getattr`, `open_body_reader` and `read_symlink`;
  - **Apple-compressed files** (decmpfs): fstool reads their header in the wrong byte order and fails them. BeeZip reads the `com.apple.decmpfs` attribute (`get_xattr`) and the resource fork (fstool's catalog and fork readers) and decodes them itself: zlib, LZVN (in-house, about 150 lines) and LZFSE, inline or in the resource fork. In the spike, the 9 files fstool failed on in a real DMG decoded this way and matched 7-Zip's;
  - with no HFS+ or APFS volume, the partitions are listed as entries, as `7z -tdmg` lists them;
  - HFS+'s private-data folder is listed as `[HFS+ Private Data]`, as 7-Zip shows it.
- **Writing** an HFS+ volume with fstool's writer (`HfsPlus::format`, `create_dir`, `create_file` from a `Read` with its length, `create_symlink`, `flush`) into a temporary file beside the output, sized up front from `ops::plan`'s entries. BeeZip's UDIF writer then compresses it in 1 MiB zlib chunks (UDZO), the format `hdiutil` uses by default. In the spike, fstool's image of a Unicode tree with a symlink and an executable passed `7z t`, with every hash matching.
- **Checked on a Mac in CI:** nobody here has one, so a macOS job mounts what BeeZip writes (§10).
- **Not used:**
  - `udif` 0.4.2: it gives a partition only whole or as one stream, has no ADC, and three header fields make it allocate until the process aborts;
  - dpp's `hfsplus` and `apfs`: self-linked nodes hang one and overflow the other's stack;
  - `apple-dmg`, `dmgwiz` (C code and OpenSSL), `lzfse` (C), and `fs-mac`, which is GPL through `fs-mac-unicode`.
- **The risk:** fstool has one author and 49 releases in five months. The calls BeeZip makes changed incompatibly twice in its history, so it's pinned exactly behind `format/dmg.rs`, which is the only file that names it.

### 5.12 Associations and the Explorer menu
- **File associations** (`xtask dist`, from `formats.list`) gain the new extensions except `.iso` and `.cab`, which Windows opens itself: it mounts ISOs and shows cabinets as folders, and taking those over would surprise people. `.a` and `.lib` aren't extensions of any format, so they're never associated.
- **The Explorer menu's archive items** cover every new extension, `.iso` and `.cab` included ("Extract here" on an ISO is useful). `xtask codegen` regenerates `gen_exts.rs`.
- **The Explorer menu's add items** stay zip, 7z and tar.zst.

## 6. Filename encodings
- **Where names are bytes:** zip entries without the UTF-8 flag or a Unicode Path extra, tar names outside pax records, cpio, ar, LHA, CAB entries without the UTF-8 attribute, ISO names outside Joliet, and squashfs. 7z, RAR, Joliet, UDF, HFS+ and APFS store Unicode, so the encoding doesn't apply to them.
- **"auto"** (the default):
  - names marked as UTF-8 are UTF-8;
  - a name that is valid UTF-8 is read as UTF-8: macOS and Linux tools often leave the flag off;
  - otherwise, zip names are read in the system's OEM code page, as Explorer and 7-Zip read them (437 on a US system, 850 in Western Europe, 932 in Japan). Other formats use the ANSI code page. Off Windows, both are 437 and Windows-1252.
  - The code pages come from `HKLM\SYSTEM\CurrentControlSet\Control\Nls\CodePage` (`OEMCP`, `ACP`), read by `beezip-commands` through windows-registry, so no unsafe code is needed.
- **A chosen encoding** applies to every name not marked as UTF-8. The choices are an enum (`NameEncoding`, so MCP and TypeScript see the list): `auto`, `utf-8`, `cp437`, `cp850`, `cp852`, `cp866`, `cp874`, `cp932` (Shift-JIS), `cp936` (GBK), `cp949`, `cp950` (Big5), `cp1250`–`cp1258`, `koi8-r`, `koi8-u`, `iso-8859-1`, `iso-8859-2`, `iso-8859-5`, `iso-8859-7`, `euc-jp` and `gb18030`.
- **Inputs:** `encoding` on every command that reads names: `archive.list`, `archive.info`, `archive.test`, `archive.extract`, `entry.read`, `entry.open`, `archive.convert`, and the three edits (so `from` and `entries` match the names as shown).
- **Config:** `[names] encoding = "auto"` sets the default.
- **What gets written:** names BeeZip writes (new and renamed entries) are UTF-8, flagged where the format has a flag. Kept entries keep their bytes.
- **Core:** `OpenOptions` gains `names: NameDecoding`, the encoding to use and the two code pages; each byte-name reader decodes `raw_path` through it, so `Entry.path` is what everything else uses. The zip reader decodes names itself rather than through the zip crate's CP437.
- **The cache key** includes the encoding.
- **No guessing:** a name that isn't UTF-8 and was written in another code page than the system's comes out wrong until an encoding is chosen. Detectors such as `chardetng` guess from text, and a few short names give them little to go on. The desktop makes choosing easy instead (§8.4).

## 7. Commands
### 7.1 `archive.add`
Effect Destructive. CLI `beezip add ARCHIVE INPUT…`, alias `a`.

| Field | Meaning |
|---|---|
| `archive` | the archive to add to |
| `inputs` | files and folders, each stored under its own name, as `archive.create` stores them |
| `dir` | the folder inside the archive to add into [default: the top] |
| `overwrite` | an entry with the same path: `ask`, `always` (replace it), `never` (keep it, skip the file), `newer` (replace it when the file is newer), `rename` (add as `a (1).txt`) [default: from config, `[edit] overwrite = "ask"`]. Paths match ignoring case on Windows, as selections do |
| `method`, `level`, `threads` | for the new entries, the 7z blocks re-encoded, or a tar's stream, as in `archive.create` |
| `password`, `encryption` | encrypt the new entries (zip, 7z) |
| `unencrypted` | add them in the clear to an archive whose entries are encrypted (§3.7) |
| `solid` | 7z only |
| `exclude`, `follow_links` | as in `archive.create` |
| `encoding` | §6 |
| `dry_run` | report what would change |

- **The archive itself** is never added, as with create.
- **An `ask`** prompts with the entry's path and the archive (`Prompt::Overwrite` gains `archive`; core's `Ctx` gains `overwrite_entry(archive, entry)`). The answers are M3's: replace, replace all, skip, skip all, rename.

### 7.2 `archive.remove`
Effect Destructive. CLI `beezip remove ARCHIVE ENTRY…`, alias `d`.

- **Input:** `archive`, `entries` (a folder takes everything under it), `glob`, `exclude` (as in `archive.extract`), `password`, `encoding`, `dry_run`.
- **Nothing matched:** `NotFound`, "nothing in a.zip matches", and nothing is written.
- **Removing everything** leaves an empty archive, which zip, 7z and tar can be.

### 7.3 `archive.rename`
Effect Destructive. CLI `beezip rename ARCHIVE FROM TO`, alias `rn`.

- **Input:** `archive`, `from` (an entry, or a folder, including one that exists only as the parent of entries), `to` (the new full path, so it also moves), `password`, `encoding`, `dry_run`.
- **A folder** renames everything under it.
- **Checks** (`InvalidArgs` or `Conflict`, before anything is written):
  - `to` is normalized like a selection's paths. It can't be empty or absolute, contain `..`, or lie inside `from`;
  - `to` mustn't exist, unless only its case differs from `from`'s;
  - `from` must exist: otherwise `NotFound`.
- **One rename per call.** The desktop renames one item at a time, and several renames would need a list in the CLI's arguments that no other command has.

### 7.4 The edits' output
All three return:

| Field | Meaning |
|---|---|
| `path`, `format` | |
| `added`, `replaced`, `removed`, `renamed`, `skipped` | entries, by what happened to them |
| `entries` | how many the archive has now |
| `copied` | entries copied without decoding |
| `recompressed` | entries decoded and encoded again |
| `bytes_before`, `bytes_after` | the archive's size |
| `unencrypted` | new entries added in the clear to an encrypted archive |
| `dry_run`, `plan` | for a dry run, each change: `{ action, path, from }` |

`--output human` gives one line: "Added 3 files to a.zip (12 entries copied as they were); 1.2 MiB → 1.4 MiB".

### 7.5 `archive.convert`
Effect Writes. CLI `beezip convert ARCHIVE OUTPUT`.

- **Input:**
  - `archive`, `password` (the source's), `encoding`;
  - `output`, `format` [default: from the output's extension], and `archive.create`'s options for the new archive: `method`, `level`, `threads`, `encryption`, `encrypt_headers`, `solid`, `volume_size`, `overwrite`. Its password is `new_password`;
  - `entries`, `glob`, `exclude` to convert part of it;
  - `decrypt`, to write an encrypted source's entries in the clear;
  - `dry_run`.
- **Raw copies** happen when the source and the output share a format and no option asks for something else: `a.tar.gz` → `a.tar.zst` copies the tar entries and re-encodes the stream; zip → zip with the same options copies everything.
- **An encrypted source** needs `new_password` or `decrypt`, or the command fails with `InvalidArgs` before reading. Encryption is never dropped silently.
- **What the target can't hold** is reported, never failed on:
  - hard links become files (zip, 7z, CAB, ISO without Rock Ridge);
  - symlinks in formats without links are skipped;
  - devices and FIFOs are skipped;
  - names a format can't store, such as ISO's without Joliet, follow that writer's rules (§5).
- **The output can't be the source:** `InvalidArgs`. Editing in place is what the edits are for.
- **Output:** `archive.create`'s, plus `copied`, `recompressed` and `skipped`.

### 7.6 `entry.open`
Effect Writes, `Surfaces::NO_MCP`. CLI `beezip open ARCHIVE ENTRY`.

- **Input:** `archive`, `entry` (a file), `password`, `encoding`, `launch` [default: true].
- **Where:** the entry is extracted through `FsSink`, with every SafeFs rule and the Mark of the Web, into `%TEMP%\BeeZip\open\<random>\<name>`. Its own folder keeps names apart, so two entries called `readme.txt` don't collide.
- **Launching:** `open::that_detached`, which calls `ShellExecuteW`: the default app, or Windows' "Open with" dialog. A program runs the way Explorer runs one from a downloaded zip: SmartScreen sees its Mark of the Web. The desktop asks first for programs (§8.3); the CLI runs what was named.
- **Refused:** a folder or a link (`InvalidArgs`).
- **Clean-up:** each call deletes folders under `%TEMP%\BeeZip\open` older than a day, skipping files still in use.
- **Output:** `path`, `launched`.

### 7.7 The engine
- **One edit per archive at a time:** a second edit of the same archive in the same process waits for the first, and logs "Waiting for another change to a.zip". Reads aren't held up. Between processes (the CLI beside the desktop), the stamp check fails the later one with `Conflict` (§3.1).
- **The cache** drops the archive's reader and listings after a swap.
- **Effects:** the edits are Destructive, so MCP marks them `destructiveHint`, `--read-only` hides them, and the desktop confirms removals (§8.1).

### 7.8 CLI
- **New subcommands:** `add` (`a`), `remove` (`d`), `rename` (`rn`), `convert` and `open`, generated as before. The letters are 7-Zip's.
- **Output:** the one-line summaries above; ndjson streams the events as for the other commands.

### 7.9 MCP
- **The tools** `archive_add`, `archive_remove`, `archive_rename` and `archive_convert` come from the registry, with no MCP code. `entry.open` is hidden.
- **The sandbox:** an edit writes its archive, so the archive must be under a root; `archive.add`'s inputs are reads. `convert` writes its output.
- **Prompts:** an `ask` overwrite reaches the client through elicitation, as extract's does (M2 §3.3). A password never does: `PasswordRequired` tells the model to pass `password` or `unencrypted`.
- **`docs/MCP.md`** gets the new tools and formats.

## 8. Desktop
### 8.1 Editing in the browser
- **Toolbar and palette:** Add files…, Add folder…, Delete, Rename and Convert…. Keys: Delete, F2.
- **Delete** confirms ("Delete 3 items from a.zip?"), since it's Destructive and can't be undone.
- **Rename** edits the name in place: Enter saves, Escape cancels, and a `Conflict` shows beside it.
- **Add** opens an add dialog: the files, the folder inside the archive, the overwrite choice, and the method, level and password, with "Copy as CLI". When the archive has encrypted entries, "Encrypt the new files" is on, and needs the password; turning it off sends `unencrypted`.
- **While an edit runs,** it's in the jobs panel. When it ends, the tab lists again, in the same folder, keeping the selection by path.
- **When an archive can't be edited** (its format, a volume set, an SFX, a read-only file), the commands are disabled and say why.

### 8.2 Dropping files on an open archive
- **On the entry table of an archive that can be edited:** the add dialog, with the dropped paths, into the folder shown. The dialog is the confirmation, so a stray drop changes nothing.
- **On one that can't:** M3's create dialog, as today, with the reason.
- **On the welcome screen or the tab strip:** as today. One archive opens, anything else offers a new archive.
- **One archive dropped on an editable table** is added to it, like any file; dropping it on the tab strip opens it.

### 8.3 Opening entries
- **Double-click or Enter on a file** runs `entry.open`:
  - an archive BeeZip reads opens in a new tab (`launch: false`, then the temporary path is opened as a tab);
  - a program (`.exe`, `.msi`, `.bat`, `.cmd`, `.ps1`, `.vbs`, `.js`, `.lnk`, `.scr` and the like) asks first: "Run setup.exe from a.zip?";
  - anything else opens in its app.
- **Updating the archive:** Rust notes each file `entry.open` extracted for the main window (its tab, entry, path, size and time). When the main window gets the focus back, it checks them, and sends the page an `entry-changed` event for any that changed. That's one event beside `open-paths` and `open-dialog`, and still four Tauri commands.
  - The page asks "readme.txt was changed. Update it in a.zip?" (Update, Not now).
  - Update runs `archive.add` with the file, into the entry's folder, `overwrite: always`, and the tab's password when the entry was encrypted.
- **Closing a tab** forgets its opened files. They aren't deleted while an editor may still have them; the next `entry.open` sweeps them after a day.

### 8.4 The name encoding
- **Per tab:** "Name encoding…" in the palette and in the info dialog: Auto, UTF-8, then the list in §6. The tab lists again, and every command on it passes the choice.
- **The default** is on the settings page's Extracting section (`[names] encoding`).

### 8.5 Converting
"Convert a.zip…" opens the create dialog in a convert mode: the source, then the output's format, options and password, and volume size, with "Copy as CLI". The output defaults to the same folder and name with the new extension.

## 9. Explorer: adding to an existing archive
- **`shell.plan`:** an add step whose archive exists carries `existing { path, keep_both, can_add }`. `can_add` is true when the archive's format can be edited and it isn't a volume set, an SFX or read-only.
- **The job window** asks "a.zip is already there" with Add to it (first, when `can_add`), Replace, Keep both and Skip.
- **Add to it** runs `archive.add` with the selection, into the top folder, `overwrite: ask`. An entry already there asks in the job window. An encrypted archive asks for the new files' password there.
- **Its title** is "Adding to a.zip".

## 14. Decisions (taken while planning, 2026-11-06)
Each could reasonably go the other way. Say which to reverse, and I'll change it.

- **In-house readers for cpio, ar, deb, RPM, CAB, squashfs and UDIF,** rather than PLAN's crates, which can abort the process on small crafted files (§16). The alternative is the crates, with upstream fixes we'd wait for.
- **deb is read-only, listed as `dpkg-deb -R` unpacks it** (files at the top, control files under `DEBIAN/`). The alternative lists the ar members, as `7z -tar` does.
- **squashfs is read by BeeZip and written by backhand,** which needs a BSL-1.0 exception in `deny.toml` for `xxhash-rust`. The alternative is an in-house writer too, about as large again as the reader.
- **A patched hadris-iso is vendored** until its name fix is upstream, rather than shipping an ISO writer that takes minutes over a large folder.
- **hadris 3.0 before its final release:** the newest 3.0 when PR 5 starts. 2.5's API is being replaced, and its writer has the bugs 3.0 fixed.
- **DMG is written too,** with fstool's HFS+ writer, checked on CI's macOS runner. The alternative is reading only, which avoids depending on fstool's writer, a young crate by one author.
- **El Torito boot images and zisofs aren't extracted from ISOs** in M5, and sparse disk images aren't opened.
- **`.iso` and `.cab` aren't associated with BeeZip,** since Windows mounts the first and shows the second as a folder. Explorer's menu still offers BeeZip's items for both.
- **squashfs is written with gzip by default,** as `mksquashfs` does, so old kernels and 7-Zip read it.
- **lzop goes through lzokay at 10–24 MB/s,** with a faster LZO1X-1 compressor left as a follow-up.
- **Fixtures:** libarchive's and delharc's test files, `makecab`, `mksquashfs`, `ar` and `dpkg-deb` in WSL, packages of MIT-licensed software for RPM and deb, and DMGs made by `hdiutil` on CI, so nothing committed carries copyleft binaries or app code.
- **Edits always write a new archive and swap it in,** even when only adding to a zip, which could be appended in place. The alternative is faster for big zips, but a failure part-way would leave a damaged archive.
- **Zip entries are copied by BeeZip, byte for byte,** not by the zip crate, whose copies are corrupt for ZipCrypto and LZMA (§16). New entries still go through the zip crate.
- **7z edits copy whole blocks** and re-encode only those they change.
- **A compressed tar is re-encoded at the config's level,** since the stream doesn't record the one it was made with.
- **Volume sets and SFX archives aren't edited;** `archive.convert` makes a single file. The alternative rewrites every part, which can't be made atomic.
- **CAB and the disk images are created, not edited** in M5. Editing them through the general path would mean rebuilding the whole image for each change.
- **Encryption is never dropped.** Adding to an encrypted archive asks for the new files' password unless `unencrypted` is given, and converting an encrypted archive needs `new_password` or `decrypt`. 7-Zip adds plain files to an encrypted archive without a word.
- **Adding over an existing entry asks by default** (`[edit] overwrite = "ask"`), like extracting. 7-Zip replaces.
- **Removing a tar hard link's target is refused** while links to it stay. The alternative turns the first remaining link into a file.
- **What a swap keeps:** Mark of the Web, the hidden and system attributes, and the creation time. It doesn't keep permissions set on the file itself, and a read-only archive is refused rather than unlocked.
- **One edit per archive at a time in a process,** the second waiting; between processes, the later one fails with `Conflict`.
- **`entry.open` lets the desktop update the archive** when the opened file changes, checked when the window gets the focus back, not by a file watcher.
- **Programs opened from an archive ask first** in the desktop; the CLI runs what you name.
- **"auto" reads zip names in the system's OEM code page,** as Explorer and 7-Zip do, rather than always CP437, and no encoding is guessed from the bytes.
- **A drop on an open archive goes through the add dialog,** which is the confirmation. A drop on the tab strip still opens archives.
- **Explorer's "Add to "a.zip"" over an existing archive offers Add to it first.**
- **One rename per call** (`beezip rename ARCHIVE FROM TO`).
- **zip, sevenz-rust2 and lzma-rust2 stay pinned** at 9.2.2, 0.24.2 and 0.23.0 until M6.
- **Five PRs:** the zip reader and encodings, editing, editing in the desktop and Explorer, archive formats, disk images. Each can be tried on its own.

## 16. Found while building

### Found while planning
Spikes in scratch workspaces outside the repo (Rust 1.99.1, release builds unless said), with 7-Zip 26.00 as the oracle, WSL Ubuntu 24.04's existing tools, and copies of the repo's `deny.toml`. Five of them were run by subagents, one per group of formats. Their code, scripts and repro inputs are kept in `target/m5-spikes/` (not committed), for the PRs to start from: the `.Z` codec, the lzop container, the RPM header parser, the UDIF reader and decmpfs decoders, and the hadris patch. Every reader was given mutated inputs (truncated, bit-flipped, extreme values) under `catch_unwind`, with a timeout and an allocation tripwire, since a failed allocation aborts.

1. **The zip crate's raw copy is corrupt for two kinds of entry** (zip 9.2.2, and 9.4.1 of 2026-11-06). The writer rebuilds the general-purpose flags from its options rather than copying them:
   - `raw_copy_file` of a ZipCrypto entry (7-Zip's `-mem=ZipCrypto`) clears bit 0, so the copy claims to be unencrypted and `7z t` reports a data error;
   - `raw_copy_file` of an LZMA entry (7-Zip's `-mm=LZMA`) clears bit 1, the end-of-stream marker, and `7z t` reports a headers error;
   - `ZipWriter::new_append` keeps the local headers but writes the kept entries' central records without bit 1, so an appended LZMA zip fails the same way.
   - Deflate, Store, BZip2, PPMd, AES-256 and .NET's zips copied correctly. Hence §3.3.
2. **sevenz-rust2 0.24.2's `push_raw_block`** copied every block of 7-Zip's solid, non-solid, BCJ2 and AES-with-encrypted-header archives, with one entry renamed. `7z t` passed all four, and the encrypted one kept `7zAES` on every entry and in its header.
3. **The million-entry zip** (§4): `has_overlapping_files` took 2.8 s in a bare spike and 4.6–5.0 s in core, out of 5.2–5.8 s. Reading the local headers in file order with a seek-relative buffer, and checking the ranges, took 35 ms.
4. **Swapping files on Windows** (Rust 1.99.1, `fs::rename`):
   - over a file this process holds with std's default share mode: it works, and the old handle reads the old bytes;
   - over one held without `FILE_SHARE_DELETE`: `ERROR_ACCESS_DENIED`, and it works once the handle closes;
   - over a read-only file: `ERROR_ACCESS_DENIED`.
5. **Newer releases:** zip went 9.2.2 → 9.4.1 between 2026-11-03 and today, and sevenz-rust2 0.25.0 came out today; both need lzma-rust2 0.25. Their changelogs fix nothing M5 needs, and the raw-copy bugs are still in 9.4.1.
6. **ISO** (hadris-iso and hadris-udf 3.0.0-rc.3, and 2.5.0):
   - 3.0 wrote a tree with Unicode and emoji names, a 200-character name, 10 levels, an empty file, a 100 MB file and a symlink in 40 ms; `7z t` passed, and Rock Ridge read back every name, mode, link and time. A 4.6 GB file spanned several extents and read back right in 7-Zip and in hadris.
   - 25 libarchive images matched 7-Zip, except relocated folders, which hadris puts back as libarchive expects. Three crafted ones were refused.
   - Windows 10's ISO: an empty ISO 9660 tree with two boot images, and a UDF tree that hadris-udf read in full (above).
   - 200 000 files: 1.06 s to plan, 1.8 s to write, 254 MB at the writer's peak; 0.7 s to list.
   - 2.5's writer duplicates a relocated folder in the Joliet tree and writes the write time instead of the files'.
   - 60 000 mutated cases: no panic, abort or hang.
7. **squashfs** (backhand 0.25.5):
   - 13 images from `mksquashfs` 4.6.1 (gzip, xz, xz with BCJ, lzma, lzo, lz4, lz4hc, zstd, large and small blocks, with and without fragments), 20 126 entries each, read through BeeZip's own codecs in `CompressionAction`: every kind, mode, time, size, link target and SHA-256 matched.
   - Listing the 20 000-file image took 10–26 ms; reading every file 0.15–0.97 s; a million entries took 0.65 s to open and 151 MiB to hold.
   - Writing 20 020 files took 0.8–7.0 s with 15–18 MiB of heap; `7z t` and `unsquashfs` passed every compressor 7-Zip reads, and repeated writes with fixed times were identical.
   - 300 000 mutated cases: 202 panics (one place) and one abort from a 1 GiB allocation.
8. **CAB, ar, cpio, RPM:**
   - `cab` read makecab's MSZIP and LZX cabinets, but took 289 s to extract 2 000 files of one folder (7-Zip: 0.37 s), opened no cabinet set, and panicked 123 times in 20 000 cases.
   - `ar` read and wrote GNU and BSD archives, and debs in six compressions listed through it and BeeZip's codecs matched `dpkg-deb -c`. 6 panics and 10 allocations over 1 GiB in 20 000 cases.
   - `cpio` read the 6 newc and crc fixtures of libarchive's 27, refusing all odc, binary and afio ones; no failures in 20 000 cases.
   - `rpm`'s metadata parser stops exactly at the payload, which BeeZip's codecs and a cpio reader then streamed, matching 7-Zip on six packages (zstd, xz, gzip, bzip2). 1 613–1 701 panics and 206–255 allocations over 1 GiB in 20 000 cases; a 204-line parser of the spike's had none.
9. **LHA, `.Z`, lzop:**
   - delharc matched 7-Zip on 161 of 255 archives, and decoded 58 that 7-Zip fails on; no failures in its share of 205 000 mutated cases.
   - The spike's `.Z` codec (above) and lzop container (above), with no failures in theirs.
10. **DMG:**
    - 9 real DMGs from MIT, Apache-2.0, BSD-2 and Unlicense apps (HFS+ with zlib and LZFSE, APFS with LZFSE, bzip2 and none): every file's SHA-256 matched `7z x`, read through udif's tables, a small partition reader of the spike's and dpp's `hfsplus`/`apfs`.
    - udif 0.4.2 hands out a partition only whole or as one stream, has no ADC, and aborts on three header fields (below).
    - dpp's `hfsplus` hangs on a node that points to itself, and `apfs` overflows its stack on one; both allocate from untrusted counts.
    - fstool 0.5.2 read the same images (all but 9 compressed files) and handled all three cycles. Its HFS+ writer made a UDZO image of a Unicode tree, a symlink and an executable that passed `7z t` with every hash matching; not checked on a Mac.
    - A chunk cache of four 1 MiB runs instead of one cut a bzip2 image's read from 6.7 s to 0.54 s.
    - The spike's own UDIF reader behind fstool's `BlockDevice` (16 cached chunks): every file of four real images matched 7-Zip; 10 000 files took 0.18 s (25 s through fstool's DMG layer), 202 000 entries 4.3 s (over 600 s).
    - decmpfs by hand: the 9 failing files were zlib in the resource fork, read through fstool's catalog and fork readers (`get_xattr` and `entry_info` exist from 0.5.2), and all 9 matched 7-Zip. The other types' decoders were written but have no sample yet, hence the `hdiutil` fixtures (§10).
    - fstool's API history, from the 49 published versions: of the calls BeeZip makes, `list` took `&mut self` from 0.0.5, and `AnyFs` became `#[non_exhaustive]` in 0.5.1; the rest were additions.
11. **hadris-iso's name de-duplication** can't be avoided by the caller: the primary names come from the tree's names, and no option skips it (L1, L2, L3 and ISO 9660:1999 all took 79–84 s for 20 000 colliding names). An 8-line patch that remembers the next suffix per name planned them in 0.12 s, and `7z t` passed the image.
12. **Bugs found in third-party code,** each with its repro in the spike's folder. They go on the upstream list when their workaround lands; the ones in crates BeeZip doesn't use are listed for reporting only:
    - **zip 9.2.2–9.4.1:** item 1's three.
    - **hadris-iso 3.0.0-rc.3:** quadratic name de-duplication (5 000 colliding names take 4.2 s, 20 000 about 80 s); a read succeeds on a file whose open failed (libarchive's `rockridge_ce_loop.iso`); 7-Zip reports a headers error on its UDF bridge output (which side is wrong is unclear).
    - **backhand 0.25.5:** a non-UTF-8 name panics on Windows; a name with `\` fails the open on Windows; a symlink target of 256 bytes or more fails the open; a block count allocates before it's checked; the fragment cache is never trimmed; duplicate detection leaves stale bytes after the image; gzip's options are written as 7 bytes.
    - **cab 0.6.0:** a folder of more than 65 535 blocks wraps its count; a folder with too few blocks reads short without an error; panics fixed on master but unreleased.
    - **ar 0.9.0:** allocations of 9–16 GB from three header fields; a size of 10¹⁰ bytes or more writes a corrupt header (not fixed on master).
    - **cpio 0.4.2:** finishing an entry short returns Ok and leaves a corrupt archive.
    - **rpm 0.30.2:** an index entry past the data panics; an overflow on libarchive's `huge_rpm`; 112- and 128-byte files allocating 2 and 4 GiB.
    - **udif 0.4.2:** three header fields that abort the process through their allocations; an LZFSE chunk decoded without a bound (1 696:1).
    - **hfsplus 0.4.0 and apfs 0.4.1:** names compared without HFS+'s case folding, so the private-data folder `walk` returns can't be opened; overflow extents ignored; a hang and an endless allocation on self-linked nodes; a stack overflow and an allocation from an untrusted count in apfs.
    - **fstool 0.5.2:** the decmpfs magic read big-endian, so Apple-compressed files fail; one decoded chunk cached; an 8 GiB chunk cap; ULFO writing documented but refused.
    - **delharc 0.8.0:** uninitialized memory passed to `read_exact` through `assume_init_mut` (`parser.rs:189`, `stub_io.rs:62`), found by reading.
    - **lzokay 2.0.1:** an empty input compresses to a block every decoder rejects. lzokay-native 0.2.1 compresses it to nothing.
    - **compcol 0.7.8:** its `.Z` decoder fails when the padding after a CLEAR is split across reads, and its encoder clears once where compress clears 246 times.
    - **7-Zip 26.00:** a data error on libarchive's `lzx_16bit` CAB, which lzxd and libarchive decode; it can't open lz4 squashfs.
    - **libarchive 3.8.9:** a non-block-mode `.Z` fails, since it doesn't skip the padding when the code width grows.
