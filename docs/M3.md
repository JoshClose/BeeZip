# BeeZip — M3 (Desktop MVP + 7z, RAR and volumes) Plan

This plan builds on [`PLAN.md`](PLAN.md), [`M0.md`](M0.md), [`M1.md`](M1.md) and [`M2.md`](M2.md) and keeps their decisions, except where §9 corrects PLAN.md. Versions and licenses were checked on 2026-11-03 against crates.io and npm. The APIs named here were checked in the sources of sevenz-rust2 0.24.2, lzma-rust2 0.23.0, unrar_sys 0.5.8 (which vendors UnRAR 7.1.0), unrar 0.5.8, rars 0.12.3, tauri-plugin-single-instance 2.5.5, tauri-plugin-dialog 2.8.4, tauri-utils 2.10.2, the NSIS template at `tauri-cli-v2.12.4`, tempfile 3.27.0, cargo-deny 0.20.2 and @tanstack/react-table 9.3.1. Two spikes back the RAR and license plans: a scratch build of the whole dependency set, which passes `cargo deny check` with the UnRAR exception below, and a small unrar_sys program that read libarchive's RAR5 fixtures (§11).

## Scope
- **beezip-core:**
  - **volumes:** a `VolumeSet` that reads `name.001`, `name.002`… as one seekable file, and a writer that splits any new archive into volumes;
  - **7z:** read and write through sevenz-rust2, with AES-256, encrypted headers, solid blocks, filters and SFX;
  - **RAR 1.5–7:** read only, through UnRAR in a new `beezip-unrar` crate: volumes, passwords for data and headers, links, SFX;
  - **detection** of 7z, RAR, 7z/RAR SFX and volume sets;
  - **partial files** tracked process-wide, so the CLI's second Ctrl+C can delete them (the M1 bug, §3.7).
- **beezip-commands:**
  - `archive.create` writes 7z and volumes: `-f 7z`, the 7z methods, `--solid`, `--encrypt-headers`, `-v/--volume-size`;
  - `archive.info`, `file.detect` and `formats.list` report volumes and the new formats;
  - `archive.list` gains `sort`, `reverse` and `kind`, for the browser;
  - an archive cache (the PLAN's index cache), a job id on prompts, and a `cli.line` command for "Copy as CLI".
- **beezip-cli:** the new flags, and the Ctrl+C fix.
- **beezip-mcp:** no code changes. The new options reach MCP through the registry; [`docs/MCP.md`](MCP.md) gets the new formats.
- **Desktop:**
  - `cmd_respond` and a prompt bridge, completing the four-command IPC;
  - the archive browser (tabs, folder tree, virtualised entry table, breadcrumb), preview, the extract and create dialogs, the jobs panel, password and overwrite prompts, the Ctrl+K palette, and "Copy as CLI" on every dialog;
  - opening files by dialog, drag-and-drop, double-click (file associations) and single-instance forwarding;
  - an About page with the formats list and the third-party notices, UnRAR's among them;
  - `cargo xtask dist`: an NSIS installer with `BeeZip.exe`, `bin\beezip.exe` on PATH, the associations and the notices.

**Out of scope:**
- **M4:** job mode (`BeeZip.exe --job`), the settings page and `settings.*`, Explorer menus.
- **M5:** adding to, removing from and converting archives (dropping files on an open archive offers a new archive instead).
- **M6:** drag-out to Explorer, the updater, signing, the tauri-driver E2E test, macOS and Linux bundles.
- **Never:** creating RAR archives (PLAN §2; UnRAR's license also forbids using its code for that).
- **Not supported in v1:**
  - 7z entries compressed with zstd, which only the 7-Zip-zstd fork writes. sevenz-rust2's `zstd` feature would turn on zstd's legacy decoders across the workspace (checked with `cargo tree -e features`).
  - Spanned zips (`.z01`), as PLAN §2 already says.

## 3. beezip-core

### 3.1 Volumes (`volume.rs`)
- **Naming:**
  - **Numbered sets:** `name.001`, `name.002`… with three or more digits, starting at 1, as 7-Zip writes them (`a.7z.001`, `a.zip.001`, `a.tar.zst.001`, `big.iso.001`).
  - **RAR sets:** `name.part1.rar`… (any digit width), or `name.rar`, `name.r00`, `name.r01`…. UnRAR opens their volumes itself; BeeZip only names them, for `archive.info` and to find the first part.
  - **Opening any part opens the whole set**, from part 1. The set ends at the first missing number.
  - **A missing part:** a gap before a part that exists is `NotFound` ("volume 3 of a.7z is missing"). A missing last part can't be seen by name, so the archive reads as truncated (`Corrupt`), and the message says how many volumes were found.
- **`VolumeReader`:** `Read + Seek` over the parts, which stay closed until they are read. The part sizes are taken when the set opens, and a part that has changed since is an `Io` error.
- **`VolumeWriter`:** `Write + Seek`, for creating:
  - It writes `<output>.001`, `.002`… as partial files (§3.7), each `volume_size` bytes except the last.
  - Seeking back rewrites earlier parts, which 7z needs for its start header and zip for its local headers.
  - `finish()` renames every part into place.
  - **Overwriting:** with `overwrite`, parts of an older set beyond the new last part are deleted too; otherwise a reader would join them on. Without `overwrite`, any existing part is a `Conflict`.
  - The smallest volume size is 1 KiB; anything smaller is `InvalidArgs`.
- **What a set's content becomes:** a set opens as whatever its joined content is: a 7z, a zip, a `tar.zst`. A set of anything else (`big.iso.001`) opens as the one-entry stream view, named `big.iso`, so extracting it joins the parts.

### 3.2 Opening (`source.rs`)
- **`Input`:** one `Read + Seek` type in place of `File`. It is a file, a `VolumeReader`, or an offset view that starts at the archive inside an SFX.
- **`Source`:**
  - It gains `volumes: Vec<PathBuf>`, with one path for a plain file, and `open_file()` returns `CountingReader<Input>`.
  - The two places that reopened `source.path` by hand switch to `Input`: zip's second handle for central-directory times, and the stream format's gzip `ISIZE` read.
  - So zip, tar and stream read volume sets with no other change.
- **Progress and limits:** `size` is the whole set's size, so progress and the ratio limit see the set as one file.
- **Mark of the Web:** extraction copies the first part's `Zone.Identifier`, or the first one found, to every file.

### 3.3 7z (`format/sevenz.rs`, sevenz-rust2 =0.24.2)
**Reading**
- **Opening:**
  - `Archive::read(&mut input, &Password)`. When it fails with `PasswordRequired` (encrypted headers), BeeZip asks `Ctx::password` and tries again.
  - A wrong header password shows up as a decode or CRC error. With a password given, that counts as a wrong password, up to the usual three prompts, then `WrongPassword`.
- **The encoded-header check** (`sevenz_header.rs`):
  - sevenz-rust2 decodes a compressed header with no memory limit (`MAX_MEM_LIMIT_KB = usize::MAX / 1024`). It grows the buffer only as data decodes, so a 1 KiB header declaring gigabytes of zeros fills memory.
  - Before `Archive::read`, BeeZip reads the 32-byte start header and the next header's first bytes.
  - For an encoded header, it reads the header block's coders and unpack size from the streams info, about a hundred lines of parsing. An unpack size over `decoder_memory`, or a dictionary over it, is `LimitExceeded`.
  - The fuzzers would otherwise hit their 2 GiB RSS limit on such inputs.
- **The index:**
  - Entries come from `archive.files`, in order, so the id is the index.
  - Directories are `Dir`. A file whose attributes carry 7-Zip's Unix extension (`0x8000`) with `S_IFLNK` in the high 16 bits is a `Symlink`, as `7z a -snl` stores it; its target is its data, read when it is extracted. 7-Zip on Windows stores `-snl` links differently, with the reparse-point attribute (`0x400`) and a reparse buffer as data; those are links too (§11). Anti-items are skipped with a warning.
  - **Metadata:** times come from `last_modified_date` (100 ns, UTC); `dos_attrs` from the low 16 bits of the attributes; `unix_mode` from the high 16 when `0x8000` is set.
  - `encrypted` means the entry's block has an AES coder. `packed_size` is set only when a block holds one entry.
- **Methods:** the names come from the block's coders: LZMA, LZMA2, PPMd, BZip2, Deflate, Deflate64, Copy, LZ4, Brotli; the filters BCJ, BCJ2, ARM, ARM64, ARMT, PPC, IA64, SPARC, RISCV and Delta; and AES-256. `info.solid` is sevenz-rust2's `is_solid`.
- **Memory:** before a block is decoded, its coders' needs are added up: the LZMA and LZMA2 dictionary sizes from their properties, and PPMd's model size. A block over `decoder_memory` is `LimitExceeded`. The decoding threads (LZMA2 only) are as many as fit in that memory, and at most one per core.
- **Extracting:** each block runs through `BlockDecoder::for_each_entries`, whose callback hands over an entry and a `&mut dyn Read`, which is the `EntrySink` model. Entries whose block holds nothing selected are never decoded. The sink's errors pass through a captured slot, since the callback must return sevenz-rust2's error type.
- **Data passwords:**
  - A block with an AES coder asks for the password before decoding.
  - 7z has no password check value, so a wrong password surfaces as a decode or CRC failure. It reads "wrong password or damaged data", is retried from the start of the block, and ends as `WrongPassword` after three prompts.
- **`open_entry`:**
  - sevenz-rust2's block decoder only calls back, so `open_entry` runs it on a helper thread with its own `Input` and a bounded pipe (`io::pipe`, 4 × 256 KiB).
  - The reader it returns pulls from the pipe. Dropping it stops the decoder.
  - A non-solid block decodes only that entry; a solid one decodes from the block's start.

**Writing**
- **Output:** `ArchiveWriter::new(W: Write + Seek)`, where W is a `File` or a `VolumeWriter`.
- **Methods**, matching what 7-Zip itself reads:

  | Method | Levels (default) | Notes |
  |---|---|---|
  | LZMA2 | 0–9 (5) | the default; `--threads` uses `Lzma2Options::from_level_mt` with chunks of 3 × the dictionary, as xz does |
  | LZMA | 0–9 (5) | |
  | PPMd | 1–9 (6) | |
  | BZip2 | 1–9 (9) | |
  | Deflate | 1–9 (6) | |
  | Copy | – | |

  No BCJ filters are applied in M3. 7-Zip adds them to executables by default.
- **Password:**
  - The content methods become `[AesEncoderOptions::new(Password::new(pw)), method]`.
  - **Headers:** `set_encrypt_header(true)` is the default when a password is given (§10), and `--encrypt-headers=false` turns it off. sevenz-rust2 encrypts the header only when an AES coder is present, so `--encrypt-headers` without a password is `InvalidArgs`.
- **Entries:**
  - Files use `ArchiveEntry::new_file` and directories `new_directory`, with the mtime and the attributes. On Unix, the mode goes in the high bits with `0x8000`.
  - Empty files have no stream, as 7-Zip writes them.
  - A symlink is stored as 7-Zip's `-snl` stores it: a file whose mode is `S_IFLNK` and whose data is the target.
- **Solid blocks:**
  - `--solid` is on by default for 7z (§10).
  - `push_archive_entries` needs every reader of a block up front, so `ArchiveWriter` gains `add_solid(entries, open, cx)`. Its default loops over `add`.
  - `ops::create` groups consecutive files into blocks of at most max(64 MiB, 4 × the dictionary), and never more than 1 GiB, and hands each block to `add_solid`.
  - The 7z writer passes `SourceReader`s over lazy readers. Each opens its file on first read, counts bytes for progress, and checks for cancellation.

### 3.4 RAR (`crates/beezip-unrar`, `format/rar.rs`)
UnRAR only takes a file name, decodes on its own call stack and hands data to a callback, so a RAR job needs a thread of its own. The `unrar` crate exposes none of that: an entry can only be read whole into a `Vec<u8>` or written to disk by UnRAR itself. That would leave no memory bound, no cancellation inside an entry, no bomb limits, and no `FsSink` between UnRAR and the disk. So `beezip-unrar` drives unrar_sys directly.

- **Structs:**
  - UnRAR's `dll.hpp` declares its structs under `#pragma pack(push, 1)`. unrar_sys declares them `#[repr(C)]` only, so every `RARHeaderDataEx` field after `FileAttr` is at the wrong offset.
  - The `unrar` crate reads only the fields before that point, which is why it works. BeeZip needs `DictSize`, `RedirType`/`RedirName` and the 100 ns times, which all come after it.
  - So `ffi.rs` declares `RARHeaderDataEx` and `RAROpenArchiveDataEx` itself, `#[repr(C, packed)]`, with size assertions for both widths of `wchar_t`: 10 244 bytes on Windows, where it is 16-bit, and the 32-bit layout on Linux. It passes them to unrar_sys's functions by pointer cast.
  - The spike crashed reading a symlink's header through unrar_sys's struct and read it correctly through the packed one (§11).
- **`Session`:**
  - It owns one UnRAR handle on its own thread and answers messages: `Next` reads a header; `Test` decodes an entry; `Skip`; `Close`.
  - It sends back `Header`, `Data(chunk)`, `Done(code)`, `Password(reply)` and `Volume(path)` over bounded channels.
  - Data arrives in `RAR_TEST` mode through `UCM_PROCESSDATA`, in chunks of at most the dictionary window. UnRAR never creates a file, so none of its own path handling runs: `FsSink` decides every path.
  - The callback returns -1, which stops UnRAR, when the job is cancelled or the reader is dropped. Its body runs inside `catch_unwind`, so a panic can't unwind into C++.
- **Shared state:** UnRAR keeps its error state in a global (`ErrHandler`), so every call into UnRAR takes one process-wide lock. Two RAR jobs therefore take turns, one UnRAR call at a time; one long entry holds the lock while it decodes.
- **Passwords:**
  - `UCM_NEEDPASSWORDW` becomes a `Password` message, and the job thread answers it with `Ctx::password`.
  - UnRAR asks once per handle and then reuses the answer for the rest of the archive. That shows in the spike: libarchive's `rar5_encrypted.rar` has `d.txt` under a second password, and UnRAR returned `ERAR_BAD_PASSWORD` for it without asking again.
  - So on `ERAR_BAD_PASSWORD` the reader reopens the archive, skips to that entry, and gives UnRAR the next answer. A wrong header password fails `RAROpenArchiveEx` with code 24 and a null handle, and is asked again the same way.
  - RAR 1.5–4 data has no password check value, so a wrong password there shows as a CRC failure, "wrong password or damaged data".
- **The index:**
  - It comes from a `RAR_OM_LIST` pass, which reads only headers, even in a solid archive.
  - Paths come from `FileNameW` with `\` turned into `/`, or from `FileNameEx` for names over 1023 characters.
  - **Links:** `RedirType` 1–3 (Unix symlink, Windows symlink, junction) is a `Symlink` and 4 is a `Hardlink`, with the target from `RedirName`. Type 5 (file copy) is a `Hardlink` too, since both copy an earlier entry.
  - **Sizes and times:** sizes are 64-bit, and the mtime is `MtimeLow/High` (100 ns).
  - **Attributes:** `FileAttr` gives `dos_attrs` for Windows hosts and `unix_mode` for Unix ones.
  - **Methods:** the method is the algorithm version (`UnpVer`): RAR 1.5, 2.0, 2.9, 5.0 or 7.0, or Store for method `0x30`.
  - **Archive info:** solid, encrypted headers, locked, a recovery record, and the comment (through `CmtBufW`).
- **Limits:**
  - **Memory:** an entry whose `DictSize` is over `decoder_memory` is `LimitExceeded` before it is decoded. RAR 7 allows dictionaries up to 64 GiB.
  - **Ratio:** at each entry's start, the ratio counter adds that entry's packed size, so the ratio limit compares what is written with the compressed bytes behind it.
  - **Progress** uses the same count, plus `Volume` notices.
- **SFX and volumes:**
  - **SFX:** UnRAR finds the archive inside an SFX by itself.
  - **Volumes:** opening any part opens the first (§3.1). UnRAR asks for the next volume with `RAR_VOL_ASK` when one is missing; BeeZip answers -1, and the job fails with `NotFound` naming that volume.
- **`open_entry`:** a fresh session skips to the entry and tests it, streaming through the same channel. In a solid archive that decodes everything before the entry.
- **Building:** unrar_sys's `build.rs` links powrprof and shell32 but not advapi32, which UnRAR's registry, token and CryptoAPI calls need; Rust's std no longer links it. `beezip-unrar`'s `build.rs` adds it. Without it, the spike failed to link with 13 unresolved symbols.
- **The cargo feature:** `rar` is on by default; without it, RAR archives are detected and then fail with `BackendUnavailable`.

### 3.5 Detection
- **7z:** the signature `37 7A BC AF 27 1C` with major version 0 is `Likely`; with a matching start-header CRC it is `Certain`. Extensions: `.7z`, `.cb7`.
- **RAR:** the signatures `Rar!\x1A\x07\x00` (1.5–4.x), `Rar!\x1A\x07\x01\x00` (5.0+) and `RE~^` (1.4) are `Likely`; with the first header's CRC checked they are `Certain`. Extensions: `.rar`, `.cbr`, and the old-style volumes' `.r00`…
- **SFX:**
  - The PE section table, which is in the head, gives where the image ends: the overlay.
  - `detect_path` reads 16 bytes there, and the 7z and RAR sniffers look for their signature at that offset. That is where 7-Zip's `7z.sfx` and WinRAR's modules put the archive.
  - A 7z SFX opens through an offset view; UnRAR handles RAR SFX itself. The zip SFX check from M1 stays.
- **Volume sets:**
  - `detect_path` on any part probes the joined set: the head of part 1, the tail of the last part, and the name without `.001`.
  - So `a.zip.001` finds the zip's end record in the last part.
  - `Detection` gains `volumes`, the parts in order, with just the file itself for a plain file.
- **Spanned zips:** a zip whose end record names another disk, or that has a `.z01` beside it, is `UnsupportedFormat` with a message saying so.
- **zip:** `.cbz` joins its extensions.

### 3.6 Caps

| Format | list | extract | create | encrypt | encrypt_headers | solid | volumes | random_access |
|---|---|---|---|---|---|---|---|---|
| 7z | ✓ | ✓ | ✓ | AES-256 | ✓ | ✓ | ✓ | – |
| rar | ✓ | ✓ | – | – | – | – | ✓ | – |

- **`ArchiveInfo`** gains `volumes: usize`, and `solid` is reported per archive. The UI warns about slow previews from `solid`, not from the caps.

### 3.7 Partial files (`safefs/partial.rs`), and the second Ctrl+C
**The bug.** `FsSink`, `ops::create` and the stream commands each make a `.beezip-partial` file through tempfile, and delete it from a `Drop` guard. The second Ctrl+C calls `process::exit`, which runs no destructors. M1's manual check left a ~750 MB partial file in 3 runs out of 3.

**The fix:**
- **One place makes partial files:** `Partial::create(dir, name)` makes `<name>.<random>.beezip-partial` and records its path in a process-wide registry. `persist(to)` renames it into place and forgets it, and `Drop` deletes it and forgets it.
- **All three places use it,** along with `VolumeWriter`'s parts and the temp files that zip-in-a-codec spools to.
- **`partial::abandon_all()`** deletes every recorded file and refuses new ones. It takes the registry's lock, so a rename racing it either lands first, leaving a complete file, or fails.
- **Deleting open files:** the files are still open on the job thread. tempfile opens named files with std's default share mode, which includes `FILE_SHARE_DELETE` (checked in tempfile 3.27.0), so the delete succeeds. The file is gone by the time the process has exited, if not before.
- **The CLI's handler:** the first press cancels the job as before. The second calls `abandon_all()`, then exits with 130.

## 4. Commands, CLI and MCP

### 4.1 Inputs and outputs
- **`archive.create`:**
  - **Format:** `-f 7z`, and `.7z` decides it from the output name.
  - **`-m/--method`** takes the 7z methods when the format is 7z: `lzma2`, `lzma`, `ppmd`, `bzip2`, `deflate`, `copy`. They are kept in a separate `SevenZMethodName` enum, so zip's `store` can't be passed to a 7z. (As built, one `MethodName` enum takes both sets on the flag, and each format accepts only its own; §11.)
  - **Options:** `--solid[=false]` and `--encrypt-headers[=false]` are 7z only. `--encryption zipcrypto` stays zip only.
  - **`-v/--volume-size <SIZE>`** works for every format. It takes `100m`, `4g`, `700MB` or a number of bytes, and on the wire it is a number or such a string (`ByteSize`: `number | string` in TS).
  - **Output:** gains `volumes: Option<Vec<PathBuf>>`.
- **`archive.list`:**
  - `--sort name|size|packed|modified|kind` with `--reverse`; folders come first when sorting. `--kind file|dir|link` filters.
  - Without `--sort` the order stays archive order, so M1's outputs don't change.
  - Sorting a level of a million entries happens once per archive and key, in the cache (§4.2).
- **`archive.info`:**
  - gains `volumes` (the paths), the number of solid blocks for 7z, and `locked` and `recovery_record` for RAR;
  - `methods` includes the 7z filters and AES-256.
- **`file.detect`:** gains `volumes`, and a 7z or RAR SFX shows as `sfx: true`.
- **`formats.list`:** gains the `7z` and `rar` rows with their caps, the 7z methods and levels, and `7z` in `create`.
- **Config:** `[levels]` takes the 7z method names too (`lzma2 = 5`). `ppmd` and `bzip2` are shared with zip's methods, whose ranges match.

### 4.2 Engine (PR 2)
- **`Interactor::prompt(&self, job: JobId, id: u64, prompt)`** now gets the job id. A GUI prompt is answered by `cmd_respond(job, prompt, reply)`, so the interactor has to know which job is asking. The CLI and MCP interactors ignore it.
- **The archive cache** (`cache.rs`):
  - It is the PLAN's index cache, made a little wider: it keeps up to four open archives, and at most 4 million entries in all.
  - The key is the canonical path, plus each volume's size and mtime.
  - **What an entry holds:** the `Opened` reader with its index, plus the folder tree and the sorted orders `archive.list` builds.
  - **Lending:** a job takes its archive out of the cache and puts it back when done, so a reader is never shared. A second job on the same archive meanwhile opens its own.
  - **Per job:** the budget and counters are reset when an archive is lent.
  - **Encrypted archives aren't cached:** a cached reader would remember the password that opened it (§10).
  - `archive.list`, `archive.info` and `entry.read` use it, so the browser pages through a million-entry zip without parsing it again, and a preview doesn't reopen the archive. The CLI makes one call per process, so it gains nothing and loses nothing.

### 4.3 `cli.line` (PR 2)
"Copy as CLI" shows the `beezip …` line that runs a dialog's command, and must stay right as options are added. So it is built in Rust, from the same clap definition that parses it.

- **Input:** `{ command, args, shell?: powershell | cmd | posix, program? }`.
- **Output:** `{ line, omitted }`.
- **Building the line:**
  - The arguments are walked with the command's clap `Command`: positionals in order, then flags.
  - **Values:** a `bool` flag that is true becomes `--smart`, and one that is false becomes `--smart=false`. A list repeats its flag, and a value enum uses its CLI name.
  - **Quoting:** PowerShell by default: single quotes, with `'` doubled. `cmd` and `posix` quote their own way.
- **Passwords are never in the line.** `omitted` names them, and the copied command prompts for them in the terminal.
- **`program`:** the desktop passes `beezip` when the installer's `bin\` is on PATH, or otherwise the full path to a `beezip.exe` it finds next to itself (in development, the same `target\debug`).
- **Surfaces:** GUI and CLI, as `Surfaces::NO_MCP`; an assistant gains nothing from it.
- **The round-trip test:** for every command, sample arguments go through `cli.line` with `posix` quoting. The line is split, parsed by the real clap command and turned back into JSON; it must equal the input, minus `omitted`.

### 4.4 CLI
- **Flags:** the new `archive.create` and `archive.list` flags come from the input structs as before, and the help snapshots change with them.
- **Ctrl+C:** the second press calls `partial::abandon_all()` (§3.7).
- **Outputs:** the human output of `list` shows RAR and 7z methods, and `info` lists volumes.

### 4.5 MCP
- **No code changes:**
  - The tools already come from the registry, so `archive_create` takes `-f 7z`, `volume_size`, `solid` and `encrypt_headers`, and `archive_list` takes `sort`.
  - `cli.line` is hidden from MCP.
- **`docs/MCP.md`:** the tool table names 7z and RAR.
- **One new in-process test** lists a RAR fixture and extracts a 7z fixture into the root, so the UnRAR thread works under the MCP runtime.

### 5.4 Opening files
- **Dialog:** `@tauri-apps/plugin-dialog`'s `open()`, filtered to the readable extensions. The capability gains `dialog:default`, which is `allow-open`, `allow-save` and `allow-message`.
- **Drag and drop:**
  - `getCurrentWebview().onDragDropEvent`. One dropped archive opens in a new tab.
  - Anything else, or several files, opens the create dialog with them as inputs.
- **Command line and double-click:**
  - **Startup:** the paths in `BeeZip.exe`'s arguments are resolved against its working directory. They reach the page through an initialization script on the main window, which `lib.rs` now builds in `setup` rather than from `tauri.conf.json`. So the page has them before any listener could miss an event.
  - **Single instance:** `tauri-plugin-single-instance` is registered first, as it must be. A second `BeeZip.exe` hands its arguments and working directory to the first over `WM_COPYDATA` and exits before `Builder::run`.
  - **Forwarding:** the first instance resolves those paths, emits `open-paths`, then unminimizes and focuses its window. The plugin calls `AllowSetForegroundWindow` for it.

- **File associations:**
  - They are set in the bundle config and registered by the installer, so only an installed build has them (§5.5).
  - **Which extensions:** the archive extensions BeeZip reads: zip, 7z, rar, tar, gz, tgz, bz2, tbz2, xz, txz, zst, tzst, lz, tlz, lzma, lz4, br, sz, cbz, cb7, cbr and 001. Not the zip-based document formats (docx, jar, apk, epub…), which belong to their own apps.
  - **What the installer does:** Tauri 2.12.4's NSIS template uses `APP_ASSOCIATE`. It makes BeeZip each extension's default handler (`Software\Classes\.zip` → `BeeZip.zip`, per user) and keeps the previous value, which uninstall restores. For `.zip`, that takes double-click away from Explorer's built-in zip folder (§10).

### 5.5 Packaging (`cargo xtask dist [--debug]`)
PLAN's Naming section puts the CLI clash fix here:
1. **Build the CLI:** `cargo build --release -p beezip-cli --target-dir target/dist-cli`, its own target dir, so the GUI's rename can't clobber it.
2. **Write the bundle config:** `target/dist/tauri.dist.json`, from `packaging/windows/tauri.dist.json`, with the file associations generated from `formats.list`, so the list has one source.
   - `mainBinaryName = "BeeZip"`;
   - `bundle.resources`: `bin/beezip.exe` and `THIRD_PARTY_NOTICES.md`;
   - `bundle.windows.nsis`: `installMode = "currentUser"` (no admin) and `installerHooks = hooks.nsh`.

   It lives outside `tauri.conf.json` because tauri-build copies the resources when the app compiles and fails on a missing one, and the dev and CI builds have no staged CLI.
3. **Build the installer:** `pnpm tauri build --bundles nsis --config target/dist/tauri.dist.json`, which gives `target/release/bundle/nsis/BeeZip_<version>_x64-setup.exe`.

**`hooks.nsh`:**
- **Adding:** `NSIS_HOOK_POSTINSTALL` adds `$INSTDIR\bin` to `HKCU\Environment\Path`, through a PowerShell one-liner. It reads the value unexpanded, adds the folder once, writes it back as `REG_EXPAND_SZ`, and broadcasts `WM_SETTINGCHANGE`.
- **Removing:** `NSIS_HOOK_PREUNINSTALL` removes exactly that entry.
- **Why PowerShell:** NSIS strings hold 1 024 characters in its default build, and editing a long PATH with them can truncate it.

### 5.6 Closing with jobs running
- **The prompt:** `onCloseRequested` asks first: "2 jobs are running. Cancel them and quit?"
- **On yes:** it cancels them, waits for each to end (they remove their partial files), then destroys the window.
- **`RunEvent::Exit`** also cancels anything left and waits up to 10 seconds, as `beezip mcp` does on disconnect.

   - BeeZip checks memory itself, because the crate has no limit.
4. **Detection (§1):** add volume sets and 7z/RAR SFX in PE overlays.
5. **Desktop libraries (§1):** TanStack Virtual without TanStack Table, whose v9 is a different API. Sorting is done by `archive.list`.
6. **Desktop IPC (§1):** one Rust-to-page event (`open-paths`) beside the four commands; startup paths through an initialization script; prompts carry the job id; `cli.line` builds "Copy as CLI".
7. **Index cache (§1):** it caches open readers along with their indexes, and skips encrypted archives.
8. **CLI (§1, Front ends):** the second Ctrl+C deletes partial files before it exits.
9. **File associations (§1, Integration):** archive extensions only. NSIS makes BeeZip their default handler, and uninstall restores the previous one.
10. **Fixtures (§4):** the RAR fixtures come from libarchive 3.8.11 and rars 0.12.3, with 7-Zip as the oracle. WinRAR isn't needed.
11. **Third-party notices (§2):** shipped in the installer and the About page from M3. A full generated list stays in M6.

## 10. Decisions (taken while planning, 2026-11-03)
Each could reasonably go the other way. Say which to reverse, and I'll change it.
- **RAR through UnRAR via `unrar_sys`,** with our own FFI declarations in `beezip-unrar`.
  - The `unrar` crate can't stream.
  - `rars` (Apache-2.0, pure Rust) would remove the C++, the unsafe code and the license exception. But its README says it "started as an agentic development experiment" (May 2026) and "could use more testing at volume", and it has made seven releases since 3 October, three of them new minor versions.
- **`.zip` is associated by default,** like the other archive extensions. The installer then takes double-click on `.zip` from Explorer's zip folder, until uninstall restores it. The alternative is to leave `.zip` out, or only add BeeZip to "Open with".
- **7z with a password encrypts the file names too** (`--encrypt-headers` defaults on), which is sevenz-rust2's default. 7-Zip's default is off.
- **7z solid blocks** hold at most max(64 MiB, 4 × the dictionary), up to 1 GiB, so a preview never decodes more than that. 7-Zip uses multi-gigabyte blocks and compresses slightly better.
- **"Copy as CLI" leaves passwords out**; the copied command prompts for them. It quotes for PowerShell, with cmd and sh available.
- **Volumes work for every format.** That includes `a.zip.001`, which only 7-Zip and BeeZip read; the alternative is to allow them only for 7z and tar.
- **Several archives per window, as tabs.** A second double-click opens a tab in the running window rather than a second window.
- **The archive cache skips encrypted archives,** so no cached reader carries a password between jobs.

## 11. Found while building
### Found while planning
These came from reading the sources and running the two spikes. The sections above already follow them.

1. **`unrar` 0.5.8 can't stream:** `read()` collects an entry into a `Vec<u8>`, and its `ProcessMode` callbacks are private (§3.4).
2. **unrar_sys 0.5.8's structs are unpacked,** while `dll.hpp` packs them to 1 byte. Through unrar_sys's `HeaderDataEx`, `dict_size` read `HashType` (1 KiB for every entry) and the mtimes were shifted. Reading a symlink's header segfaulted, because UnRAR took the `RedirName` pointer from the wrong bytes. With a `#[repr(C, packed)]` copy the spike read 128 KiB and 32 MiB dictionaries, full FILETIMEs, and the targets of a symlink (`file.txt`), a directory link (`dir`) and a hardlink.
3. **unrar_sys 0.5.8 doesn't link with MSVC:** its `build.rs` omits advapi32, and 13 symbols went unresolved (`RegOpenKeyExW`, `OpenProcessToken`, `CryptGenRandom`, `SetFileSecurityW`…).
4. **UnRAR asks for a password once per handle** and reuses it. A per-entry password needs a reopen (§3.4).
5. **Cancelling** by returning -1 from `UCM_PROCESSDATA` ends the entry with code 21 (`ERAR_UNKNOWN`). BeeZip reads that as `Cancelled` when it was the one cancelling.
6. **sevenz-rust2 0.24.2 has no decoder memory limit** (`MAX_MEM_LIMIT_KB = usize::MAX / 1024`) and decodes an encoded header before anything else can look at it (§3.3). lzma-rust2 0.23.0 limits the dictionary to the uncompressed size and allocates as it goes, so the risk is the decoded size, not the declared dictionary.
7. **sevenz-rust2's `zstd` feature** enables zstd's default features, `legacy` among them, for the whole workspace, so it stays off.
8. **cargo-deny** would accept unrar_sys as `MIT OR Apache-2.0` without the clarification. Its license-file hash is XxHash32 with seed 0.
9. **Tauri's NSIS `APP_ASSOCIATE`** sets each extension's default handler, not just "Open with" (§5.4).
10. **@tanstack/react-table 9.3.1** is the v9 API (`useTable(options, selector)`, with features and row models declared explicitly), not the v8 one PLAN had in mind (§9).

### Found while building PR 1 (formats)
The crate APIs matched §3 with the exceptions below. The sections above were corrected where they would otherwise mislead. PLAN.md got the §9 corrections.

**Crate APIs and tools**

11. **7-Zip's links on Windows (§3.3):** `7z a -snl` on Windows stores a symlink as a file with the reparse-point attribute (`0x400`) whose data is the reparse buffer (`7z-links.7z`: 56 bytes for `link-to-hello`), not in the Unix form. The 7z reader reads both. A target is in the data, so a listing shows `name (link)` and extraction or `open_entry` reads it.
12. **sevenz-rust2's encoded header (§3.3)** keeps its block CRC in substreams info, after the unpack info. The header check stops at substreams info, which says nothing about memory; until it did, it missed every encrypted header BeeZip wrote, and `info` called them partly encrypted.
13. **UnRAR's volume notices (§3.4):** for each new volume UnRAR sends `UCM_CHANGEVOLUMEW` and then the narrow `UCM_CHANGEVOLUME`. Refusing the narrow one aborted every volume switch with `ERAR_EOPEN`.
14. **Split files in extract mode (§3.4):** list mode hides the continuation of a split file in its next volume; extract mode shows it when the file before it was skipped. BeeZip skips those headers, so ids stay the listing's.
15. **RAR 2.x–4 Unix symlinks (§3.4):** UnRAR reports them with an empty `RedirName`: their target is the entry's stored data, which UnRAR reads past the data callback even in test mode. BeeZip reads those few bytes from the archive itself, walking the RAR 4 block headers (types and sizes only), for unencrypted headers.
16. **RAR 2.x–4 names (§3.4):** without the Unicode flag, a name is in its creator's encoding. RAR for Linux writes UTF-8 there; UnRAR on Windows and 7-Zip decode it in a Windows code page (`abcdefghijklmnopqrsテスト.txt` came out as `…pâåpé¦pâê.txt` and `…πâåπé╣πâê.txt`). The same header walk reads a Unix-made name that is valid UTF-8 as UTF-8, which is what libarchive's own test expects. `fetch-rar.ps1` records that name with the same fix.
17. **A wrong RAR 4 header password (§3.4)** doesn't fail the open: the first header reads as damage (`ERAR_BAD_DATA`). When UnRAR was given a password, that is asked again like a wrong one.
18. **UnRAR changes `:` on Windows (§6):** `C:/abs.txt` comes back as `C_/abs.txt`. Everything else in the traversal corpus comes back unchanged, and FsSink still rules on all of it.
19. **UnRAR on Linux** reports reading past the end of a damaged entry as `ERAR_EREAD` (`test_read_format_rar_symlink_huge.rar`); BeeZip calls that `Corrupt`, not `Io`. Linux CI found it.
20. **`UCM_LARGEDICT`** exists in UnRAR 7.1 (a dictionary over UnRAR's own limit); BeeZip answers it from `decoder_memory`, after its own check.
21. **tempfile and `FILE_ATTRIBUTE_TEMPORARY` (§3.7):** tempfile creates named files with that attribute, and a rename keeps it, so every file M1 extracted carried it (checked: `0x120`). tempfile's `keep()` should have cleared it, but it ran on the old path after the rename. `Partial` opens files with std, and doesn't call `keep()`, which also fails past 260 characters.
22. **7-Zip and DOS times (§6):** 7-Zip converts a DOS (local) time with today's UTC offset; UnRAR, and so BeeZip, with the offset in force at that date. Across a daylight-saving change the two differ by an hour, so the interop test allows exactly ±1 h for RAR 1.5–4 entries. BeeZip's is the right one.

**Interfaces**

23. **`-m/--method` (§4.1):** clap takes one value enum per flag, so `MethodName` holds zip's and 7z's names together; `ZipMethodName` and `SevenZMethodName` are what each format accepts, and anything else is `InvalidArgs` (`--method store -f 7z`).
24. **`ByteSize` (§4.1)** keeps a string as written (`"100m"` reads back as `"100m"`), so "Copy as CLI" can show what the user typed.
25. **`ArchiveInfo` (§3.6)** gained `volumes`, `solid_blocks`, `encrypted_headers`, `locked` and `recovery_record`; `archive.info` reports them, with volume paths named the way the archive was given. Core gained `ErrorKind::BackendUnavailable` for a build without the `rar` feature.
26. **`ArchiveWriter::solid_block_limit` (§3.3):** `ops::create` groups files only for a writer that has a limit, so zip and tar keep M1's order. A 7z lists folders, links and empty files where they come, and the files in blocks after them.
27. **The test and null sinks (§3.3, §3.4)** stop on `PasswordRequired` and `WrongPassword`, as `ops::test`'s doc already said: in 7z and RAR 1.5–4 a wrong password shows as a failing entry, and the reader has to see it to ask again.
28. **`VolumeWriter` (§3.1)** keeps one part's handle open at a time; a set of thousands of 1 KiB parts would otherwise hold thousands of handles.

**Tests and tooling**

29. **Fixtures (§6):**
    - `7z-sfx.exe` is M1's zip SFX, so the 7z SFX is `7z-7zsfx.exe`.
    - The filter fixtures (BCJ, BCJ2, ARM64, Delta) filter the tree rather than an executable, so no third-party binary is committed.
    - `make-thirdparty.ps1 -Keep` adds the 7z set without regenerating M1's archives, whose bytes (atime, ctime) would change.
    - libarchive 3.8.11 has no unencrypted RAR 4 solid archive; `rar4_solid_encrypted` is the solid one, and `rar4_encrypted_filenames` (RAR 4 header encryption) joined the set.
    - No fixture uses old-style RAR volume names (`.rar`, `.r00`…): libarchive's set uses new numbering, and UnRAR names the next volume by a flag in the archive, so renaming the parts doesn't work. The naming rules have unit tests.
    - In total: 17 7-Zip fixtures (263 KiB, 194 KiB of it the SFX module), and 24 RAR fixtures (22 from libarchive, 2 from rars) plus 20 broken ones (380 KiB with the license files). 61 fixtures are in the manifest.
30. **The malicious 7z files (§6)** are written by hand in `xtask`, with an uncompressed header, not through sevenz-rust2: its writer won't declare an 8 GiB header or a 4 GiB dictionary, and the corpus must come out byte for byte the same every run.
31. **`abandon_all` (§6)** refuses partial files for the rest of the process, so its test is a test binary of its own (`tests/partial.rs`).
32. **The Ctrl+C check (§8):** the helper's `SetConsoleCtrlHandler(NULL, TRUE)` is inherited by every child it starts afterwards. Running several checks from one helper made the later children ignore Ctrl+C and finish (exit 0); each run needs a fresh helper.
33. **Mark of the Web (§8):** a file with a 280-character path had its `Zone.Identifier`, but PowerShell reads it only through `\?\`.
34. **Fuzzing (§6):** the sanitizer build links UnRAR, so both new targets run. The `sevenz` target goes through a scratch file like `zip`, because `SevenZReader` reads through `Source`. `mutations.rs` with the 7z and RAR bodies takes about 66 s (35 s before).
35. **The `sevenz` fuzzer's first find:** a 7z whose BZip2 block makes libbz2-rs-sys 0.2.6 (the latest; the pure-Rust bzip2 behind the `bzip2` crate) subtract past zero: `curr -= 1` on a `u8` in `decompress.rs`. Release builds wrap and then reject the data, as the C library does, but cargo-fuzz builds with overflow checks, and so do debug builds, where it was a panic. Both profiles now turn overflow checks off for that one crate (the fuzz profile declares `debug-assertions` so Cargo passes `-C overflow-checks=off` explicitly). The input is in `tests/fixtures/regress/`, with a test of its own (item 36). It is worth reporting upstream.
36. **A retry with no end (§3.4):** `mutations.rs` hung on a damaged RAR 4 whose header claims encrypted names. UnRAR asked for the password while reading the first header, not at open; the listing answered that request as attempt 0 every time, so the job gave the same password back, the header read as damage again, and it retried forever. It also stalled the `rar` fuzzer and timed out the Linux job. The listing now counts those failures like any other, every password loop in the 7z and RAR readers stops after `MAX_PASSWORD_TRIES` (8) whatever the context does, and the fuzzers run with `-timeout=60`, so a hang reports its input. The input is in `tests/fixtures/regress/`, whose test fails on a hang as well as a panic.

### Found while building PR 2 (desktop)

**Engine**

37. **`Interactor::expect` (§4.2, §5.1):** beside the job id, the trait gained `expect(job, id)`, which `JobCtx` calls just before it emits the `Prompt` event. The GUI makes its reply slot there, so an answer can't arrive before there is a slot to take it.
38. **The archive cache (§4.2):**
    - **Threads:** a cached reader moves between job threads, so `ArchiveReader` is now `Send`, and so are the codec decoders (`Box<dyn Read + Send>`). No reader needed more than that.
    - **When a reader goes back:** after success, or an error about the arguments (`InvalidArgs`, `NotFound`, `UnsupportedOperation`). After a read error or a cancellation it is dropped.
    - **"Encrypted archives aren't cached"** became the exact rule: a reader that a password reached is never put back, whichever archive it is. A zip whose data is encrypted but whose names aren't stays cached until someone reads an entry.
39. **What `archive.list` keeps (§4.2):**
    - **What it holds:** the folder tree and up to eight filtered or sorted listings per archive, as row numbers, not `EntryInfo`s. A level of a million entries costs 8 MB, and a page builds only the rows it returns.
    - **The tree** is built in one pass and keeps the order levels always had.
    - **Sorting by `modified`** compares times rather than RFC 3339 text, which misorders sub-second times.
40. **Every column sorts (§5.2):** the plan made seven columns sortable, but `--sort` had five keys; `method`, `crc` and `encrypted` were added.
41. **`cli.line` (§4.3):**
    - **Commands without a subcommand** become `beezip run <name> --json '…'`.
    - **Flags:** a `require_equals` bool is written `--flag` or `--flag=false`, and flags use their long names.
    - **The round-trip test** generates its arguments from each command's schema, so a new option is covered without a new sample.
42. **MCP, from trying `beezip mcp` in Claude Code:** Claude Code warned about schemars' `"format": "uint64"` on every integer, so the registry drops number formats from the schemas (`minimum: 0` stays). The server's instructions also still named only zip and tar.

44. **Libraries (§1):**
    - `@testing-library/dom` 10.4.2 was added: it is a peer of `@testing-library/react` 16 that the table missed.
    - `@tanstack/react-virtual` 3.14.22 brings `virtual-core` 3.19.7, which sizes the viewport from `clientHeight` (the jsdom test stubs it).

    - The page never calls `close()`; a real close arrives as `WM_CLOSE`. `core:window:allow-destroy` lets the close-requested handler finish the close.
    - The extract dialog's dry run is "Show plan", listed in the dialog.

**Packaging**

48. **Where the installer is built (§5.5):** `pnpm tauri build` runs with `CARGO_TARGET_DIR=target/dist`. In `target/debug`, Tauri's rename of `beezip-desktop.exe` to `BeeZip.exe` replaced the development `beezip.exe`, which Windows takes for the same file: the next "CLI" run started the GUI, and `cargo test` could have run it too. The installer is at `target/dist/<profile>/bundle/nsis/`.
49. **The associations (§5.4)** are `formats.list`'s extensions, less the zip-based documents and `.r00`, plus `.001`. Besides the plan's list that adds `.zz`, `.zlib`, `.tbz` and `.zstd`. Zip gained `.cbz`, as 7z has `.cb7` and RAR `.cbr`. They come out as 26.
50. **Windows decides the default (§5.4, §10):**
    - **The picker:** a newly registered handler doesn't become the default by itself. The first open of each type brings up Windows' "Pick an app", with BeeZip offered.
    - **`.zip`:** an Explorer `UserChoice` (hash-protected; on this machine `.zip` → `CompressedFolder`) wins over anything an installer writes. So the decision to take `.zip` by default holds only on machines without one. The installer doesn't touch `UserChoice`, and couldn't.
    - **The check:** the association check ran the registered `BeeZip.<ext>` commands, which is what Explorer runs once BeeZip is picked.
51. **Uninstalling (§5.5):** Tauri 2.12's `APP_UNASSOCIATE` writes back the default it saved at install time even when there was none, and leaves its `_backup` value. The empty default hid Windows' own `ArchiveFolder`, so `.7z`, `.rar`, `.tar` and the rest lost their handler. It also puts a stale value back over an app that took an extension since. The hooks fix both:
    - before it runs, the backup becomes the current handler, when that isn't BeeZip;
    - afterwards, the backup value goes, as does a default that is empty or still BeeZip's, and then the key if it is empty.
    - `cargo xtask dist` writes `target/dist/hooks.nsh` with the list. Install then uninstall now leaves associations and PATH exactly as they were.
    - Not handled: installing over an older install records BeeZip as the backup, so the original handler is lost; the updater is M6.
52. **PATH (§5.5):**
    - **Order:** the hooks keep empty segments, so a trailing `;` survives the round trip.
    - **The broadcast:** `WM_SETTINGCHANGE` goes out by deleting a variable that doesn't exist through .NET, which keeps P/Invoke, and its double quotes, out of the NSIS strings.
    - **A second `beezip`:** a `beezip.exe` earlier on PATH (`~/.cargo/bin` here) still wins in a new shell.
53. **`cargo xtask bigzip`** gives its files 0–99 bytes rather than none, so sorting by size has something to sort (1 001 000 entries, 176 MB).
54. **A million entries (§8):**
    - **Cold:** the first rows take about 5 s in the release build, nearly all of it opening the zip (`beezip list --flat --limit 1` alone takes 4.9 s; the folder tree adds 0.45 s). That is M1's reader: the `zip` crate's central-directory parse, the overlapping-entry check and a second pass for times. Worth profiling later.
    - **Warm:** after that, a folder of 1 000 opens in 23 ms and sorts in 17 ms, served from the cache.
