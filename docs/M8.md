# BeeZip — M8 (Virtual disks, Windows compression, WIM and installer speed) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M7.md`](M7.md) and keeps their
decisions. M7 gave BeeZip its own readers for disks, file systems and MSI. M8 takes on what M7
left, as the user scoped it on 2026-11-10 after 0.2.0:
- the virtual disks those file systems usually arrive in: VHD, VHDX, VMDK, QCOW2 and VDI;
- NTFS files Windows compressed with WOF (CompactOS), skipped today;
- WIM and ESD, Windows' install images;
- CAB and MSI extraction, still two to three times slower than 7-Zip's;
- MSI cabinets whose folder runs on from one embedded cabinet into the next.

Spikes on this machine back the plan, one folder each under `target/m8-spikes/` (`vhd`,
`vmdk-qcow-vdi`, `wof`, `wim`, `lzms`, `cab`), each with a `REPORT.md`; §15 sums them up. Each
candidate crate, and each prototype of BeeZip's own, was:
- checked against real images, byte for byte against an oracle;
- fuzzed for 15–20 minutes in a child process with an allocation cap and a timeout;
- timed against 7-Zip 26.00 (the timings in this plan were rerun alone afterwards: §15).

Test files that only Windows can write as administrator (WOF files, DISM's WIMs and ESD,
Windows-written differencing disks, a VHDX whose log was left active) were made in the
BeeZip-Win10 VM, as the user agreed on 2026-11-10, with a checkpoint taken first and applied
after (`target/m8-spikes/vm/`, `target/m8-spikes/samples/README.md`). Nothing ran elevated on the
host.

These findings change what was expected:
- **No crate is usable for any of the new formats,** as in M7. Of over forty candidates, most
  read only some variants. Others ask for gigabytes on crafted input, panic, or follow a backing
  file's absolute or UNC path as written. One "read-only" VHDX reader writes into the file. Every
  Rust LZMS decoder found is LGPL, a port of wimlib, or derived from disassembling Windows (§15).
  BeeZip's own readers and decoders passed every check, and every fuzz run once the WIM
  prototype's two findings were fixed.
- **LZMS has no public specification, and a clean-room decoder isn't worth it now** (8–15
  engineer-weeks, with legal points for the user). But **Windows' own Compression API decodes it**
  (`cabinet.dll`, Windows 8 and later): every chunk of Microsoft's install.esd came out matching
  its SHA-1, and fuzzing found nothing. So on Windows BeeZip reads ESD itself; on Linux and macOS
  an LZMS image goes to 7-Zip, as today (§5.3).
- **Natively, a virtual disk's files are a step away, not two.** 7-Zip opens a disk of several
  partitions as partition images, so getting at the NTFS inside the test VM's 64 GiB VHDX chain
  means streaming a 68 GB partition out first (80 s). BeeZip lists it in 0.7 s. 7-Zip can't
  read many variants at all: VMDK, QCOW2 and VDI children, zstd QCOW2, qemu's streamOptimized
  VMDK, a parent in another folder, an active VHDX log.
- **WOF's layout is confirmed on Windows-written NTFS,** byte for byte, for every algorithm and
  for files over 4 GiB. BeeZip's LZX decoder needs 29 lines more for WOF and WIM, and XPRESS is a
  300-line decoder of BeeZip's own from MS-XCA. 7-Zip extracts a WOF file as zeros of its full
  size, not empty as the scope first said, and `7z t` reports nothing wrong.
- **CAB and MSI close most of the gap.** A faster LZX decoder (1.45×) and serving files that
  share data from the copy already written bring LLVM's installer from 2.5× 7-Zip's time to 1.4×
  (test) and 1.5× (extract) (§6). What's left on installers of many small files is creating the
  files.
- **Two 0.2.0 bugs, fixed first, in a PR of their own, and released with 0.3.0** (§10, decision 1):
  - extracting any NTFS volume Windows formatted stops at `[SYSTEM]/$Extend/$RmMetadata/$Repair`,
    a zero-length file the NTFS reader takes for damaged (`join_checked`: a last VCN of −1
    overflows). Checked here with BeeZip 0.2.0 on a VM-made volume: 15 files, then `Corrupt`. M7's
    fixtures were all made by mkntfs, which writes no such file. The VM's Windows volume has 85;
  - on crafted input, an LZX match that runs past its 32 KiB frame decodes to wrong data with no
    error (§6.1), found by fuzzing the new decoder against today's.

## Scope

- **Virtual disks, read by BeeZip** (§3): VHD (fixed, dynamic, differencing), VHDX (the same, with
  4 KiB sectors and its log replayed in memory), VMDK (monolithic and split, sparse, flat and
  streamOptimized, `vmfs` descriptors, children), QCOW2 (v2 and v3, compressed with deflate or
  zstd, backing files, extended L2, data files) and VDI (fixed, dynamic, differencing). M7's
  partition and file-system readers run inside them: `vhdx > gpt > ntfs`.
- **WOF files decompressed** on NTFS (§4): XPRESS4K, XPRESS8K, XPRESS16K and LZX.
- **WIM, ESD and SWM read by BeeZip** (§5): XPRESS, LZX, and LZMS through Windows' own decoder on
  Windows.
- **Faster CAB and MSI extraction** (§6).
- **Embedded cabinet sets** in MSI (§7).
- **Unchanged:** the format names on the wire, detection (`backend/sniff.rs`), the commands and
  Explorer's menu. `formats.list` reports these formats with no backend.
- **Stays skipped:** EFS-encrypted and deduplicated NTFS files, and WOF files whose data is in a
  WIM elsewhere (WIMBoot).

## 2. How it fits

- **Routing.** `External::native()` gains `Vhd`, `Vhdx`, `Vmdk`, `Qcow2`, `Vdi` and `Wim`. As in
  M7, what a reader doesn't support (`UnsupportedOperation`, never `Corrupt` or `NotFound`) goes
  to 7-Zip when it's installed, with a note in Info, and without 7-Zip fails with 7-Zip's
  `BackendUnavailable` saying what BeeZip couldn't read.
- **A virtual disk is one more level under `DiskReader`.** A `VirtualDisk` (Read + Seek + Send, its
  virtual size, sector size, the bytes its files hold, and where they hold them) sits between the
  file and `Device`. `DiskReader::open` opens it first, then does what it does with a raw image:
  - a partition table goes to `disk()`, each readable partition a folder when there are several;
  - a bare file system opens straight through;
  - anything else is listed as one raw file, `<file stem>.img`, as 7-Zip names it, to open in
    turn.

  Info gains the level and its properties: `vhdx > gpt > ntfs`, the disk's type, block size,
  sector sizes, creator, parents, and whether a log was replayed.
- **WIM is its own `ArchiveReader`** (`format/wim/`), as MSI is: an ESD must be read in data
  order, one chunk serving many files.
- **Shared code moves:** `format/cab/lzx.rs` becomes `format/lzx.rs` (CAB, WOF and WIM use it),
  XPRESS is `format/xpress.rs`, and `decode_reparse` leaves `ntfs.rs` for a module NTFS and WIM
  share.
- **Files besides the one opened** (§3.6): a differencing disk's parent, a VMDK's extents, a
  QCOW2's backing and data files. They're looked for by rules that never open a network path a
  file names, and each is counted as input, as a volume set's parts are.
- **Limits** (§3.7): the ratio check reads a virtual disk as it would a raw image, and a disk-wide
  cap keeps a small file from claiming terabytes.
- **Detection doesn't change.** BeeZip already claims these formats (M6 §3.2). Pipable WIMs
  (wimlib's own layout) aren't claimed, and 7-Zip can't open them either.
- **Associations** (decision 6): `.vhd` and `.vhdx` stay Windows', which mounts them. `.wim`,
  `.esd` and `.swm`, and `.vmdk`, `.qcow2` and `.vdi`, become BeeZip's on install, since
  `xtask dist` associates every format with no backend that's in Explorer's menu.

## 3. Virtual disks

BeeZip has its own readers, in `format/volume/vdisk/`: VHD and VHDX (`target/m8-spikes/vhd/`),
VMDK, QCOW2 and VDI (`target/m8-spikes/vmdk-qcow-vdi/`). The two prototypes came to about 3,800
lines with the parent rules; in BeeZip they'll be about 4,000 with their docs, plus tests. They
read through positional reads, need read access only, and allocate a table only when the file
holds it, so memory is bounded by the file's size.

### 3.1 VHD

From Microsoft's VHD Image Format Specification.
- **Read:** fixed, dynamic and differencing disks; the footer at the end, or its copy at the start
  when the end's is damaged (with a note in Info); Virtual PC's 511-byte footer.
- **The size** is the footer's current size, as Windows reads it. A disk qemu-img rounded to its
  CHS geometry reads 8 KiB of zeros past the raw image, as qemu does.
- **Dynamic disks** read a block whatever its bitmap says (Windows zero-fills new blocks);
  differencing disks follow the bitmap (most significant bit first) to the parent.
- **The parent's identity** is its footer's unique id, which must equal the child's Parent Unique
  ID. The parent time stamp isn't checked: Hyper-V writes 0.
- **Refused:** a dynamic header version other than 1.0 (`UnsupportedOperation`).

### 3.2 VHDX

From MS-VHDX.
- **Read:** fixed, dynamic and differencing disks, blocks of 1–256 MiB, logical sectors of 512 or
  4096 bytes, every BAT state: not present (zeros, or the parent), undefined, zero and unmapped
  (zeros, never the stale offset they may hold), fully and partially present (the sector bitmap).
- **The log** (decision 3): a header whose LogGuid is set has writes still to apply. BeeZip
  replays them into an overlay in memory, by MS-VHDX §2.3.3's sequence search with wrap-around,
  and never writes the file. A log with no valid sequence, or a file shorter than its
  FlushedFileOffset, is `Corrupt`. Windows' own crash-left file (made in the VM by turning it off
  mid-write) replays to the disk Windows and qemu give. 7-Zip doesn't replay ("non-empty LOG was
  not replayed"), reads the stale disk and lists it as one item.
- **Every file Hyper-V writes has stale entries in its log** with LogGuid zero: those are never
  replayed.
- **Refused** (`UnsupportedOperation`): a version other than 1, a log version other than 0, a log
  over 64 MiB, an unknown region or metadata item marked required (7-Zip and Hyper-V refuse too),
  a parent locator of another type. Equal header sequence numbers, BAT states 4 and 5, and blocks
  in the header area are `Corrupt`.
- **Blocks past the file's end** read as zeros, counted in Info, as M7 reads a truncated image.

### 3.3 VMDK

From VMware's Virtual Disk Format 5.0.
- **Read:**
  - monolithicSparse (with compat6 and zeroed-grain entries);
  - streamOptimized, VMware's (grain directory at the end, a footer) and qemu-img's (at the
    start, no footer), whose grains are deflate;
  - monolithicFlat, twoGbMaxExtentSparse and twoGbMaxExtentFlat, their extents beside the
    descriptor;
  - `vmfs` descriptors with their `-flat.vmdk` (copied off a datastore);
  - descriptors mixing FLAT, VMFS, SPARSE, ZERO and NOACCESS extents (the last two read as zeros);
  - a bare sparse extent opened alone;
  - child disks and chains (`parentFileNameHint`), whose parent's CID must equal the child's
    `parentCID` (decision 4).
- **Descriptors** are UTF-8, or Latin-1 when they declare a `windows-125x` encoding.
- **Refused:** vmfsSparse (COWD) and seSparse snapshots (no public spec for seSparse; neither
  leaves a datastore often), raw device maps, compressed grains without markers, compression other
  than deflate. A device extent (`\\.\PhysicalDrive0`) is `Unsafe` (decision 4).
- **The redundant grain directory** isn't used: a damaged primary one is `Corrupt`.

### 3.4 QCOW2

From qemu's format description (`docs/interop/qcow2.txt`).
- **Read:** versions 2 and 3, clusters of 512 bytes to 2 MiB, any refcount width; zero and
  discarded clusters; clusters compressed with deflate or zstd; extended L2 entries
  (subclusters); an external data file beside the image; the dirty and corrupt bits (refcounts
  aren't needed to read, and Info says so).
- **Backing files** of QCOW2, raw, VMDK or VDI, the format from the header's backing format, else
  the extension, else sniffed. A backing file shorter than the disk reads zeros past its end.
- **Internal snapshots:** the active disk is read; Info gives the count (decision 2).
- **Refused:** encryption, legacy AES or LUKS ("BeeZip doesn't decrypt disk images"); QCOW
  version 1 (7-Zip reads the uncompressed ones, through the fallback); unknown incompatible bits
  or compression types. A backing name that isn't a file (`json:{…}`, `nbd://`, a UNC path) is
  `Unsafe`.

### 3.5 VDI

From public format documentation, never VirtualBox's code.
- **Read:** fixed and dynamic images with qemu's header (0x180 bytes) or VirtualBox's (0x190),
  discarded blocks, blocks stored out of order, a disk that isn't whole blocks long, blocks of
  any power of two from 512 bytes to 256 MiB.
- **Differencing images:** a VDI names its parent by uuid only. BeeZip reads the headers of the
  `.vdi` files beside the child and in the folder above it (where VirtualBox keeps the base and
  `Snapshots/` holds the children), at most 1,024, and takes the one whose uuidCreate is the
  child's uuidLinkage. Its uuidModify must equal the child's uuidParentModify when that's set
  (decision 4).
- **Refused:** extra bytes before each block (`cbBlockExtra`: VirtualBox never writes them, and
  readers disagree on them), undo images, version 0.x headers.
- **Not checked against VirtualBox itself:** no VirtualBox is installed here (it needs an admin
  install with kernel drivers). The crafted differencing chain is read alike by BeeZip's
  prototype and by virtdisk, whose docs say it's checked against VirtualBox 7.2.

### 3.6 Parents, extents and backing files

A file a disk names is opened only by these rules (decision 4). The spikes' `chain.rs` and
`FsOpener` become one module, `vdisk/files.rs`.
- **Where:**
  1. the path as recorded, when it's relative, resolved from the naming file's folder and
     staying on the same drive or share;
  2. the last part of the name, beside the naming file (so `/var/lib/libvirt/images/base.qcow2`
     and `C:\VMs\base.vhdx` from another machine still resolve);
  3. for VHD, VHDX and VMDK, whose parents carry an identity BeeZip checks, the absolute path as
     recorded, on a local drive only.
- **Never:** UNC paths (`\\server\share`, `//server`), `\\?\UNC`, `\\.\` and `\\?\GLOBALROOT`
  device paths, mapped network drives (GetDriveTypeW), `/dev/…`, `json:` and `proto://` names,
  alternate streams, DOS device names, reparse points on the way that lead off the local drives,
  or anything that isn't a regular file. Opening a UNC path would send the user's NTLM hash to
  whoever wrote the disk. A name like these is `Unsafe` (decision 4), not a 7-Zip fallback.
- **Identity:** VHDX the parent's DataWriteGuid against `parent_linkage` (and its sector size);
  VHD the unique id; VMDK the CID; VDI the uuids. A candidate that fails is passed over for the
  next one. QCOW2 has none, so its backing file is looked for by rules 1 and 2 only.
- **Bounds:** at most 64 levels and 4,096 files a disk; a file already in the chain (by canonical
  path) is `Corrupt`. qemu-img never finishes on such a loop.
- **A missing parent, or one changed since the child was made** (none of the candidates has the
  identity the child records), fails the open with `NotFound`, naming every place looked and why
  each failed: "`base.vmdk` beside it has CID 1a2b3c4d, not 5e6f7a8b: it changed after this disk
  was made" (decision 4). VMware and Hyper-V refuse such a chain too. 7-Zip can't read these
  either, so there's no fallback.
- **A disk spooled out of a codec** (`disk.vhdx.gz`) looks for its files beside the original.
- **Each file opened** reads through the same counting reader as the image, so progress and the
  ratio see it, and Info names the parents.
- **What BeeZip finds that 7-Zip doesn't:** 7-Zip follows a VHDX parent only by its relative
  path, never `..\`, never the absolute path or the name beside; it follows no VMDK, QCOW2 or VDI
  child at all.

### 3.7 Limits

Today the ratio check counts the bytes read from the archive file. A dynamic disk's holes, zero
clusters and compressed grains read little or none of it, so an ordinary file of zeros can trip
the check: a 200 MiB zero-filled file in a compressed QCOW2 reads none of the container and is
refused after the 64 MiB grace. A crafted 2 TiB dynamic disk of nothing, on the other hand, is
refused today only after 64 MiB has been written. The rule (decision 5):
- **A virtual disk reads as a raw image would.** The per-entry ratio counts virtual bytes, through
  a counter on the virtual disk. M7's `check_claim` still refuses a file system's sparse files
  against what the file system allocated to them.
- **Raw items** (a partition no reader opens, or the whole disk as one file) take their packed
  size from what the disk's files hold in that range (`VirtualDisk::allocated_in`), and are
  claim-checked before any byte is read. The crafted 2 TiB disk is refused at once.
- **One disk yields at most `max_ratio` times the bytes of its files**, across one pass
  (`extract`, and `open_entry` summed, so MCP's 256 KiB `entry_read` calls add up), plus the
  grace: `LimitExceeded` past it. A 1 KB VMDK can give 10 MB, a 20 GB one 200 TB.
- **Measured on the VM's 64 GiB chain:** 91,425 files read, none refused; the worst is
  `pagefile.sys`, 2.01 GB of which 163 MB is in the disk's files.

### 3.8 Plumbing

- **`part::read` takes the disk's sector size for MBR.** It reads MBR LBAs in 512-byte sectors
  today, so a 4 KiB-sector VHDX with an MBR would be misread (GPT already probes 4096).
- **Info properties** use 7-Zip's names where it has them (Method, Cluster Size, Sector Size,
  Creator Application, Parent), plus Log ("replayed in memory: 2 entries") and Snapshots.
- **Fuzz targets** `vhd`, `vhdx` and `vdisk` (VMDK, QCOW2 and VDI), seeded from the small images.

## 4. WOF

`target/m8-spikes/wof/`. Every WOF file in the VM-made samples (154, two of them 4.5 GiB) and the
VM's own 168 (Edge's `.pak` files, which its installer compresses with LZX) decoded byte for byte
as Windows reads them.

### 4.1 The layout, as Windows writes it

Established from Windows-written NTFS, never from GPL code:
- **The reparse point** (tag 0x80000017) is 16 bytes: WOF version 1, provider (2 the file provider,
  1 WIMBoot), the file provider's version 1, and the algorithm: 0 XPRESS4K, 1 LZX, 2 XPRESS8K,
  3 XPRESS16K. `ntfs.rs` already maps these.
- **`:WofCompressedData`** holds a table of the starts of chunks 1 to n−1, relative to the table's
  end, then the chunks. Entries are 4 bytes, or 8 when the file is 4 GiB or more. Chunks are
  4, 8 or 16 KiB for XPRESS and 32 KiB for LZX, each decoded alone; one that didn't shrink is
  stored as is, the last one included. The stream may be resident.
- **The unnamed `$DATA`** is sparse, with the file's size and no clusters, so the size and packed
  size M7 gives a WOF file are already right. Other alternate streams aren't compressed.
- **Ratios:** the worst seen is LZX on zeros at 368.9:1.

### 4.2 XPRESS

BeeZip's own decoder of MS-XCA's LZ77+Huffman (`format/xpress.rs`, about 300 lines and 150 of
tests). It decodes every stream Windows' Compression API and ntdll wrote, every WOF chunk Windows
wrote and DISM's XPRESS WIMs, at 77–86 % of Windows' own speed. 28.5 million fuzzed inputs, each
checked against `RtlDecompressBufferEx`, found nothing.
- **It follows Windows where MS-XCA's decoder pseudocode falls short:** the 32-bit match lengths
  Windows' compressor writes are read. compcol fails on exactly those.
- **Where it differs from Windows, only on damaged data** (decision 7): an over-full Huffman
  table, which Windows sometimes accepts and decodes non-canonically, is refused, as the spec
  says; input left after a chunk's output is full is ignored.

### 4.3 LZX for WOF and WIM

`lzx.rs` gains `Lzx::new_wim(bits)`, 29 lines more and 6 changed (`target/m8-spikes/wof/data/
lzx.diff`):
- no E8 header bit: translation is always on, with size 12,000,000;
- a block's size is one bit set for 32,768, else 16 bits, or 24 when the window is over 32 KiB;
- one frame per chunk, as long as the window, and a fresh state for each chunk. §6.1's rule
  that a match may not run past its frame's end applies at the chunk's end.

Found by trying variants on Microsoft's boot.wim, DISM's and wimlib's WIMs (32 KiB to 2 MiB
chunks) and WOF files; every other variant failed. CAB's decoding is unchanged: LLVM's 2.2 GB
cabinet and every CAB fixture decode as before, errors included.

### 4.4 In the NTFS reader

- A WOF file whose reparse point names the file provider and an algorithm BeeZip knows reads
  through a `WofReader` (`format/volume/wof.rs`, about 200 lines): Read + Seek, one chunk at a
  time, the table read as needed (never allocated whole), each chunk's bounds checked. `ntfs.rs`
  changes by about 50 lines.
- **`:WofCompressedData` is no longer listed once the file decodes** (decision 7). It's listed,
  as today, when the file can't be decoded.
- **Still skipped with the reason:** WIMBoot (provider 1: the data is in a WIM elsewhere), other
  provider versions, unknown algorithms, a WOF reparse point with no stream (`Corrupt`).
- Method names in Info stay `XPRESS4K`, `LZX`…

## 5. WIM and ESD

`target/m8-spikes/wim/` (the container) and `target/m8-spikes/lzms/` (LZMS).

### 5.1 The container

BeeZip's own reader (`format/wim/`), from Microsoft's 2007 WIM paper and libyal's WIM document,
the rest read from sample files and checked by SHA-1. In BeeZip about 2,500 lines with docs and
tests.
- **Read:** WIM 1.13 and ESD 0.14 (0xE00); none, XPRESS, LZX (chunks up to 2 MiB) and LZMS;
  solid resources of each method, concatenated in table order; chunks up to 64 MiB; several
  images; split sets (`.swm`, opened from any part, by GUID); integrity tables; files over 4 GiB;
  empty images and none.
- **Every blob's SHA-1** is checked when it's read, and each image's metadata on open. A flipped
  byte is caught, as `7z t` catches it. SHA-1 costs about 9 % of one LZX thread.
- **The integrity table** is checked by `archive.test` only (decision 8): it means reading the
  whole file. 7-Zip ignores it.
- **Refused** (`UnsupportedOperation`, so 7-Zip may take it): other versions, unknown compression
  flags or solid methods, chunks really over 64 MiB, spanned resources, pipable WIMs (7-Zip can't
  either), encrypted ESDs (no sample was found: an XML with `<ESD>` and `<KEY>` is taken for one).
- **Caps:** a metadata resource and the lookup table 256 MiB, the XML 16 MiB (skipped past it,
  with a warning), a decoded chunk 64 MiB, chunks in flight `decoder_memory` / chunk size. A
  folder list reached twice, a depth over 256, and bad names are warnings; a damaged folder lists
  the rest, with a warning (decision 8).
- **Totals:** install.esd's files add up to 65 GB across its images, 9.4 GB for image 1; 7-Zip's
  listing claims 106.5 GB. `max_total_bytes` is checked against the selected files before
  extracting, and the per-entry ratio uses each blob's share of its resource's packed size.

### 5.2 How it lists

Against 7-Zip 26.00's listing, entry for entry: boot.wim's 46,383 entries, install.esd's 901,138
and every DISM and wimlib sample. Extracted, boot.wim's image 1 matches `7z x` byte for byte.
- **Images** are folders `1/`, `2/`… as 7-Zip names them; a single image is at the top. Image
  names from the XML are in Info (decision 8).
- **Not listed:** 7-Zip's `[1].xml` and `[DELETED]/` (3,205 unreferenced blobs in install.esd);
  Info gives the count (decision 8).
- **Alternate streams** are `file:stream`, as for NTFS.
- **Hard links:** further names of a link group are `EntryKind::Hardlink` (200,451 in
  install.esd).
- **Reparse points** decode as NTFS's do, through the shared `decode_reparse`. Targets DISM
  "fixed" at capture (absolute paths inside the captured folder) become relative links inside the
  image; others stay as stored, so FsSink refuses `Users/All Users → /??/C:/ProgramData` (decision
  8). 7-Zip re-roots every absolute target at the destination.
- **WOF, deduplicated and EFS files** inside an image are skipped with the reason, as on NTFS.
  ntfs-3g's Interix links are listed as files, as 7-Zip lists them (decision 8).
- DOS attributes and the modified time to 100 ns are kept; short names and security descriptors
  aren't.

### 5.3 LZMS

- **What can be learned legally:** Microsoft documents only the Compression API's calls, not
  LZMS's bitstream; the WIM paper predates LZMS and solid resources; MS-XCA and MS-PATCH don't
  cover it; no patent or paper describes it. The only implementations are wimlib's and 7-Zip's,
  (L)GPL, and wimlib's author reverse-engineered it.
- **Crates:** every Rust LZMS decoder found is LGPL (ms-compress, newtua-mscompress), says it
  ports wimlib, or names Windows' internal symbols from a disassembly (napbat/lzms,
  jlevere/msdelta). None was built or run.
- **A clean-room decoder of BeeZip's own** is possible in principle, with the Compression API as
  a black-box oracle on Windows, but takes 6–12 weeks to derive the format by experiment and 2–3
  more to build, with high risk. It must be written by someone who never read wimlib's or
  7-Zip's LZMS code, which may rule out Claude, and Windows' license terms restrict reverse
  engineering. These are the user's to judge; it isn't planned (decision 9).
- **Windows' decoder** (`cabinet.dll`, `CreateDecompressor(COMPRESS_ALGORITHM_LZMS |
  COMPRESS_RAW)` and `Decompress`, Windows 8 and later) decodes WIM and ESD chunks as stored:
  - all 1,841 chunks of install.esd (11.38 GB), every stream matching its SHA-1;
  - DISM's ESD, every source file matching by SHA-256, and wimlib's variants up to 1 GiB chunks;
  - 2.2 million fuzzed inputs with guard pages around the buffers: no crash, hang, capped
    allocation or leak; 0.6 MiB a decoder.
  - **But:** damaged input sometimes decodes "successfully" to wrong bytes, so the SHA-1 check is
    what catches it. A handle used by two threads at once crashes: one decoder per worker (Send,
    not Sync). Over 1 GiB it refuses at once. One thread is 1.3–1.5× slower than 7-Zip's
    decoder; chunks decode in parallel.
- **So (decision 9):** on Windows, LZMS goes through `cabinet.dll`, loaded at run time from
  System32 (`LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_SYSTEM32`, since cabinet.dll isn't a
  KnownDLL and a load-time import would look in the app's folder first), and only when an LZMS
  image is read. `format/wim/lzms_win.rs`, about 110 lines with `#![allow(unsafe_code)]`, joins
  PLAN §1's short list of unsafe places. On Linux and macOS, and if cabinet.dll can't be loaded,
  an LZMS image is `UnsupportedOperation` and goes to 7-Zip, as today. XPRESS and LZX WIMs are
  native everywhere.
- **Windows 10** wasn't checked: the spike ran on Windows 11 (build 26300). The PR runs the
  spike's `verify` over a DISM ESD in the Windows 10 VM before it's opened.

### 5.4 Speed

Chunks are independent, so the reader decodes them on `[extract] threads` workers, bounded by
`decoder_memory` (ESD's solid chunks are 64 MiB). One small file from a solid ESD costs a whole
chunk, about 0.4 s; `open_entry` keeps the last chunk decoded. Timings (§15): testing
install.esd's image 1 takes 5–6 s on 16 threads against `7z t`'s 38 s, and 55 s on one; extracting
boot.wim's image 1 takes 19 s against 7-Zip's 26 s, and install.esd's 126–143 s against 200 s.

## 6. CAB and MSI speed

`target/m8-spikes/cab/`. M7 §16 left two gaps: the LZX decoder's speed, and files that share data
decoding their folder again. A third showed up: QGIS's 35,791 files take twice 7-Zip's time to
write. Timings are in §15.

### 6.1 The decoder

A sampling profiler written for the spike (no profiler can be installed here) put a fifth of the
time in `copy_match`'s byte-by-byte tails and a tenth each in Huffman decoding and refilling. The
decoder that replaces `lzx.rs` (decision 10; about +215/−86 lines) decodes LLVM's cabinet 1.45×
faster (372 → 538 MB/s run alone; up to 1.51× in the spike's A/B runs):
- a ring of twice the window plus 512 bytes, so matches copy 16 then 8 bytes at a time and may
  overrun into bytes no match can reach yet, and the hot loop checks one bound;
- the empty-tree check off the fast path; refilling split into an inline fast path and a cold
  tail; extra bits read without branches;
- a pair table: two literals per 12-bit lookup.

Memory per decoder goes from 2 to 4 MiB for 21-bit windows. Output is byte for byte the same on
every fixture, LLVM's 2.2 GB, QGIS's and RustDesk's installers, and the same broken files fail;
8.5 million inputs fuzzed against today's decoder found no difference otherwise. What's left is
about a fifth to a third more: a read-ahead thread for packed blocks (10 %), two-phase decoding, a
cheaper E8 pass. Not planned.

**A bug in today's decoder** (decision 1): on crafted input, a match that runs past the end of
its 32 KiB frame, in a 32 KiB window, decodes to wrong data with no error: the window is exactly
one frame, so the overflow lands on the frame's first bytes. MS-PATCH says no match may span a
32 KiB boundary, and 7-Zip calls it a Data Error in every window size; no real cabinet tested has
one (`lzx.rs`'s comment that Microsoft's compressor makes them is wrong). Such a match becomes
`Corrupt`, a five-line change, in PR 0 on today's decoder and in the new one. In WIM and WOF the
frame is the chunk (§4.3).

### 6.2 Files that share data

LLVM's installer has 20 files with the same folder, offset and size as another (973 MB:
`clang.exe` = `clang++.exe` = `clang-cl.exe` = `clang-cpp.exe`, 104.5 MiB each), all at their
folder's start; 14 of them start behind the 32 blocks the reader keeps, so 3.20 GB is decoded for
2.23 GB of folders. QGIS has 2,160 small ones and decodes about once anyway. Keeping more blocks
would take 128 MiB for 1.06×; the files are already next to each other in data order.

So the sink serves them (decision 11), about 105 lines:
- `EntrySink::same_as(entry, earlier)`, `false` by default. `cab.rs` offers it for a file whose
  folder, offset and size equal one already handed over.
- FsSink copies the file it wrote for that entry in this job, once it has checked that file is
  still the latest at its path and the expected size; the copy goes through the ratio guard as a
  hard link does.
- TestSink counts the file as passed without reading it, since its bytes are the earlier file's.
- The MSI reader passes it on only when the size and MsiFileHash match the earlier file's.
- Preview (`open_entry`) is unchanged, and faster only from the decoder.

### 6.3 Writing many small files, and MSI's hashes

Not spiked; time-boxed in the CAB PR (decision 13):
- **QGIS's extraction is bound by creating 35,800 files** (about 47 s against 7-Zip's 23 s, the
  same with or without the decoder work). The decoding thread hands each small decoded file to
  writer threads (`[extract] threads` of them, as M6 §6.3's zip extraction writes on several), with
  the bytes in flight bounded; FsSink's checks stay per file. WIM's extraction (§5.4) uses the
  same. Zip's workers decode as well as write, so this is a new, smaller piece.
- **MsiFileHash's MD5** is 1.8 s of QGIS's 5.4 s test: it moves to a second thread.

## 7. Embedded cabinet sets

A cabinet folder that runs on from one embedded cabinet into the next fails its files with
`NotFound` today: `cab.rs` follows a set only through files beside each other, and the MSI reader
opens each embedded cabinet alone.
- **The fix** (decision 12; about +138/−70 lines): `cab.rs` takes a resolver for the next and
  previous cabinets, `Siblings::{None, Dir(path), Streams(fn)}`, and reads a `CabStream` from it as
  it reads a sibling file. The MSI reader resolves only cabinets its Media table names (`#a.cab`,
  ignoring case), and opens a set once however many Media rows name its members. An embedded
  cabinet continuing into an external one isn't supported.
- **Test packages:** makecab.exe splits a folder across `a.cab` and `b.cab` (`MaxDiskSize`), and an
  MSI built on the msi dev-dependency embeds both (`span-small.msi`, 56 KB, the fixture). Windows
  Installer's own database API reads it, and `7z t` passes it, though 7-Zip lists only its streams.
- **How rare:** none of 485 packages on this machine (477 of them in `C:\Windows\Installer`) has
  such a set; 29 have several embedded cabinets. WiX makes them on request
  (`MaximumCabinetSizeForLargeFileSplitting` with `EmbedCab`), and a file over about 2 GB can't
  fit in one cabinet, so very large installers are where they'd appear.

## 14. Decisions

Approved by the user on 2026-11-10: every recommendation, except that 0.2.1 isn't released
("Don't release 0.2.1 and just work on 0.3.0"), so decision 1 is as amended below.

1. **Fix the two 0.2.0 bugs first, in a PR of their own** (PR 0, §10): the NTFS reader reads a
   zero-length non-resident stream as empty, so a Windows-formatted volume extracts whole; an LZX
   match past its frame's end is `Corrupt`. They ship with **0.3.0**; there's no 0.2.1.
   (Recommended was a 0.2.1 release; until 0.3.0, a Windows-made NTFS volume stops extracting at
   `$Repair`.)
2. **Virtual disks: BeeZip's own readers for all five** (§3), with no crate. They read the
   variants in §3.1–3.5 and refuse the rest: VHD/VHDX of unknown versions or required items, VMDK
   seSparse and vmfsSparse, QCOW version 1 (7-Zip reads the uncompressed ones), encrypted QCOW2,
   VDI blocks with extra bytes. A QCOW2's internal snapshots aren't listed, only counted; the
   active disk is what's read. A disk with nothing BeeZip recognises inside is one raw file,
   `<stem>.img`. *Alternatives:* vhdx-core for VHDX, rust-img-vmdk and rust-img-qcow2, or virtdisk
   for VMDK, QCOW2 and VDI, each with BeeZip's parent rules and limits around it: half the
   variants, and the faults in §15.
3. **A VHDX's active log is replayed in memory** (§3.2), never written to the file. *Alternative:*
   refuse it, as 7-Zip in effect does; Windows' own crash-left disk then shows stale data or
   nothing.
4. **Files a disk names** (§3.6):
   - looked for by the relative path (same drive or share), then by name beside the naming file,
     then, for VHD, VHDX and VMDK, by the absolute path on a local drive; each checked by the
     identity its format carries;
   - a name that points off the machine or at a device (UNC, `\\.\`, `json:`, `nbd://`, `/dev/…`)
     is `Unsafe`, never handed to 7-Zip;
   - a missing parent, or one changed since the child was made (its identity differs), is
     `NotFound`, naming every place looked and why each failed; the child isn't listed alone.

   *Alternatives:* look only beside the naming file, by name (stricter, and still finds every
   chain made here); read a changed parent with a warning; list a child whose parent is missing
   with zeros where the parent's data would be.
5. **Limits for virtual disks** (§3.7): the ratio counts virtual bytes, raw items are
   claim-checked against what the disk's files hold for them, and one disk yields at most
   `max_ratio` times its files' size per pass. *Alternative:* count the container's bytes as
   today, which refuses ordinary zero-filled files in compressed or trimmed disks.
6. **Associations** (§2): `.wim`, `.esd`, `.swm`, `.vmdk`, `.qcow2` and `.vdi` become BeeZip's on
   install, as every format BeeZip reads itself and offers in Explorer's menu does; `.vhd` and
   `.vhdx` stay Windows' (`WINDOWS_OWNS` in `xtask dist`), which mounts them. *Alternative:*
   associate only the WIM family, and leave the VM disks to VMware and VirtualBox.
7. **WOF** (§4):
   - BeeZip's own XPRESS decoder, not sootmark-prefetch (right but half as fast, a prefetch
     parser, lenient with incomplete tables);
   - `lzx.rs` gains the WIM mode and moves to `format/lzx.rs`;
   - `:WofCompressedData` is no longer listed once its file decodes (Windows hides it; listed, it
     would extract beside the file as an opaque blob);
   - on damaged data, an over-full Huffman table is refused as MS-XCA says, and input left after a
     chunk's output is ignored;
   - WIMBoot files (provider 1) stay skipped with the reason.
8. **WIM** (§5):
   - BeeZip's own reader, routed natively, with what it refuses going to 7-Zip;
   - images as `1/`, `2/`, a single image at the top, image names in Info (*alternative:*
     `1 - Windows 10 Pro/`);
   - no `[1].xml` or `[DELETED]/` entries, as 7-Zip lists them;
   - targets DISM fixed at capture become relative links inside the image, others stay as stored
     (*alternatives:* all as stored, as NTFS does; or re-rooted at the destination, as 7-Zip does);
   - the integrity table is checked by `archive.test` only (7-Zip ignores it);
   - a damaged folder lists the rest with a warning, as FAT does;
   - ntfs-3g's Interix links in a capture are listed as files, as 7-Zip lists them.
9. **LZMS through Windows' Compression API on Windows, 7-Zip elsewhere** (§5.3): `cabinet.dll`
   loaded at run time from System32, one decoder per worker, every stream's SHA-1 checked; a new
   `unsafe` place in core. No clean-room decoder now: weeks of work for Linux and macOS only, where
   7-Zip already reads ESD, and legal points (§5.3) that are yours to weigh. *Alternative:* leave
   ESD and LZMS WIMs to 7-Zip everywhere.
10. **The new LZX decoder** (§6.1): 1.45× faster, 2 MiB more memory per decoder (4 MiB for a
    21-bit window).
11. **Files that share data** (§6.2): served by the sink from the copy already written
    (`EntrySink::same_as`), and passed by `archive.test` without reading them again (in an MSI only
    when their size and hash equal the earlier file's). *Alternatives:* a sink that takes several
    entries for one stream (150–250 lines, saves only re-reading 973 MB); keeping more decoded
    blocks (128 MiB for 1.06×).
12. **Embedded cabinet sets** (§7), through a resolver limited to the cabinets the Media table
    names; an embedded cabinet continuing into an external one stays unsupported.
13. **Two speed items, time-boxed in the CAB PR** (§6.3): small decoded files handed to writer
    threads, and MsiFileHash's MD5 on a second thread. If they don't pay within the time box,
    the gap is noted in the docs. *Alternative:* leave both out of M8.
14. **The order of work** (§10): PR 0, then virtual disks, CAB, WOF, WIM, each after the previous
    merges, and 0.3.0 after the last. *Alternative:* one branch for all of M8, as M7 was.

## 16. Found while building

**PR 0 (`m8-fixes`, #35):**
- **Windows writes an empty non-resident stream as one piece whose last cluster is −1,** with no
  runs. The NTFS reader now takes it for an empty run list; runs after such a piece, or a second
  piece, are still damage.
- **The fixture is crafted:** ntfs-3g keeps an empty value resident, so `make-ntfs.sh` makes
  `thirdparty/ntfs/empty-nonres.img` and rewrites `empty.bin`'s data and `after.txt:empty` as
  Windows writes them. Rerunning the script made `rich.img` and `frag.img` again byte for byte.
  7-Zip 26.00 lists both streams as empty; BeeZip 0.2.0 said "its pieces overflow".
- **The LZX rule is three lines in `decode_symbols`.** Its test crafts a verbatim block of 32,765
  literals and an 8-byte match; 0.2.0 returned that frame with its first byte wrong. The spike's
  repro cabinets (0.7–1 MB) weren't committed.

**PR 1 (`m8-vdisk`):**
- **One stack of levels for all five formats.** The VMDK/QCOW2/VDI spike's model (a level
  answers data, zeros or a hole; a hole reads the next level down) carries VHD and VHDX as well,
  so a differencing VHDX is its own level over its parent's, and `vdisk/files.rs` is the only
  place a disk opens another file.
- **A parent that's been changed, or isn't the one named, is passed over for the next place,**
  with the reason kept: the open fails `NotFound` listing each place and why, as decision 4 says.
  The VMDK/QCOW2/VDI spike made a CID mismatch `Corrupt`.
- **A name that's only a network or device path is `Unsafe`;** one such name among others that
  were simply missing is listed in the `NotFound` message, never opened.
- **The local-drive check** (`GetDriveTypeW`) went into `safefs/disk.rs` beside the seek-penalty
  query, so no new file joins PLAN §1's list of `unsafe` places.
- **The ratio limit reads a virtual disk through a metered device:** each entry's ratio counts the
  disk's bytes, the disk-wide cap counts them per extraction (and across `open_entry` calls), and
  progress still counts the files' bytes, against all of the disk's files.
- **A native fixture record now fails if 7-Zip read it,** which the old check let through when
  7-Zip's levels happened to match (`mbr-fat.vhd`: `vhd > mbr > fat` both ways).
- **PLAN.md §2** gains only the virtual-disk row here; the WIM, NTFS and CAB rows change with
  the PRs that change them (§12 had them all in PR 1).
- **Built by two helpers in parallel** on the level stack and the file rules (VHD and VHDX; VMDK,
  QCOW2 and fixtures for VDI), each in a worktree, cherry-picked. The readers came to about 1,800
  (VHD 630, VHDX 1,180) and 1,630 lines (VMDK 925, QCOW2 706), with about 2,200 of tests.
- **A VDI chain of two or more children failed as a loop:** VirtualBox keeps a chain's children
  side by side in `Snapshots/`, so a grandchild's own file was among its parent's candidates.
  Such a file is now passed over, unless its header is the parent's.
- **Names never opened** grew past §3.6's list: qemu's `protocol:` names (`nbd:host:10809`,
  `file:…`), and on Windows an alternate stream or a DOS device name anywhere in a name, all
  `Unsafe`.
- **A VHDX's parent is checked before its own parents are opened:** its DataWriteGuid from the
  headers, then its sector size, so a candidate passed over leaves nothing of its chain behind.
- **Log replay** checks descriptors and data sectors before their CRC and caps the CRC work at
  four times the log's length (`Corrupt` past it), so crafted overlapping entries can't run for
  minutes; a valid log takes about once.
- **Refusals beyond §3:** a VHD footer version other than 1.0 and unknown disk types; VHD blocks
  over 256 MiB; VMDK grains over 1 MiB, grain tables other than 512 entries, and markers without
  compression (`UnsupportedOperation`). A VMDK grain entry of 1 is a zero grain only when the
  header's zeroed-grain flag is set, as the format says (the spike always took it as zero). A
  QCOW2 data file with a backing file is read; an unknown backing format is
  `UnsupportedOperation`.
- **Fixtures:** `thirdparty/vhd/` (38.7 MB on disk, 1.1 MB in git) by `make-vhd.ps1` with

- **The shared mutation test** walks the new fixtures too: about 245 s, from 171 s.

**PR 2 (`m8-cab`):**
- **The decoder is the spike's,** with the frame-end rule always on (the spike had it behind a
  switch for fuzzing) and today's tests, PR 0's included. Clippy's `manual_swap` rewrote the
  repeated-offset swap, with no measurable change.
- **Shared data and embedded sets are the spike's prototype diff,** applied whole. Then: a
  sink is told whether the reader still holds the shared bytes decoded (`same_as`'s `decoded`),
  and FsSink writes them from memory then rather than open a file it has just written; a copy is
  for data that would mean decoding the folder again.
- **Small files go to writer threads inside FsSink** (`safefs/behind.rs`), not through zip's
  "plan everything, then workers" path: a cabinet or MSI decodes on one thread, the MSI renames
  and checks every file, and a shared file is copied from one already written. Placement, the
  overwrite policy and its prompts, the report and the reader's checks (ratio, size, hash) stay
  on the job's thread; a file of at most 4 MiB is read whole there and handed to a worker, at
  most 64 MiB in flight. The sink waits for the workers before a hard link or a copy reads a
  file this job wrote, before a later entry writes the same file, and at the end. CAB and MSI
  ask for it; WIM can too.
- **MsiFileHash's MD5** goes to a thread of its own for files of 64 KiB or more, one file at a
  time, its digest awaited at the file's end, so a mismatch still fails that file's read. Smaller
  files are hashed in place: handing them over costs about what hashing does.
