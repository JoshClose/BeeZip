# BeeZip — M13 (`.bhive`) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M12.md`](M12.md) and keeps their
decisions, except PLAN §6, which it replaces (§12). On 2026-11-17 the user asked for a
compression format of BeeZip's own, with the extension `.bhive`: no compression at one end
("basically just bundling all the files"), high compression at the other, a medium default that
is fast with a decent ratio, and levels as none/small/medium/high or a 0–100 % slider. They
asked what novel algorithm could be created that hasn't been used.

A spike on this machine backs the plan (`target/m13-spikes/hive/`, a throwaway program built
only on crates in BeeZip's lockfile, with its raw results in `out*.txt` and a `REPORT.md`). It
packs a folder in memory in each candidate design and in the designs of zip, tar.zst and
tar.xz, checks every round trip, and times both directions. A helper searched for prior art.
§14 has the tables. The folders:

| Name | What | Files | Size |
|---|---|---|---|
| node | the desktop app's `node_modules` | 10,596 | 192 MiB |
| src | Cargo's unpacked crate sources | 70,913 | 972 MiB |
| build | the first 1.5 GiB of `target/release/deps` (rlib, rmeta, pdb, exe) | 826 | 1,499 MiB |
| packed | Cargo's downloaded `.crate` files (gzip: already compressed) | 1,822 | 337 MiB |

These findings shape the plan:
- **Three ideas that would have been BeeZip's own were measured and none earned its place**
  (§2): dictionaries trained from the archive's own files, sorting files by type, and spending
  effort block by block where it pays most.
- **What does pay is a design, not a new coder: independent cells, chunk dedup, and the two
  best existing coders.** Files are packed in the order given into cells of 4 to 64 MiB, each
  compressed alone. Against today's formats, in memory on this machine's 32 threads:
  - **The default level is a third to a half smaller than zip, and faster.** node 18.1 % of its
    size against zip's 28.5 %, src 13.2 % against 25.7 %, build 23.4 % against 35.1 %, at
    1.4–3.4 GiB/s where zip's deflate does 0.7–2.2 GiB/s.
  - **The high level matches or beats tar.xz, 1.5–1.9× faster:** node 14.3 % against
    14.2 %, src 10.6 % against 12.0 %, build 17.8 % against 20.4 %.
  - **Any file comes out by decoding one cell:** 3–5 ms at the fast levels, 55–340 ms at the
    high ones. A solid 7z or tar.zst decodes from the start of its block or stream.
  - **Every core works in both directions.** The fast levels decode at 11–18 GiB/s here; one
    zstd stream decodes at 1.3–1.9 GiB/s on its one thread.
- **Independent cells cost almost nothing at the fast levels,** because zstd's window there is
  2–8 MiB anyway: 4 MiB cells at zstd 3 pack node to 20.6 %, where one solid zstd 3 stream
  gives 20.75 %.
- **Chunk dedup is cheap and sometimes large.** Cutting files at content-defined points
  (about 16 KiB) and storing each distinct chunk once takes node from 20.7 % to 20.1 %, src
  from 16.2 % to 14.7 % and build from 30.8 % to 24.8 %, and is no slower, since there is less
  to compress. Whole-file dedup alone is 15 % of src.
- **zstd at 12–19 isn't worth a level.** LZMA2 in 16 MiB cells is 2–9 % smaller than zstd 19
  in the same cells at the same speed; it extracts 3–6× slower, still 1.2–4.7 GiB/s here.
- **For folders of small files, reading them is the cost.** BeeZip 0.4.0 makes a zip of node
  in 1.26 s and a tar.zst in 1.27 s; the spike reads the same files in 1.0–1.5 s and
  compresses them at the default level in 0.13 s. Cold, the 70,913 files of src took 3.5–5 min
  to read. No format changes that.
- **Prior art:** every part exists somewhere (§2); no mainstream archiver combines them.

Nothing was built into the repo, committed or pushed while planning. The user approved every
recommendation in §13 on 2026-11-17.

## Scope

- **A format,** `.bhive`, version 1, with a written specification (`docs/bhive.md`).
- **Reading and writing it in `beezip-core`:** create, list, extract, test, single-entry reads,
  and editing (add, remove, rename, convert) through the existing commands.
- **Five levels,** None to Max.
- **The app around it:** the Create dialog, the Explorer menu, the file association and icon,
  the CLI, the MCP server, the site and README.

## 1. Dependencies

- **zstd 0.14.3 and lzma-rust2 0.25.0,** as now. The spike used zstd's one-shot API with a
  pledged size and lzma-rust2's raw LZMA2 writer and reader.
- **xxhash-rust 0.8.19** (`xxh3`): already in the lock through backhand; it becomes a direct
  dependency of `beezip-core` for cell checksums.
- **blake3** (new; decision 6): the identity of a chunk, for dedup. A chunk taken for another
  must be the same bytes, so the hash must be one nobody can make collide. SHA-256, which
  BeeZip already has, is the alternative: about a third of the speed where the CPU has SHA
  instructions, and slower than the Fast level's compression where it doesn't.

## 2. What is new, and what isn't

**Byte-level coders are a crowded field with a hard frontier.** LZ77 with Huffman or ANS
(deflate, zstd, brotli, LZ4), LZ with a range coder (LZMA), BWT (bzip2), PPM and context mixing
are each two to four decades of tuning. A coder written here in safe Rust (the workspace denies
`unsafe`) would take months to be correct on hostile input and would be slower than zstd's C at
the same ratio. Nothing in the spike suggests a gap worth that.

**An archiver knows things a stream coder doesn't:** every file before the first byte is
written, their names, their duplicates. The spike tried four ideas that use this:

| Idea | Result | Verdict |
|---|---|---|
| **Dictionaries from the archive's own files:** one zstd dictionary (512 KiB) trained per file type, every cell compressed against it | With 4 MiB cells: node 21.5 % → 21.8 %, src 15.5 % → 15.7 % (worse: the dictionaries cost more than they save). With 256 KiB cells: 24.4 % → 23.6 % and 17.7 % → 17.4 %. Training took 0.7–1.3 s, cutting 4–7 GiB/s to 0.2–0.7 GiB/s | Out. A cell of a few MiB is its own context, and nothing needs cells smaller than that: a 4 MiB cell decodes in 3 ms |
| **Sorting files by type,** then name, path or size | src 16.3 % → 15.5 %, but node 20.6 % → 21.5 %: a package's files resemble each other more than they resemble other packages' files of the same type | Out. The order given is kept, which is also the order a disk reads best |
| **Effort where it pays:** each cell at every zstd level, then the best mix for a time budget, chosen knowing every outcome | 0–15 % less time for the same size at zstd 3–9. Large only on already-compressed data, where zstd 19 spent 84 CPU-seconds to save 1 % | Out, except its one real case: a quick probe stores what won't shrink (§3) |
| **Chunk dedup:** content-defined chunks, each stored once | node −3 %, src −9 %, build −20 % of the packed size; no slower | In |

**So the answer to "what novel algorithm": none that I could show to be better.** What `.bhive`
would be is a combination no mainstream archiver ships:

| | zip | 7z, RAR (solid) | tar.zst | `.bhive` |
|---|---|---|---|---|
| Similar files share context | no | yes | yes | yes, within a cell |
| One file without decoding others | yes | no | no | one cell |
| All cores when extracting | per file | per block | no | yes |
| Repeated content stored once | no | RAR: whole files | no | chunks |
| Damage loses | one file | the block or the archive | everything after | one cell |

**Prior art, from the helper's search** (about 45 searches and pages; details and links in the
spike's `REPORT.md`):
- **Independent blocks of similar files:** DwarFS (a read-only file-system image, the closest
  design), 7z's solid block size, WIM, ZIM, Apple Archive.
- **Chunk dedup as extents:** zpaq, DwarFS, casync, Borg and restic.
- **Per-block coder choice and raw storage:** DwarFS, ZIM, zpaq.
- **A trailing index that can be appended to:** zip, zpaq.
- **Dictionaries trained from the content:** RocksDB, WARC-zstd, and one archive, `zar`
  (a month old, opt-in). Not adopted here anyway.

The search found no established general-purpose archive that combines these; it did not reach
encode.su or proprietary game packers, so "not found" is the honest claim, not "doesn't exist".

## 3. The design

- **Cells.** The files' bytes, in the order given, are cut into cells of the level's size. A
  file that fits in a cell is never split; a bigger one fills cells. Each cell is compressed
  alone, by one of three coders: stored, zstd, or LZMA2. Each has an XXH3-64 of its contents.
- **Extents.** A file is a list of extents, each a range of one cell. That one mechanism gives
  big files (several cells), duplicate files (the same extents), and repeated chunks (an extent
  into an earlier cell).
- **Chunk dedup.** Each file is cut where a rolling hash of its bytes hits a pattern (a gear
  hash: at least 4 KiB, about 16 KiB, at most 64 KiB), so an insertion moves only the cuts
  near it. A chunk whose BLAKE3 was seen before becomes an extent into the earlier cell. A
  file's cells are found from the index alone; decoding a cell never needs another cell.
- **The probe.** At High, a cell is first tried with zstd 3; if that saves under 2 %, it is
  stored, and LZMA2 never runs on it. packed at High took 48 MiB/s for 94.6 %; stored, it is
  98.3 % at the Fast level's speed. Max tries everything.
- **The index** is written last, zstd-compressed: paths, sizes, times, attributes, links,
  extents, and the cell table. A footer at the end of the file points to it. Writing needs no
  seek, so a `.bhive` can go to a pipe; reading starts from the footer.
- **Recovery records** (decision 9). Each cell is preceded by a small record: its lengths, its
  coder, its checksum, and the paths and sizes of the files that start in it. If the index is
  lost (a download cut short), the cells before the cut can still be listed and extracted. It
  costs about 0.2–0.3 % of the archive (the names twice).
- **Memory.** A decoder holds one cell, and for LZMA2 its dictionary: at most 128 MiB a
  thread at Max, checked against `decoder_memory` before anything is allocated. The writer
  keeps as many cells in flight as fit a budget: xz's own preset 9 encoder takes 674 MiB, and
  Max's is of that order for each cell, so it runs fewer at once than there are cores.
- **Not encrypted** in version 1 (decision 11). The header has feature flags, so a reader
  refuses what it doesn't know instead of misreading it.

## 4. Levels

| Level | Coder | Cells | Dedup | node | src | build | packed | Compress, 32 threads | Compress, 8 threads | One cell |
|---|---|---|---|---|---|---|---|---|---|---|
| **0 None** | stored | — | no | 100 % | 100 % | 100 % | 100 % | a copy | a copy | a read |
| **1 Fast** | zstd 3 | 4 MiB | yes | 20.1 % | 14.7 % | 24.8 % | 98.3 % | 3.8–7.1 GiB/s | 3.0–4.3 GiB/s | 3 ms |
| **2 Balanced** (default) | zstd 6 | 8 MiB | yes | 18.1 % | 13.2 % | 23.4 % | 98.4 % | 1.4–3.4 GiB/s | 1.1–1.8 GiB/s | 5 ms |
| **3 High** | LZMA2 6 | 16 MiB | yes | 14.3 % | 10.6 % | 17.8 % | 94.6 % | 41–121 MiB/s | 30–51 MiB/s | 55–115 ms |
| **4 Max** | LZMA2 9 | 64 MiB | yes | 12.5 % | 9.9 % | 15.5 % | 93.0 % | 11–75 MiB/s | 11–40 MiB/s | 180–340 ms |

For comparison, the same folders in today's designs, in memory, 32 threads:

| Design | node | src | build | packed | Compress |
|---|---|---|---|---|---|
| zip (deflate 6, each file alone) | 28.5 % | 25.7 % | 35.1 % | 98.8 % | 0.7–2.2 GiB/s |
| tar.zst 3 | 20.8 % | 18.1 % | 30.6 % | 98.2 % | 4.0–6.0 GiB/s |
| tar.zst 19 | 14.6 % | 11.9 % | 21.9 % | 92.9 % | 22–75 MiB/s |
| tar.xz 6 (BeeZip's blocks of three dictionaries) | 14.2 % | 12.0 % | 20.4 % | 95.5 % | 26–79 MiB/s |

- **Sizes are of the original,** with an index counted. Speeds exclude reading the files.
  node at Max is the slow end of each range: its 192 MiB make only three 64 MiB cells.
- **None is a bundle:** files end to end, no dedup, so creating one is a copy and any tool can
  cut a file out with the index. Checksums are still written.
- **Why zstd 6 for the default and not 3 or 9.** From Fast to Balanced costs 2–3× the CPU
  for 6–10 % less; zstd 9 in 16 MiB cells would cost about 2× again for 5–6 % less (node 17.2 %,
  src 12.4 %, build 22.2 %). At 8 threads Balanced still runs past 1 GiB/s, faster than zip's
  deflate on the same threads (0.6–1.0 GiB/s).
- **The step from Balanced to High is 25–40× in time.** That is the price of LZMA2, and the
  size is what people expect of "high": 7z's. Between them only zstd 9 fits, for 5–6 %.
- **A slider of 0–100 % would map onto these five.** There are no more useful points between
  them, so the plan shows five named stops (decision 2).
- **What isn't known:** how these hold on photos, video and office documents. packed stands
  for all already-compressed data here; nothing on this machine was a fair sample of the
  others, and no laptop-class machine was timed (8 threads on this one is the nearest).

## 5. How it fits

- **Core:** `format/bhive/` holds the layout, the index, the chunker, the writer and the
  reader. `FormatId::Bhive` goes first in `FormatId::ALL`. Detection is by the 8-byte magic.
- **Writing:** `ops::create` already hands a writer its files in groups
  (`solid_block_limit`, `add_solid`); the bhive writer takes them as cells, compresses on
  worker threads as the parallel zip writer does (M6 §6.2), and writes cells in order.
- **Reading:** `entries` and `info` come from the index. `extract` and `test` decode cells on
  all cores and check each checksum. `open_entry` decodes the cells of one file, and keeps the
  last one decoded, so previews and `entry.open` are immediate.
- **Editing** (decision 14): the edit engine writes a new archive and swaps it in, as for zip
  and 7z. The bhive writer's `copy_from` copies cells as they are, compressed, and writes a new
  index: a rename or delete of anything costs a file copy and no decoding. A cell that has
  lost more than half its bytes to deletes is re-packed.
- **`archive.info`** reports the level, the cell count and size, and what dedup saved.
- **Commands, CLI, MCP:** `bhive` joins the create formats; `--level 0`–`4` or the names;
  `[levels] bhive`. Nothing else is new: list, extract, test, add, remove, rename and convert
  take it like any format.

## 6. The format on disk

`docs/bhive.md` is the specification, written in PR 1 before the code and kept exact. In outline:

| Part | Holds |
|---|---|
| Header, 16 bytes | the magic `\x89BHIVE\r\n` (the high bit and the line ending expose a transfer that mangled the file), the version, feature flags |
| For each cell | a recovery record, then the cell's bytes: raw, one zstd frame, or one raw LZMA2 stream |
| Index | one zstd frame: entries, extents, the cell table |
| Footer, fixed size | the index's offset, length and checksum; the magic again |

- **Every coded part is a standard stream.** A reader needs zstd, LZMA2 and XXH3, and the
  specification. Decision 12 adds an independent reader, a short Python script using only the
  standard library (Python 3.14 has zstd), which CI runs against BeeZip's archives: proof that
  the specification is enough to read the format, and that a `.bhive` is never locked to
  BeeZip.
- **Version 1 is frozen when it is released.** Later versions may add coders and features
  behind flags; every BeeZip reads every released version.
- **Stored in version 1:** files, folders, symbolic links, modification and creation times,
  Unix modes and DOS attributes. Not stored: extended attributes, alternate data streams,
  ACLs, hard links as such (their content is stored once by dedup).

## 7. Limits and damage

- **Checked when it opens:** the footer and index checksums; every offset and length against
  the file's size; every extent against its cell's size; path rules as for every format
  (the sink's). A cell's raw size above the version's maximum (256 MiB) is `Corrupt`.
- **`decoder_memory`** bounds a cell's raw size plus its dictionary before allocation.
- **A cell that fails its checksum or its decoder** fails the files with extents in it, as
  `Corrupt`, and the rest of the archive extracts.
- **A missing or damaged index:** BeeZip says so and offers what the recovery records list.
- **Extents may repeat by design** (dedup), so an archive can expand to far more than its
  cells hold. The existing limits on extracted size and entry count apply, and a test of a
  crafted archive of that kind is in §8.

## 8. Tests

- **Round trips:** a proptest over trees of files (empty, tiny, cell-sized ±1, several cells,
  duplicates, shifted copies) at every level; the result equals the input, and `test` passes.
- **The specification's examples:** small archives written out byte by byte in `docs/bhive.md`
  are fixtures, read by BeeZip and by the Python reader.
- **Fixtures** made by `cargo xtask gen-fixtures`, one per level and per feature, committed, so
  a later BeeZip is always checked against version 1 files written by this one.
- **Malicious:** truncated at every part; extents out of range; a cell table that overlaps; an
  index that claims 2^60 entries; a cell whose raw size lies; a dedup bomb.
- **Fuzzing:** two targets, the index parser and a whole small archive.
- **Interop:** the Python reader extracts each fixture identically, in CI on all three systems.
- **Editing:** the existing edit suite, run over bhive; a cell copied raw is byte-identical.
- **Speed:** `bench.run` is per codec and stays so; M13 adds no benchmark. The spike's program
  stays in `target/` for reruns.

## 11. Not in M13

- **Encryption** (decision 11).
- **Appending in place** without rewriting the file (the format allows it: new cells, a new
  index, a new footer).
- **Transforms by file type** (an x86 filter for programs, delta for images and audio).
  Unmeasured; the per-cell coder field leaves room.
- **A coder of BeeZip's own.** The same field leaves room for that too.
- **Splitting into volumes, comments, extended attributes and ACLs.**

## 12. PLAN.md corrections

- **§6** suggested that a `.bhive` be a 7z or tar.zst underneath with a manifest inside. M13
  replaces that with a format of its own, kept open by a specification, standard coders and a
  second reader. §6 becomes a pointer to `docs/bhive.md`; its extension check and rejected
  names stay.
- **"Own archive format: none in v1"** in the Context section becomes the format's name.

## 13. Decisions

For the user's approval. Each is a recommendation, followed by its alternative.

1. **The algorithm is the archive's design, on zstd and LZMA2** (§2, §3); no new byte-level
   coder. *Alternative:* write a coder of BeeZip's own first: months, slower than zstd in safe
   Rust, and nothing measured says it would be smaller.
2. **Five named levels:** None, Fast, Balanced, High, Max (`--level 0`–`4` or the names), the
   slider showing the names. *Alternatives:* 0–9 as zip and 7z have, with steps that barely
   differ; or 0–100 %, snapping to the same five.
3. **Balanced is the default: zstd 6 in 8 MiB cells** (§4). *Alternatives:* Fast (zstd 3:
   6–11 % bigger, 2–3× less CPU), or zstd 9 in 16 MiB cells (5–6 % smaller, about 2× the CPU).
4. **High and Max use LZMA2.** *Alternative:* zstd 19 in the same cells: 2–9 % bigger at the
   same speed, and 3–6× faster to extract.
5. **None is a pure bundle,** without dedup. *Alternative:* dedup at None too: smaller when
   there are duplicates, but every byte is hashed and a file is no longer one plain run.
6. **Chunk dedup from Fast up, by BLAKE3,** a new dependency. *Alternatives:* SHA-256, no new
   dependency, slower; or whole-file dedup only (src loses 9 %, build 20 %).
7. **Files in the order given; no sorting by type and no dictionaries** (§2). *Alternative:*
   sort by type and path or name, which helped src by 2–4 % and hurt node by 2–4 %.
8. **The probe at High, not at Max** (§3). *Alternative:* no probe: High then spends LZMA2's
   time on photos and video for a few percent.
9. **Recovery records before each cell** (§3), about 0.2–0.3 % bigger. *Alternative:* the index
   only, as 7z: smaller and simpler, and a cut-off archive is lost.
10. **An XXH3-64 for each cell; no hash per file.** *Alternative:* also a BLAKE3 of each file
    in the index, for comparing a file against a published hash without extracting it.
11. **No encryption in version 1.** A later version adds it behind a feature flag, designed on
    its own. *Alternative:* in version 1 (an authenticated cipher per cell and for the index,
    and a password hash): two more dependencies and the part of a format most costly to get
    wrong.
12. **A specification, and a second reader in Python checked by CI** (§6). *Alternative:* the
    specification alone.
13. **zip stays the default format.** `.bhive` is offered in the Create dialog and Explorer's
    menu, and opens in BeeZip by association. Nobody without BeeZip can open one today.
    *Alternative:* make it the default for new archives.
14. **Edits copy cells without decoding them, into a new file** (§5). *Alternative:* append in
    place now: faster for a big archive, and a second way of writing to get right.
15. **Three PRs** (§9), **each committed, pushed and merged when green without asking,**
    stopping before the release, as for M8–M11. *Alternative:* stop for the user's word before
    each merge.
16. **Ship in 0.8.0,** after the last PR, with the format marked version 1 and frozen.
    *Alternative:* ship it first as a preview that BeeZip promises to keep reading but may
    stop writing.

## 14. Found while planning

All in memory, on this machine (32 threads, 64 GB), each round trip checked. Sizes are a
percentage of the original with a compressed index counted; speeds are the original's MiB per
second and exclude reading the files. "Cells" are independent; "solid" is one stream.

**The folders.** Duplicate files: node 3.8 %, src 15.2 %, build 0 %, packed 0 %. Bytes in
repeated chunks among the distinct files (about 16 KiB chunks): node 7.2 %, src 13.4 %, build
19.0 %, packed 0.2 %. A fifth folder, `tests/fixtures` (127 MiB, mostly disk images), is 71 %
repeated chunks and packs to 5–9 % in every design; it changed no decision.

**Cell size, zstd 3, whole-file dedup only:**

| Cells | node | src | build |
|---|---|---|---|
| 1 MiB | 22.0 % | 17.5 % | 32.0 % |
| 4 MiB | 20.6 % | 16.3 % | 30.8 % |
| 16 MiB | — | 16.0 % | 30.6 % |
| 64 MiB | — | 15.8 % | 30.5 % |
| solid zstd 3 | 20.75 % | 18.1 % | 30.6 % |

Solid loses to cells on src because cells dedup whole files and the stream doesn't.

**zstd levels in 4 MiB cells** (src; node and build move alike): 1: 18.8 %, 3: 16.3 %,
6: 14.8 %, 9: 14.3 %, 12: 14.0 %, 15: 13.8 %, 19: 12.9 %, at 9,084, 8,235, 3,462, 1,579, 545,
237 and 143 MiB/s. Levels 12 and 15 cost 3–7× level 9's time for 2–4 %. Level 1 saves 15–30 %
of level 3's CPU and is 12–16 % bigger, so there is no level below Fast but None.

**High-end candidates, with chunk dedup:**

| | node | src | build | Compress | Extract |
|---|---|---|---|---|---|
| zstd 19, 16 MiB | 15.1 % | 10.8 % | 19.5 % | 42–112 MiB/s | 7.5–14.5 GiB/s |
| LZMA2 6, 16 MiB | 14.3 % | 10.6 % | 17.8 % | 41–121 MiB/s | 1.2–4.7 GiB/s |
| zstd 19 long-range, 64 MiB | 13.2 % | 10.2 % | 17.2 % | 12–71 MiB/s | 2.6–12.1 GiB/s |
| LZMA2 9, 64 MiB | 12.5 % | 9.9 % | 15.5 % | 11–75 MiB/s | 0.4–2.5 GiB/s |
| solid zstd 19 long-range (27) | 13.0 % | 10.0 % | 15.2 % | 12–49 MiB/s | 1.4–2.3 GiB/s |

**BeeZip 0.4.0 on node, files read from a warm cache:** zip 58.9 MB in 1.26 s; tar.zst
42.4 MB in 1.27 s; tar.xz 28.8 MB in 7.7 s; 7z 29.4 MB in 17.7 s. The spike's Balanced is
36.6 MB with 0.13 s of compression after the read; High is 28.9 MB with 4.7 s.

**Limits of the spike.** It is not the format: it holds everything in memory, writes no file,
and its dedup uses a non-cryptographic hash. Its speeds are of 32 threads; the
8-thread runs on the same machine were 1.3–2× slower at the fast levels, which says memory,
not cores, bounds them here. Three of the four folders are a programmer's; decision 3 should
be read with that in mind.

## 15. Found while building
