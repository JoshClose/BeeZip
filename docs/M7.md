# BeeZip — M7 (Native disk images and MSI) Plan

This plan builds on [`PLAN.md`](PLAN.md) and [`M0.md`](M0.md)–[`M6.md`](M6.md) and keeps their decisions. M6 read 17 formats through an installed 7-Zip (M6 §3). M7 reads eight of them with BeeZip's own code, so they open without 7-Zip:
- FAT;
- NTFS;
- ext2/3/4;
- GPT and MBR disks;
- bare HFS+ and APFS volumes;
- MSI installers.

These are the formats behind the "established" Rust crates the user picked on 2026-11-09. Versions and dates were checked that day against crates.io and the crates' repositories.

Spikes on this machine back the plan, one folder each under `target/m7-spikes/` (`ext`, `ntfs`, `fat`, `msi`, `parts`), each with a `REPORT.md`; §15 sums them up. Each candidate crate was:
- checked against the committed fixtures and M6's larger sample images;
- fuzzed for 15–20 minutes in a child process with an allocation cap and a timeout;
- timed against 7-Zip 26.00.

These findings change what was expected:
- **The new crates are mostly not usable.** They give wrong data with no error, panic or ask for gigabytes on crafted input, or can't move between threads. ext4-view, ntfs, fatfs, gpt and msi all fall into one or more of these (§15).
- **fstool, already a dependency** (0.5.2, for HFS+ and APFS inside DMGs), reads ext and NTFS much better. Fuzzing found:
  - ext: 750,000 inputs, no hang, and three failures, each avoidable by a check before opening;
  - NTFS: 413,000 inputs, no panic, hang or capped allocation, and one stack overflow BeeZip can check for first.

  Each needs only a cargo feature, with no new crates. BeeZip adds its own folder, name, time and link reading around it, where fstool loses information (§5, §6).
- **FAT, partition tables and MSI's tables are BeeZip's own code.** Each is small, and the crates fail exactly where BeeZip needs care. The only new dependency is **cfb** 0.16.0 for the MSI's compound file. Its own cargo-fuzz harness has run since 2022, and the spike's 1.2 million inputs found nothing.
- **MSI gains real names:**
  - BeeZip shows `ProgramFiles64Folder/RustDesk/RustDesk.exe` where 7-Zip shows cabinet keys like `filPUc62cd…`.
  - Every file of RustDesk's, QGIS's (35,791 files) and LLVM's installers came out byte for byte as `7z x` writes it.
  - **The catch:** BeeZip's CAB decoding (LZX) is about 4× slower than 7-Zip's, so extracting an MSI gets slower than today (§8.4).
- **7-Zip 26.00 gets ntfs-3g's sparse files wrong** (Data Error); the native reader gets them right.

## Scope

- **Native readers:**
  - partition tables (GPT and MBR) and raw disk images (§3);
  - FAT12/16/32 (§4);
  - ext2/3/4 (§5);
  - NTFS (§6);
  - bare HFS+ and APFS volumes (§7);
  - MSI (§8).

  Each is read only, as through 7-Zip.
- **Still through 7-Zip** (§9):
  - WIM/ESD, CHM, NSIS and CramFS;
  - VHD, VHDX, VMDK, QCOW2 and VDI, with the disks and file systems inside them;
  - MSI patches and transforms (`.msp`, `.mst`) and merge modules (`.msm`).
- **Unchanged:** the format names on the wire (`fat`, `ntfs`, `ext`, `hfs`, `apfs`, `gpt`, `mbr`, `msi`), detection (`backend/sniff.rs`) and the commands. `formats.list` reports these formats with no backend, and they're always available.
- **Not in M7:**
  - exFAT: fstool reads it, but it wasn't fuzzed and 7-Zip doesn't read it either;
  - the virtual-disk containers;
  - any writing.

## 1. Dependencies

| Crate | Change | Why |
|---|---|---|
| fstool =0.5.2 | features `hfs-plus`, `apfs` + **`ext`, `ntfs`** | ext and NTFS readers (§5, §6). Both features only add `std`, which is already on, so no new crates. 0.5.3 (2026-11-09) changes only archive, zip and tar writing, so the pin stays. |
| **cfb =0.16.0** (MIT) | new | MSI's compound file (§8). Brings fnv, uuid and web-time, all MIT/Apache and already in the lock. cfb 0.14.0 is in the lock through Tauri's infer, so cargo-deny's duplicate warning gets a `skip` entry. |
| msi 0.11.1 (MIT) | dev-dependency of beezip-core only | builds test MSIs, never ships |

Rejected, with the reasons in §15: ext4-view 1.0.0, ntfs 0.4.0 and its master, fatfs 0.3.6 and its master, gpt 4.1.0, mbrman 0.7.0 (fit for MBR, but BeeZip's own reader covers MBR and GPT in one place), and msi at runtime.

## 2. How the native readers fit

- **Routing.** Each `External` kind (`backend/mod.rs`) whose reader is now native opens through it, and the 7-Zip backend isn't asked. Detection doesn't change, and neither do the format names or the CLI.
- **Shared volume layer** (`format/volume/`):
  - a read-only `BlockDevice` over BeeZip's `Source`, windowed to a partition (today's `Device` in `format/dmg.rs`, made general);
  - a walk with a visited set, depth and path caps, and cancellation between folders;
  - the mapping from file system nodes to `Entry`.

  The DMG reader keeps using it for the volume inside an image.
- **Sparse files and limits.** An entry's packed size is the bytes the file system has allocated for it:
  - NTFS: from its data runs;
  - ext: from `i_blocks`;
  - FAT: not sparse, so its size.

  BeeZip's existing per-entry ratio check (`[limits] max_ratio`, 10,000:1 by default) then refuses a 100 GB sparse file in a 256 KiB image before any byte is read, as M6 does through 7-Zip. The spikes showed why it matters: both NTFS readers stream every zero of such a file, and one bench wrote 28 GB before it was stopped.
- **Untrusted sizes.** Every count and size is checked before memory is allocated for it, as in every BeeZip reader. The checks fstool itself lacks are listed with each reader. Every read of entry data checks the bytes delivered against the listed size.
- **Times** are UTC where the file system stores UTC:
  - NTFS: 100 ns;
  - ext: nanoseconds, with the epoch bits;
  - HFS+/APFS: as DMG today.

  FAT stores local time with no zone. Those times are taken as written, as 7-Zip and Windows show them (§4).
- **Names that aren't UTF-8:**
  - ext: names are bytes and go through BeeZip's name decoding (M5);
  - FAT: 8.3 names go through the OEM code page, chosen as for zip;
  - NTFS: names are UTF-16, and an unpaired surrogate becomes U+FFFD.
- **When a native reader can't read a volume** because the volume uses something it doesn't support (`UnsupportedOperation`, never `Corrupt`), and 7-Zip is installed, BeeZip opens the file through 7-Zip and says so in Info. Examples are NTFS clusters over 64 KiB, or ext features fstool lacks (decision 7).

## 3. Partition tables and raw disks

BeeZip has its own partition reader (`format/volume/part.rs`, about 300 lines). The spike's comparison is in `target/m7-spikes/parts/REPORT.md`.

- **GPT:**
  - The header is looked for at 512 and at 4096 bytes, because a 4K-sector disk has its header at 4096. fstool and 7-Zip read such a disk as MBR.
  - The entry array is bounded as fstool bounds it: at most 4096 entries of at least 128 bytes, a power of two, within the device, with the CRC checked.
  - The backup header at the disk's end is used when the primary one fails (fstool gives up instead).
- **MBR:**
  - the four primary entries, then the extended partition's EBR chain, whose links must go forward (mbrman's rule), so a chain can't loop;
  - logical partitions are numbered from 5, as Linux numbers them; fstool reads primaries only.
- **APM** stays fstool's, for DMGs.
- **What a disk shows** (decision 2):
  - A disk with one partition BeeZip can read opens straight into that file system, as 7-Zip does today (`mbr-fat.img` lists its files).
  - With several partitions, each one whose file system BeeZip reads is a folder named as 7-Zip names the partition, without its extension (`0.data/`, `1.linux/`).
  - The others stay files of raw sectors (`2.swap.img`), as today, for opening in turn.
  - Free space and the table itself aren't listed, unlike 7-Zip's `0.MBR` and `3.free`.

## 4. FAT

BeeZip has its own read-only FAT12/16/32 reader (`format/volume/fat.rs`): about 550–650 lines of FAT logic, plus the shared glue. The spike (`target/m7-spikes/fat/REPORT.md`) leaves its images and harness as the test bed, and fstool's FAT `Volume` serves as a second reader in tests.

- **FAT32 or not** is decided from the boot sector, as Windows' fastfat and 7-Zip decide it: FAT32 when the 16-bit sectors-per-FAT field is 0, otherwise FAT12 below 4,087 clusters and FAT16 above. All three crates use the cluster count alone, so they refuse the committed `fat32.img` (1,984 clusters).
- **Chains:**
  - every cluster number is checked against the FAT's range;
  - every chain walk stops after the volume's cluster count;
  - a file's chain must cover its size;
  - a chain that comes back to a cluster already seen in that file is `Corrupt`.

  fatfs reads wrong data silently on all four; fstool misses the last one.
- **Folders:**
  - deleted slots and the end marker are honoured;
  - long names are checked by their checksum and sequence, falling back to the 8.3 name;
  - NT's lowercase flags (byte 12) are applied;
  - `.` and `..` are skipped;
  - a folder already seen (by first cluster) isn't entered again.
- **Names:**
  - long names: UTF-16, an unpaired surrogate becoming U+FFFD;
  - 8.3 names: OEM bytes through BeeZip's name decoding (fstool only knows CP437).
- **Volume label:** the root folder's label entry, otherwise the boot sector's, shown in Info.
- **Truncated images** read zeros past the end, with a warning, instead of being refused.
- **Times:** modified (2 s), created (10 ms) and accessed (a date), as written.

## 5. ext2/3/4

The reader is fstool's ext module (feature `ext`) behind BeeZip's checks, with BeeZip reading what fstool would lose (`format/volume/ext.rs`, about 550–650 lines; `target/m7-spikes/ext/REPORT.md`).

- **Before opening, BeeZip checks the superblock:**
  - group count against the device;
  - `s_log_block_size` ≤ 6;
  - `s_log_groups_per_flex` < 32;
  - `s_blocks_count_hi` zero without 64bit;
  - `blocks_per_group` ≥ 256.

  Without this, fstool's group layout can ask for 128 GiB (`layout.rs:683`) or panic in a checked build (`layout.rs:680`).
- **Folders are read by BeeZip** from the blocks fstool maps:
  - names stay bytes (fstool turns them into U+FFFD);
  - inline-data folders, which fstool lists as empty, are read too;
  - names holding `/` or NUL are refused.
- **Symlink targets are read by BeeZip,** as bytes, at most 4096. fstool reads a 64-bit size into memory past its own cap (`mod.rs:4961`).
- **Times:** atime, mtime, ctime and crtime with nanoseconds and epoch bits, from the raw inode (fstool keeps 32-bit seconds).
- **Hard links** come from inode numbers, and so does the visited set.
- **Encrypted folders** (fscrypt's flag) are `UnsupportedOperation`, since fstool ignores the flag.
- **A journal that needs recovery** is replayed into a copy-on-write layer in memory, never onto the image. Without it, files show their stale contents (decision 4).
- **Speed:** listing and reading a 512 MiB image of 20,205 files took 0.75 s through fstool, against `7z t`'s 0.25 s. fstool reads one block at a time. BeeZip can read whole extents itself if this matters (§13).

## 6. NTFS

The reader is fstool's ntfs module (feature `ntfs`) behind BeeZip's checks, with BeeZip's own folder walk (`format/volume/ntfs.rs`, about 850–1,000 lines; `target/m7-spikes/ntfs/REPORT.md`).

- **Record 0 is checked before opening.** An image whose `$MFT` data refers to itself through its attribute list overflows fstool's stack (`mod.rs:281`/`:390`), which aborts the process.
- **Folders are walked by BeeZip** on fstool's public index functions, with a visited set. fstool's `read_directory` drops a second name of a file in the same folder, so a hard link would go missing.
- **Records and attributes** are read through fstool's public `read_mft_record` and `AttributeIter`:
  - `$STANDARD_INFORMATION` times at 100 ns, and attributes;
  - every data stream;
  - the runs, which give the on-disk size.
- **Data** comes through fstool's stream reader, which decodes LZNT1 compression and reads holes as zeros. EFS-encrypted files are listed but not readable (`UnsupportedOperation`).
- **What's listed** keeps today's 7-Zip view where it's useful, and does better where 7-Zip doesn't:
  - system files go under `[SYSTEM]/`, without `$BadClus:$Bad` (decision 3);
  - alternate streams appear as `file:stream`;
  - DOS 8.3 names are skipped;
  - reparse points are decoded by BeeZip (about 100 lines: symlink, junction, WSL symlink, WOF, Interix) and become symlinks, which FsSink judges as for any other format;
  - a second name of a file is a hard link (7-Zip lists a second file);
  - folders are listed.
- **Speed:** fstool reads plain data a cluster at a time (about 800 MB/s here). That's enough, since extraction is bound by writing files: 1.4–1.6 s for a 15 MB volume of 1,560 files, against `7z x`'s 2.1–2.9 s.

## 7. Bare HFS+ and APFS

The DMG reader already reads both inside images, through fstool, with BeeZip's decmpfs, capped attributes and composed names (M5 §5.11).
- A bare volume is the same walk over the shared device of §2 (signatures `H+`/`HX` at 1024 and `NXSB` at 32). Both fixtures open that way (`target/m7-spikes/parts/REPORT.md`).
- A raw disk with APM or GPT and an HFS+ or APFS partition goes through §3.

## 8. MSI

BeeZip has its own table reader on cfb, plus the layout of the installer's folders, with the files' data from BeeZip's own CAB reader (`format/msi/`, about 870 lines; `target/m7-spikes/msi/REPORT.md`).

### 8.1 Tables

- **Tables read:** the string pool and the `_Tables`/`_Columns` catalog, then Directory, Component, File, Media, MsiFileHash, Binary and Icon, read straight from their streams (about 180 lines).
- **Every size is checked before allocating.** The msi crate asks for up to 4 GiB from a string pool length (`stringpool.rs:115`) or a summary string (`propset.rs:69`), and panics on NULLs in its catalog.
- **Code pages:**
  - 1252, 65001 and the others decode through encoding_rs;
  - code page 0 is the system's ANSI code page, as Windows Installer reads it, not UTF-8 (the msi crate turns `café.txt` into `caf�.txt`).

### 8.2 Names

- **Each file's folder** is its Windows Installer folder property, with the long half of `short|long` names and the target half of `target:source`:
  - TARGETDIR itself is dropped;
  - a standard folder property starts again at the top wherever its row sits;
  - so does a merge module's copy of one (`System64Folder.<GUID>`);
  - `.` adds no level.
- **Examples:**
  - `ProgramFiles64Folder/RustDesk/RustDesk.exe`
  - `System64Folder/msvcp140.dll`
  - `LocalAppDataFolder/BeeZip fixture/readme.txt`
- **An empty file name** falls back to the File key.
- **Path limits:** every path is capped in depth (64 folders), length and total bytes. The spike's `deep.msi` is a valid 96 KiB MSI, 3,000 folders deep with 2,000-character names, and drove an uncapped layout past 1 GiB.
- **The same path twice:** real installers do this for conditional alternates (VC++'s x64 and Arm64 `msvcp140.dll`; 10 of 480 installed packages, 82 paths). The file with the lowest Sequence keeps the plain name, and the others take their File key before the extension: `msvcp140.<key>.dll` (decision 5).
- **Custom-action DLLs and icons** are listed as `[Binary]/<name>` and `[Icon]/<name>`. The tables, cabinets and signature are not listed (decision 5).

### 8.3 Data

- **Embedded cabinets** are read in Media order through BeeZip's CAB reader, from a cfb stream. Today the CAB reader needs a path; it gains a stream input (about 60 lines, plus a thread-safe wrapper around cfb's stream).
- **Missing files:**
  - an external cabinet is opened beside the MSI;
  - an uncompressed file is read from the source image beside the MSI, with its source names;
  - if either is missing, that file fails with a warning saying where it was looked for.
- **Integrity:** each file is checked against the File table's size and against MsiFileHash where there is one. WiX stores zeros for an empty file's hash, so that one isn't checked.

### 8.4 Speed

- Listing takes as long as 7-Zip's: 36–53 ms for RustDesk and LLVM.
- Extracting LLVM's installer (597 files, 3.2 GB) took 19–25 s, against 4.4–5.6 s through 7-Zip. The time is BeeZip's CAB/LZX decoding: `beezip test` on LLVM's bare cabinet takes 13.4 s, `7z t` 3.15 s.
- The MSI PR includes a time-boxed speed pass on LZX decoding (lzxd 0.2.7 and BeeZip's E8 step), which helps every `.cab` too (decision 6).

## 13. Not in M7

- **exFAT:** fstool's `exfat` reads it, but it wasn't fuzzed and opens entries by path only.
- **The virtual-disk containers:** fstool reads QCOW2; a fixed VHD is a raw disk plus a footer. Once disks and file systems are native, these are thin layers.

## 14. Decisions

Approved by the user on 2026-11-10, every one as written.


1. **Readers:**
   - fstool for ext and NTFS, with BeeZip's checks and own folder, name, time and link reading;
   - BeeZip's own FAT reader, partition reader and MSI table reader;
   - cfb for MSI's compound file.

   ext4-view, ntfs, fatfs, gpt and msi aren't used (§15). *Alternative:* fstool's FAT `Volume` with workarounds (about 350 lines). But it still can't read the committed FAT32 image, decode OEM names or show the label.
2. **Disks with several partitions** show each readable partition as a folder (`0.data/`) and the others as raw files. A single readable partition opens straight through. *Alternative:* 7-Zip's view, with every partition a file.
3. **NTFS** keeps `[SYSTEM]/` and `file:stream` as today, without `$BadClus:$Bad`, a sparse stream as long as the volume. Junctions become symlinks to their targets. *Alternative:* hide `[SYSTEM]/` entirely.
4. **ext journals** needing recovery are replayed in memory. *Alternative:* show the volume as written, with a warning that it wasn't cleanly unmounted.
5. **MSI:**
   - names as §8.2;
   - for the same path twice, the lowest Sequence keeps the plain name and the others take `name.<File key>.ext`;
   - `[Binary]/` and `[Icon]/` are listed;
   - uncompressed files are read from beside the MSI;
   - `.msp`/`.mst`/`.msm` stay with 7-Zip.
6. **The LZX speed pass** goes in the MSI PR, time-boxed. MSI goes native even if it leaves a gap, since real names are the point; the gap is noted in the docs.
7. **Falling back to 7-Zip** when a native reader can't read a volume because of something it doesn't support (never because the volume is damaged), when 7-Zip is installed. *Alternative:* no fallback; the error says what isn't supported.

## 15. Found while planning

**The crates** (details and repros in each spike's REPORT.md):
- **ext4-view 1.0.0** (ext):
  - Can't move between threads (it holds an `Rc`).
  - Gives no inode numbers, so neither hard links nor folder loops can be detected; one edited folder entry in a 384 KiB image made its listing grow past 1.6 GB.
  - Any inode with a time before 1970, or from 2038 to 2106, can't be read at all (`timestamp.rs:39`).
  - Holes on ext2/ext3 fail (`block_map.rs:194`).
  - Refuses the whole volume for inline_data, casefold, meta_bg, large_dir, ea_inode, mmp, and any journal needing recovery without 64bit and checksum v3, which is all of ext3.
  - Has three allocations that abort the process.
  - Upstream closed the outside fixes unmerged.
- **ntfs 0.4.0 and master** (NTFS):
  - 11 panic sites in 15 minutes of fuzzing.
  - Allocations of up to 4 GiB (`index_record.rs:69`), and memory past 1 GiB on a looping index.
  - Compressed files come back as raw clusters and `$Boot` as zeros, with no error.
  - No `$MFT` attribute lists.
  - No release since 2023.
- **fatfs 0.3.6 and master** (FAT):
  - Refuses the committed `fat32.img`, as fstool does.
  - Panics on cluster arithmetic (`fs.rs:448`), and hangs for good in one folder iteration (`file.rs:226`).
  - Reads short, wrong or past the image without an error.
  - 0.3.6 can't move between threads.
  - Its open fuzz issues date from 2021, and 0.4 is unreleased since 2023.
- **gpt 4.1.0** (GPT):
  - Asserts 128-byte entries, so the spec's 256-byte entries panic (`partition.rs:261`).
  - The table size is bounded only against overflow.
  - Needs write access.
  - The caller must know the sector size.
- **msi 0.11.1** (MSI):
  - Allocations of up to 4 GiB.
  - 8 panics on NULL catalog cells.
  - Can't move between threads.
  - Decodes code page 0 as UTF-8.
- **fstool 0.5.2:**
  - **NTFS:** no failure in 413,000 inputs; same-folder hard links dropped; a stack overflow on a self-referring `$MFT`.
  - **ext:** no hang in 750,000 inputs; a group-layout allocation of up to 128 GiB; a symlink read past its cap; a shift panic in checked builds; inline folders listed empty; names and link targets made lossy; the journal ignored unless replayed onto the device.
  - **FAT `Volume`:** no failure in 296,000 inputs; refuses small FAT32 and truncated images; CP437 only.
  - **Partitions:** 512-byte GPT only, MBR primaries only, no backup GPT header.
  - 0.5.3 fixes none of these, nor the four already in `docs/UPSTREAM.md`.
- **mbrman 0.7.0** (released 2026-11-09): right on every disk, including logical partitions, and an EBR linking to itself is refused.
- **cfb 0.16.0:** no failure in 2.4 million inputs over the two runs.

**7-Zip 26.00:**
- "Data Error" on ntfs-3g sparse files (`sparse.bin`, `sparse-100g.bin` in the NTFS spike's `rich.img`).
- A 4K-sector GPT disk read as MBR (already in `docs/UPSTREAM.md`).

**wixl 0.103** (a fixture tool):
- empties non-ASCII file names under code page 65001;
- writes Latin-1 names with code page 0;
- crashes on code page 932.

**BeeZip:** CAB/LZX decoding is about 4× slower than 7-Zip's (§8.4).

## 16. Found while building

**Part 1 (routing, the volume layer, partitions, bare HFS+/APFS):**
- **One branch, not five PRs,** as the user asked. The FAT, ext, NTFS and MSI readers were built
  in parallel on the plumbing commit, each in a worktree of its own, and cherry-picked.
- **`FileSystem::open` returns a reader that isn't `Send`:** fstool's and decmpfs's readers
  aren't, and nothing needs it to be.
- **Detection changed in one place:** GPT is sniffed at 4096 bytes too, since BeeZip reads disks
  of 4 KiB sectors itself.
- **Partition names follow 7-Zip's numbering,** logical partitions after the primaries (`2`, not
  Linux's `5`). An MBR partition has no name, so its folder is just its number (`0/`).
- **Without 7-Zip,** what a native reader doesn't support fails with 7-Zip's
  `BackendUnavailable`, saying what BeeZip couldn't read, so the app offers Install 7-Zip.
- **Info:** `ExternalInfo.backend` became optional, so the disks BeeZip reads report their levels
  (`gpt > ntfs`) and properties the way 7-Zip's levels are reported. The CLI prints
  `levels: gpt > ntfs` and the app a Levels row.
- **A hard link opens as its file** through `open_entry`, as tar's do, and extracts as nothing (the
  sink links it).
- **`.img` and `.msi` stay unassociated:** `xtask dist` now leaves out formats that aren't in
  Explorer's menu, since they no longer have a backend.
- **The native records** (`tests/fixtures/native-records.py`) are derived from make-7z.sh's 7-Zip
  records, not from BeeZip's output. HFS+'s decomposed names are composed, as for a DMG.
- **The branch started from c256f97,** before PR #30 merged; master was merged in.

**Part 2 (FAT):**
- **The FAT12/FAT16 boundary isn't agreed:** fastfat switches at 4,087 clusters, the spec, Linux
  and 7-Zip at 4,085 (as does `sniff.rs`). BeeZip follows fastfat, so a volume of 4,085 or 4,086
  clusters reads as FAT12 in BeeZip and Windows and as FAT16 in 7-Zip and Linux. mkfs.fat and
  Windows avoid those counts.
- **Folder chains can multiply a listing:** a crafted volume points many folders at shared
  directory clusters. Directory clusters are tracked across the whole walk, and paths are capped:
  65,536 slots a folder, 32 KiB a path, 512 MiB in all (`LimitExceeded`). The FAT is cached in
  at most 256 pages of 64 KiB.
- **A damaged folder is listed as far as it goes,** with a warning; a damaged file is `Corrupt`
  at its first read, so a test reports it and goes on.
- **Only the modified time reaches an entry:** `Entry` has no created or accessed time.
- **Sectors of 128 or 256 bytes are `UnsupportedOperation`** (Windows reads them); other sizes
  outside 512–4096 are `Corrupt`.
- **The edge images are built by the tests,** since the spike's are 16–36 MiB each; the spike's
  own run in the opt-in `the_spikes_images` test.

**Part 4 (NTFS):**
- **Extraction checks every selected file's claim before writing anything,** so a sparse file
  over the ratio limit refuses the whole extraction, as M6's 7-Zip path does. A real volume could
  hit this with a large `$UsnJrnl:$J` or a sparse VM disk; select around it.
- **A Windows volume may not extract whole:** an EFS-encrypted, WOF-compressed (CompactOS) or
  deduplicated file is `UnsupportedOperation` at its first read, which stops an extraction there,
  as a damaged file does. A test reports each and goes on. Reading WOF (LZX, XPRESS) or a
  skip-and-report mode in FsSink would fix it.
- **Info's encryption stays None for EFS files;** only `Entry.encrypted` is set.
- **Which name is the hard link** follows the folder's index order, since NTFS doesn't record
  which came first: in the fixture `readme.txt` is the link to `hard-readme.txt`, and its
  alternate stream a link to the other's.
- **Junction and absolute-symlink targets** are the substitute name with `/` (`/??/C:/Users`),
  which FsSink refuses as leading outside.
- **ntfs-3g's Interix FIFOs** can't be told from empty system files, so they're listed as files.
- **Limits beyond §6:** MFT records over 64 KiB and LZNT1 units over 1 MiB are
  `UnsupportedOperation`; a record budget of 3× `$MFT`'s records + 4096, an index budget of 2×
  the volume + 16 MiB, and 256 MiB of paths.
- **Two rich images** (`tests/fixtures/thirdparty/ntfs/`): `rich.img` (LZNT1, sparse, streams,
  links, reparse kinds) and `frag.img` (512-byte clusters, a file's runs over several records),
  made by `tests/fixtures/make-ntfs.sh`. The reader came to about 1,470 lines.
- fstool's NTFS bugs are in `docs/UPSTREAM.md`.

**Part 5 (MSI):**
- **Embedded cabinet sets aren't followed:** a folder that continues from one embedded cabinet
  into the next fails its files with `NotFound`.
- **Code page 0** goes through `NameDecoding`: with "auto", a name that's valid UTF-8 reads as
  UTF-8 and others in the system's ANSI code page; a chosen encoding wins.
- **Entry order is data order** (Media, then cabinet folder and offset), not Sequence order, then
  `[Binary]/` and `[Icon]/`.
- **Caps list rather than refuse:** a folder deeper than 64 or with a path over 4,096 bytes is
  listed at the top under its Directory key, with a warning; only names over 128 MiB in all are
  `LimitExceeded`.
- **Merge modules** have the package's CLSID and are told by their ModuleSignature table.
- **Method names are the CAB reader's** (`LZX`, `MSZIP`), not `LZX:21`.
- **cfb's `Stream` isn't `Send`,** so `CfbStream` reopens it for each read, under a mutex; at
  64 KiB reads that costs nothing measurable.
- **A null MsiFileHash part is 0x80000000,** Windows Installer's null integer.
- **The reader came to about 2,270 lines** with its docs, against the spike's 870.
- **Before the speed pass,** extracting QGIS's installer took 10.7 s (7-Zip 3.1 s), LLVM's
  17.7 s (3.9 s) and RustDesk's 0.47 s (0.15 s), every file the same as 7-Zip's.
